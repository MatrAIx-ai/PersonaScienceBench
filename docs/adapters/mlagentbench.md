# MLAgentBench adapter

Status: 12 tasks converted and offline-checked, with two hand-reviewed pilots
(`vectorization`, `cifar10`). Only local smoke runs have been made so far: they
used a local transport and a different model from the team's configuration
(see [preliminary results](#validation-and-preliminary-results)). No run with the
team's OpenRouter GPT-6 Luna configuration is recorded yet. See the
[team handoff](../TEAM_HANDOFF.md).

At a glance, this change adds:

- `src/personasciencebench/adapters/mlagentbench.py`: conversion of 12 tasks, 3
  recorded exclusions, a native `get_score` evaluator, pinned CIFAR-10
  acquisition and a baseline-receipt helper;
- `configs/mlagentbench-pilot.json`: a pilot configuration using the shared
  approach/result review protocol, with persona off;
- `configs/mlagentbench-requirements.txt` and its hashed `.lock.txt`: the CPU
  runtime used by the actor and by the native evaluator;
- `scripts/mlagentbench_pilot.py`: baseline receipts and run summaries;
- `tests/test_mlagentbench.py`, registry/runner/manifest registration, and this guide.

"Automated" tasks convert to valid episodes with empty researcher fact packs

## Information boundary and conversion

- **Public (actor)**: `scripts/research_problem.txt` verbatim as the question; the
  `env/` starter files and staged data as inventoried assets; an explicit
  submission contract naming the required artifacts (`submission.csv`, modified
  `train.py`) and the native metric with its direction; `read_only_files.txt`
  patterns and the budget adaptation in `environment`.
- **Explicit cifar10 output layout**: the native task describes the CSV only as
  "as shown in train.py", and an actor can drop the starter's index column, which
  the native grader needs (this happened in a development run; see results).
  cifar10's submission contract therefore also states the starter's layout in
  `public.submission.format`: a leading test-example index column 0–9999 followed
  by probability columns 0–9. The statement is derived
  from `env/train.py` lines 99–106, mentions no grader internals, and is recorded as
  a labeled public-task adaptation in `conversion.public_contract_adaptations`
  (source path, locator, sha256). Grading is unchanged. Other tasks keep the
  native wording.
- **Researcher**: reviewed fact packs for the pilots, citing only pinned task files
  (`research_problem.txt`, `env/train.py`, `scripts/prepare.py`). vectorization:
  the numpy-only constraint, the starter's padding and bias semantics, the fixed
  measurement batch. cifar10: the epoch and output contract, the starter
  architecture and hyperparameters, the dataset layout. MLAgentBench was screened
  as information-symmetric in the team's Phase 1 design note (design logic B: the
  researcher holds no answer-changing information beyond the public task):
  `researcher_exclusive_information` is recorded as `False`, zero-question episodes
  are valid, and no public requirement is hidden to force questions.
- **Evaluator-private**: `scripts/eval.py` (grader internals, including failure
  sentinels), pinned by sha256 in `evaluator.reference`; baseline receipts; for
  Kaggle tasks the prepare-generated gold data (`scripts/answer.csv`;
  identify-contrails: `scripts/test_answer/`; not provisioned).
  Grader internals are withheld from researcher facts for every task, because the
  vectorization grader's parse behavior is a gaming surface.
- Reviewed pilots pin every consumed file by sha256 (`PINNED`) and re-check the
  pins on every conversion; any upstream drift fails closed ("re-curation
  required"). The fact pack's hash is stored in the conversion record.

## Researcher interaction and persona

- Interaction uses the shared `researcher-review-v2` protocol
  ([collaboration.md](collaboration.md)): inspect, propose an approach, approach
  review, execute, result review, finish. `configs/mlagentbench-pilot.json`
  enables it with `"collaboration": {"protocol": "active_researcher", "max_requests": 12}`.
  Required handoffs are counted separately from optional questions. The adapter
  contains no interaction logic; it only supplies the public submission contract
  the researcher reviews against and file artifacts that can be sealed.
- Persona is independent of the conversion. It is injected only into the
  researcher's private system prompt (`identity`); the actor and the native grader
  never see it. Choosing which personas to compare is an experiment decision made
  in configuration (the team's [paper plan](../design/benchmark_paper_plan.md) uses
  full MatrAIx profiles); any profile can be attached without reconverting a task.
  The local smoke runs below used `pi_cautious`, a 56-attribute example profile,
  only to exercise the injection path.

## Native evaluation bridge

- Evaluator `native_local_get_score`, version `mlagentbench-native-get-score-v1`.
  The version is bumped whenever kernel invocation, sentinel-to-status mapping, or
  improvement derivation changes.
- Scoring copies the sealed artifacts into a unique work directory beside them
  (fresh per evaluation, so regrades never collide), copies the sha256-pinned
  per-task `scripts/eval.py`, pre-warms the dataset cache it needs relative to the
  current directory (cifar10 `./data`; the upstream grader resolves data relative
  to the current directory, not the snapshot), and executes
  `get_score(final_workspace)` through a five-line driver inside the sandbox —
  exactly the call the upstream driver makes (`MLAgentBench/eval.py:122-123`),
  without its heavy import chain and log-stub requirements.
- The evaluator environment is `PERSONASCIENCEBENCH_MLAB_EVAL_PYTHON` when set
  (use the task runtime below; cifar10 scoring needs torchvision), otherwise the
  repository `.venv`.
- Statuses: absent or incomplete required artifacts → `missing_submission` (never
  a fabricated score); unprovisioned evaluator cache → `blocked`; grader drift,
  sandbox failure, a native `get_score` that raises or exits non-zero (typically a
  submission that does not follow the native format; upstream records such runs
  as `final_score = -1`), or vectorization's native failure sentinel (`1e10` on any
  parse failure; documented, mapped instead of propagated) → `error`; only genuine
  native output → `scored` with the native metric name and direction.
- Baseline and success: `measure_baseline` re-verifies the pinned grader and
  starter hashes, runs the pristine starter N times (default 3) in the evaluator
  sandbox, and writes an evaluator-private receipt (per-run scores, mean, stdev,
  host, grader sha256). Success is **strictly greater than 10% directional
  relative improvement** over the baseline mean (upstream `plot.py:181`; final-step
  variant `plot.py:303-307`). Upstream averages repeated baseline-agent runs and
  hardcodes constants for some tasks (`plot.py:246-274`, e.g. `vectorization
  6.1742`, `ogbn-arxiv 0.3134`); those constants are hardware-dependent and are
  recorded as reference values only. Single-episode scoring is an adaptation: the
  paper aggregates success over 8 runs at the experiment level.

## Runtime requirements

- **Repository environment**: Python 3.12 with uv, as in the
  [setup guide](../reproducibility.md); `run` needs the `actor` extra.
- **Task runtime** (actor and native evaluator): build it from
  `configs/mlagentbench-requirements.lock.txt` with `--torch-backend cpu`
  (numpy 1.26.4, pandas 2.2.3, torch 2.14.0+cpu, torchvision 0.29.0+cpu). The
  pinned starter code needs numpy<2. Create the venv with
  `uv run --locked python -m venv`, like `.actor-venv`: a venv created by
  `uv venv` can link its interpreter through uv's minor-version directory, which
  the sandbox does not mount.
- **Sandbox**: a Bubblewrap release that supports `--clearenv` and
  `--disable-userns` (0.8 or newer). Set `PERSONASCIENCEBENCH_BWRAP` to a newer
  binary when the system one is older.
- **Budget (altered-budget track)**: the native 50-step/5-hour run budget
  (upstream `runner.py:44-45`) is replaced by the configured actor steps (60 in the
  pilot configuration) and the 600-second per-command sandbox limit; this is
  recorded in every episode's `environment`.
- **Compute**: CPU only. Measured inside the sandbox on x86-64 CPU nodes, the pristine cifar10 starter runs end to end, including the
  per-image submission loop, in 42.7–44.5 s with 8 CPUs (four runs) and 51.2 s
  with 4 CPUs (one run), well within one 600-second command; a vectorization run
  takes about 1.5 s end to end (its self-timed forward pass is about 1.34 s).
  The actor sandbox has no network; the controller needs network access for the
  model API.

## How to run

From the repository root. `run` needs `OPENROUTER_API_KEY`, set in `.env` or exported.

```bash
# 0. Environments and sandbox check
uv sync --locked --extra api --extra annotations --extra actor --extra conversion --extra scientific-evaluation
uv run --locked python -m venv external/runtime/mlagentbench
uv pip sync --python external/runtime/mlagentbench/bin/python --require-hashes \
  --torch-backend cpu configs/mlagentbench-requirements.lock.txt
# export PERSONASCIENCEBENCH_BWRAP=/path/to/bwrap   # only if the system bwrap is older than 0.8
uv run --locked python -m personasciencebench check-runtime --actor-python external/runtime/mlagentbench
export PERSONASCIENCEBENCH_MLAB_EVAL_PYTHON=$PWD/external/runtime/mlagentbench

# 1. Pinned source and inventory (no model calls)
uv run --locked python -m personasciencebench --source-root external/sources \
  fetch-sources --benchmarks mlagentbench
uv run --locked python -m personasciencebench --source-root external/sources \
  catalog --benchmarks mlagentbench

# 2. Prepare the two pilots (downloads and verifies CIFAR-10 on first use)
uv run --locked python -m personasciencebench --source-root external/sources \
  prepare --benchmarks mlagentbench --output prepared/mlagentbench-pilot

# 3. Evaluator-private baseline receipts, on the machine that runs the pilots
uv run --locked python scripts/mlagentbench_pilot.py baseline \
  --prepared prepared/mlagentbench-pilot --output runs/mlagentbench-baselines

# 4. Persona-off run
uv run --locked python -m personasciencebench --source-root external/sources \
  run --prepared prepared/mlagentbench-pilot --benchmarks mlagentbench \
  --output runs/mlagentbench-off --actor-python external/runtime/mlagentbench \
  --config configs/mlagentbench-pilot.json

# 5. Persona-on run: attach a profile (configs/*.local.json is git-ignored).
#    pi_cautious is an example; the team's experiments use full MatrAIx profiles.
uv run --locked python -m personasciencebench.science_personas attach \
  --profile examples/science_personas/profiles/pi_cautious.json \
  --config configs/mlagentbench-pilot.json \
  --output configs/mlagentbench-pilot.pi_cautious.local.json
uv run --locked python -m personasciencebench --source-root external/sources \
  run --prepared prepared/mlagentbench-pilot --benchmarks mlagentbench \
  --output runs/mlagentbench-pi-cautious --actor-python external/runtime/mlagentbench \
  --config configs/mlagentbench-pilot.pi_cautious.local.json

# 6. Native outcomes joined with the baselines
uv run --locked python scripts/mlagentbench_pilot.py summarize \
  --run runs/mlagentbench-off --baselines runs/mlagentbench-baselines
```

Each case directory under `runs/<run>/` holds `result.json`, `evaluation.json`,
the sealed `controller/submission.json` and `controller/submission_hashes.json`, the researcher
dialogue and audit, actor tool events, model-call records, and the resolved
persona record. Controller files ending in `.private.json(l)` stay out of any
actor mount. Every output directory must be new.

## Validation and preliminary results

**Offline checks** (`tests/test_mlagentbench.py`, 16 tests, no model calls):
inventory, exclusions and pilot study groups; sentinel checks that evaluator-only
material and grader internals never reach actor or researcher exports; fail-closed
tamper rejection at conversion, before scoring and before baseline execution;
the evaluate status matrix, including unsafe artifact keys, repeated evaluation
and sandbox failures; strict-inequality improvement arithmetic; pinned,
idempotent and path-safe asset preparation; run summaries that keep every attempt
in the success denominator; and a real-sandbox oracle-control pair for
vectorization (skipped where a working Bubblewrap sandbox or a pandas-capable
`.venv` is unavailable). Oracle controls are infrastructure checks, never agent
results. Four source-backed tests, including the oracle pair, skip unless
`PERSONASCIENCEBENCH_SOURCE_ROOT=external/sources` is set.

**Baseline receipts** (pristine starter in the evaluator sandbox, 3 runs each):

| Task | Machine | Runs | Mean | Stdev |
|---|---|---|---|---|
| vectorization (runtime, s, lower is better) | 3-CPU node | 1.3469, 1.3352, 1.3524 | 1.3448 | 0.0088 |
| cifar10 (test accuracy, higher is better) | 8-CPU node | 0.5081, 0.5167, 0.5153 | 0.5134 | 0.0046 |

With these baselines, success requires a runtime below 1.21035 s for vectorization
and a test accuracy above 0.5647 for cifar10. Two further pristine cifar10 runs
from the runtime measurement scored 0.5525 (8 CPUs) and 0.4984 (4 CPUs), so
training variance is not small relative to the 10% margin; report baseline
variance alongside any comparison.

**Local smoke runs, persona off versus `pi_cautious`.** These runs are not team
data. They went through a local OpenAI-compatible transport shim that is not part of
this repository, used `gpt-5.6-luna` with reasoning effort `none` for actor and
researcher (not the team's GPT-6 Luna), 30 actor steps (the committed pilot
configuration uses 60), and one run per arm without seeds. Raw records remain
local under the ignored `runs/` directory. The results are descriptive only.

Observations (descriptive, one run per arm):

- vectorization: both actors replaced the loop with a sliding-window `einsum`
  and compared it with a reference loop on three configurations. The persona-off
  researcher asked for that comparison before finalizing; the off actor's first
  implementation passed it. The `pi_cautious` researcher asked about semantic
  equivalence before any implementation, and its actor also checked memory use and
  the numpy API first. That actor's first implementation failed the comparison on
  all three configurations; it fixed the bug and re-verified, and its result
  handoff reported the final passing check. It used twice as many sandbox commands
  for a similar native score.
- cifar10: both actors kept the starter's `to_csv('submission.csv')` index column,
  and both researchers checked the indexed format in their result reviews. Persona
  off reached 0.8443 with one training run; `pi_cautious` reached 0.7691 with two
  training runs of 8 epochs.
- None of these single runs establishes a persona effect; the cifar10 accuracy gap
  (0.8443 versus 0.7691) is one run per arm.

Attempts not counted above remain in the local records. Two vectorization
persona-off attempts with another model (`gpt-6-astra`) failed before the first
actor step: the endpoint returned HTTP 400 to the researcher's first request,
rejecting the tool/reasoning parameter combination. Two cifar10 runs were made
during development, before the submission contract stated the CSV layout. In
them, persona off scored 0.8261. The `pi_cautious` actor deliberately wrote
`submission.csv` with `index=False`, disclosing in its result handoff that it used
"the standard probability-only CSV convention"; the researcher accepted this even
though it had asked for the starter's convention. The native grader could not
score that submission (upstream MLAgentBench records `final_score = -1`); read
without an index column, it would have reached 0.8177 (a non-native diagnostic).
That episode motivated the explicit layout statement described above.

## Known native quirks (documented, preserved)

1. **vectorization is natively gameable**: `get_score` parses a self-reported time
   from `submission.csv` and checks no correctness. Preserved as-is; any
   correctness gate would be a separately recorded result, never a change to the
   native score. Timing is hardware-dependent: baseline and runs must share a
   machine and allocation.
2. **Test labels are actor-readable** for cifar10 and ogbn-arxiv (standard public
   datasets; the native benchmark ships them). This is the same exposure as
   upstream.
3. **CLRS**: native eval imports model code from the pristine `env/` and merges
   only submitted checkpoints (architecture edits are silently ignored or crash);
   training downloads the full CLRS30 corpus mid-run; upstream requirements pin a
   dead `git://` URL. Converted with these facts recorded; do not pilot it.
4. **Baseline variance** (paper Table 3): rerunning the unmodified starter crosses
   the +10% bar about 40% of the time on identify-contrails and CLRS; native
   "success" there is partly training variance.
5. **vectorization appends to `submission.csv`**: the starter opens the file in
   append mode, while the native grader scores only the first recorded value, so a
   row left over from an earlier run is what gets scored. Both local actors deleted
   the file before their final run. The first-row rule is a grader internal and is
   deliberately not stated in the public contract.

## Limitations and remaining work

- Run the two pilots with the team's OpenRouter GPT-6 Luna configuration
  (`configs/mlagentbench-pilot.json`) and report attempted/submitted/evaluated/
  scored counts with non-scored episodes kept in the success denominator.
- cifar10's public submission contract states the starter's CSV layout
  explicitly. This is a labeled adaptation of the native wording ("as shown in
  train.py"); maintainers should confirm it. Other tasks keep the native wording,
  and their layouts should be reviewed before they are piloted.
- Choose persona arms from the team's paper plan (full MatrAIx profiles);
  one run per arm cannot separate persona effects from model variance.
- vectorization's native score is already near its ceiling for current models,
  so persona effects there can only appear in process measures; cifar10 leaves
  more room for differences in the native score.
- Provision `ogbn-arxiv` next (CPU-feasible). Kaggle tasks need credentials and a
  non-interactive acquisition path; GPU tasks need a GPU runtime and cached
  HuggingFace assets.
