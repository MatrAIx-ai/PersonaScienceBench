## Experiment design: cross-file versus in-file context for code completion

### Research question and estimand
Estimate whether substituting retrieved cross-file context for part of a fixed prompt-token budget improves code-completion performance relative to spending that same budget on in-file context. The primary estimand is the mean within-target difference in exact-match accuracy between the two conditions over eligible held-out completion targets. This tests the value of cross-file information under a fixed total context budget, not the effect of simply giving the model more tokens.

### Recommended dataset and task
No benchmark or task is specified in the supplied repository. As a recommendation, use a public, repository-organized benchmark with realistic code-completion targets and enough surrounding project files to retrieve from. Define each example as a repository snapshot, a target location, and a withheld completion. Prefer a fill-in-the-middle or next-span completion task whose target is an exact contiguous code span; make the task format, target-length limits, and handling of imports/comments explicit. If an established benchmark is selected, document its license, snapshot date, split construction, and preprocessing. Do not treat this recommendation as a source-supported project choice.

### Conditions and prompt construction
For every target, construct both conditions using the same model, tokenizer, task instruction, target location, decoding parameters, and total prompt-token ceiling, including code context and fixed prompt overhead:

1. **In-file-only control:** allocate the available code-context tokens to code surrounding the target in its own file. Use a prespecified, deterministic truncation rule (for example, nearest lines first, with balanced left/right expansion where applicable).
2. **Cross-file condition:** retain a prespecified minimum of the same local context, then allocate a prespecified portion of the remaining code-context budget to retrieved snippets from other files in that repository snapshot. Thus the cross-file treatment *replaces* some in-file tokens; it does not increase the total prompt length. State the local/cross-file allocation before evaluation and include a small allocation sensitivity analysis only if compute allows.

Use identical prompt wrappers and token accounting; apply a documented policy for overlong examples. The model should generate the same target span under the same stopping rules in both arms. Fix decoding (prefer greedy decoding for reproducibility) and do not tune prompts or retrieval on the test split.

### Retrieval recommendation
Use a simple, auditable retrieval procedure to avoid introducing a second model-dependent treatment. Exclude the target file from cross-file candidates. Rank remaining files/snippets using lexical relevance to identifiers and symbols visible in the prompt, optionally combined with lightweight structural signals such as imports or symbol references. Break ties deterministically; select non-overlapping snippets within the token allocation. Document candidate construction, ranking, snippets, and tokenization. A deterministic lexical baseline is feasible on CPU and makes the intervention interpretable. If adding embeddings or another learned retriever, treat that as a separate, pre-specified variant and fit/select it without test targets or test outcomes.

### Controls and validity safeguards
- **Paired comparison:** evaluate both contexts for each identical target and repository snapshot; pair all statistical comparisons by target.
- **Equal total token budget (principal control):** count all prompt tokens using the evaluated model's tokenizer and hold the ceiling constant. Keep non-context prompt text identical. Report actual token counts and truncation rates by condition.
- **Other fixed factors:** same model/checkpoint and version, tokenizer, target, snapshot, decoding, generation cap, stopping rules, and hardware/runtime configuration where possible.
- **Repository-level separation:** assign train/validation/test splits by repository, not random snippets. If using temporal snapshots, ensure the test target is evaluated against only files present at that snapshot. Keep all examples from a repository (and known forks/near-identical copies) in one split where feasible.
- **Target and retrieval leakage:** remove the withheld completion from model input and retrieval index; exclude the target file from cross-file candidates; ensure snippets do not duplicate the answer or expose a later version. Audit exact/near-duplicate code and generated artifacts. Apply identical license/secret filtering in both conditions. Retrieval may use only repository content available at prediction time.
- **Tuning discipline:** use validation data only for fixed choices such as context allocation and retrieval settings; freeze the procedure before test scoring. Keep test labels hidden from retrieval, prompt selection, and model selection.
- **Reporting:** log per-example inputs or reproducible references, token counts, retrieved paths/ranks, truncation, outputs, and scoring decisions, subject to data and license restrictions.

**Primary metric:** exact match of the generated completion after only predeclared, semantics-preserving normalization (ideally none beyond newline convention). Define normalization before scoring; do not normalize away identifier, whitespace, or syntax differences ad hoc.

**Supporting metrics:** token-level edit similarity (e.g., normalized edit distance or chrF), exact match stratified by target length and repository, parse/compile success where applicable, and a blinded human review of a manageable sample of disagreements for correctness/usefulness. Report generation latency and input/output token counts as operational outcomes, not substitutes for quality. Also report repository-level results and the number of repositories/examples. Avoid treating many targets from one repository as independent. Pre-specify exclusions and missing/failed generation handling; report denominators and failures per arm. Treat supporting metrics and subgroup analyses as secondary, and disclose multiplicity or label them exploratory. Report effect size and uncertainty rather than relying solely on a significance threshold.
