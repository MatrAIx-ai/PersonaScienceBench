## Experiment design

### Research question and estimand
Test whether adding relevant, retrievable context from other files in a project improves code-completion quality over an in-file-only baseline. The primary estimand is the mean paired change in exact-match completion rate at fixed completion sites when cross-file context is enabled, compared with the matched in-file-only condition. The conclusion applies to the chosen benchmark, model, prompt, and context-retrieval policy—not automatically to all languages or completion systems.

### Benchmark and dataset strategy
Use a public, permissively licensed, multi-file code-completion corpus with repository history or stable repository identities, such as a benchmark built from GitHub repositories. Prefer an established benchmark with fill-in-the-middle or next-span completion examples and project-level source trees. If none meets the requirements, construct a benchmark from pinned repository revisions: sample repositories across a declared language set, select eligible source files and completion spans, and retain the full project tree for retrieval.

Eligibility should require a parseable source file, enough preceding in-file context, a nonempty held-out target span, and at least one other source file in the repository. Include ordinary sites rather than only sites known to have a cross-file dependency; pre-register a secondary “dependency-present” subset using static references/imports or manually validated references. Record repository, revision, language, file, target location, and license. Deduplicate identical or near-identical files across repositories and remove generated/vendor code. Pin dataset versions, revisions, filters, sampling seed, and benchmark manifest.

### Completion task and paired conditions
At each site, hide a contiguous target span (for example, one syntactic unit or a fixed token-length range) and ask the same model to complete it. Select sites before inspecting model outputs. The two conditions use identical model/version, tokenizer, system instructions, completion prefix/suffix, decoding settings, and target sites:

1. **In-file baseline:** provide only the permitted local file context around the hole.
2. **Cross-file treatment:** provide the exact same local context plus retrieved snippets from other files in that repository.

Use deterministic decoding (temperature 0 where supported), fixed stopping rules, and no condition-specific tuning. Do not expose the target span or any duplicate copy of it to retrieval or prompt construction.

### Retrieval and matched context budget
Operationalize retrieval as a frozen, reproducible pipeline. Index only eligible source files in the same pinned repository revision, excluding the target file and generated/vendor files. Query using the target file path, language, imports/references visible outside the hole, and local prefix/suffix; never use the hidden target text. Rank candidate files/snippets using a fixed lexical-plus-symbol strategy (for example, exact imported-symbol/path matches followed by BM25 over identifiers and text), with deterministic tie-breaking. Select top-ranked snippets, trim at syntactic boundaries when feasible, and label each with relative path; exclude comments or metadata that reveal benchmark labels or the target.

Set a total prompt/context token budget in advance based on the selected model's context window. Reserve the same budget for context in both arms. The baseline fills it with additional in-file context (expanding left/right around the hole under a fixed rule); the treatment uses a fixed local in-file allocation plus cross-file snippets, with the total context-token count matched to baseline. Keep task instructions and target format identical. Report actual token counts and truncation rates. Also run a pre-registered sensitivity analysis with a natural fixed local-context allocation (same in-file portion in both arms and cross-file context added only in treatment) to distinguish the value of cross-file information from displacement of local context; this is a separate, explicitly non-budget-matched comparison, not the primary causal contrast.

The retrieval policy is itself part of the treatment. Freeze its code and parameters before test evaluation. Include a retrieval ablation with the same number of tokens of unrelated same-repository snippets, selected deterministically from non-target files, as a negative control for simply adding more code. Optionally include an oracle-retrieval diagnostic only as an upper bound, clearly separated from the primary result.

### Leakage-safe splits and controls
Partition at repository level, never by completion site or file alone: train/development repositories for prompt/retrieval tuning, and disjoint test repositories for final evaluation. If using an existing benchmark, inspect its split construction and deduplicate repositories and file contents across splits. Pin revisions and ensure no later repository revision is indexed. Retrieval at test time may access only the test repository's permitted tree and may not access other test targets or benchmark answers. The target file's full contents must not be available to retrieval; construct the prompt from a version with the target span removed. Search for exact and near duplicates across prompt sources and test targets, and document exclusions.

Hold constant the model and decoding, local context, target sites, prompt wording, output budget, hardware/software inference stack, and scoring code. Randomize or interleave condition order where feasible, cache deterministic outputs, and blind scoring to condition labels. Include a no-cross-file baseline and the unrelated-snippet negative control. Report failures, timeouts, and malformed outputs under a predeclared rule rather than silently dropping them.

### Outcomes
**Primary metric:** exact match of the generated completion to the held-out target after only benign normalization fixed in advance (e.g., line-ending normalization; do not normalize away semantic differences). Exact match is interpretable and resistant to selective post hoc metric choice, though strict.

**Secondary metrics:** token-level exact match / edit similarity (such as normalized edit distance), pass@1 on executable or unit-testable cases where a safe isolated test harness exists, parse/compile success, and completion validity. Report these separately; do not combine them into a single post hoc score. Analyze performance by language, target length, identifier/reference use, dependency-present subset, and available local context. Measure retrieval coverage and relevance separately, using mechanically observable reference matches and/or a small blinded manual audit; these are explanatory outcomes, not substitutes for completion quality.

### Statistical analysis
For each test site compute the paired difference in exact-match indicator (treatment minus baseline). Estimate the mean difference and a two-sided 95% confidence interval with repository-clustered resampling (bootstrap repositories, retaining paired sites within each sampled repository); use a predeclared significance level, e.g. 0.05. Report arm-wise rates, absolute percentage-point difference, relative change as descriptive, number of repositories/sites, and cluster-aware interval. A paired permutation test that swaps arm labels within site can serve as a robustness check, with repository-level dependence addressed through cluster aggregation or a cluster-aware procedure. Avoid treating all sites as independent.

For secondary binary metrics, use the same paired and clustered approach. For continuous edit similarity, report paired difference with repository-clustered intervals. Predefine subgroup contrasts and treat them as exploratory or adjust multiplicity (e.g. Holm correction) if confirmatory claims are desired. Report sensitivity to repository weighting (site-weighted primary; equal-repository-weighted secondary), token budget, retrieval method, and duplicate filters. Conduct a power/precision calculation using pilot-free assumptions or a development-only estimate of baseline rate, paired discordance, repository count, and intra-repository correlation; determine required repositories/sites before test evaluation. Do not use test-set results to increase sample size or tune the method.
