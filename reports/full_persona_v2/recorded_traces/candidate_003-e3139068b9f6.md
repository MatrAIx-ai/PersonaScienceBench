## Experiment design

### Question and estimand
Test whether adding useful cross-file source context improves code-completion performance relative to using only the target file’s preceding context. The primary estimand is the mean within-example performance difference between a cross-file arm and an in-file-only arm, under an otherwise identical completion system and a matched total prompt-token budget. This matched-budget comparison helps separate the value of cross-file information from the effect of simply supplying more tokens.

### Arms
For every benchmark example, run the same fixed model and completion interface under two conditions:

1. **Control — in-file only:** provide the target file’s permitted prefix (and any identical task instructions). No source content from other files is included.
2. **Treatment — cross-file context:** provide the same target-file prefix and instructions, plus retrieved excerpts from other files in the same repository that are available at the prediction point. Retrieval is deterministic and blinded to the answer and target suffix.

For the primary, equal-budget comparison, define a fixed context-token allowance in advance. The treatment divides this allowance between the in-file prefix and retrieved cross-file excerpts. The control uses the same total allowance for target-file prefix/context, extending farther backward within the same file where possible. If it cannot fill the allowance, leave the remainder unused; do not pad with answer-bearing text. This is a conservative test of cross-file content against additional in-file context. Also report a secondary **natural-context** comparison in which both arms receive the same baseline in-file prefix, with the treatment receiving additional cross-file tokens up to a prespecified cap. Label that comparison separately because total prompt length differs.

Use the same prompt wrapper, model version, decoding settings, stop condition, and output cap in both arms. Deterministic decoding (for example, greedy decoding) is preferable for a clean paired comparison if supported. If stochastic generation is required, use matched seeds where the system permits and repeat with a prespecified number of seeds; treat seed/example structure appropriately in analysis. Record the exact prompt token counts and retrieved file identifiers for auditing.

### Benchmark construction and split
Use a fixed, versioned repository corpus containing source files and a defined completion target. Construct examples at valid completion locations, such as held-out code spans or function-body continuations. For each example, the prompt exposes only the source before the target span; the target span is the reference completion. Exclude examples that cannot be evaluated consistently, such as those with ambiguous target boundaries or unavailable dependencies for the chosen functional metric.

Split by repository, not randomly by completion, where corpus size permits. This reduces leakage from near-duplicate files and repository-specific patterns across splits. If a repository-held-out test set is infeasible, use grouped splits by project/file, document the weaker generalization, and deduplicate near-identical snippets across partitions. Freeze the benchmark and its split before evaluating either arm. Use a validation partition only for selecting retrieval and token-budget settings; do not tune on test outcomes.

### Retrieval and leakage safeguards
Use a reproducible retrieval procedure restricted to files in the same repository and excluding the target file itself. A feasible simple baseline is lexical retrieval (e.g., identifier overlap with the visible target prefix), optionally followed by a deterministic ranking/tie-breaker and excerpt selection. Do not use target suffix, reference completion, future repository state, test labels, or model-generated answers for query construction or ranking. Retrieve only from the frozen repository snapshot. Exclude files that duplicate or contain the target span. Cap both the number of files and tokens per file, and preserve provenance for each selected excerpt. If retrieval requires learned embeddings, use a fixed model available in the eventual environment and ensure no test-reference information enters it; otherwise the lexical baseline avoids additional model/dependency uncertainty.

Because repositories may expose the answer elsewhere (including duplicated implementations), audit for target-span copies and near-duplicates. Apply identical repository snapshot rules to both conditions. If the use case is real-world completion, report results both with and without cases where retrieval finds near-identical answer text, if such cases can be reliably identified; define this audit before seeing performance.

### Outcomes
Prespecify one primary metric, preferably **exact match** on normalized completion text if target spans are narrowly defined. Normalization must be fixed in advance (for example, line endings and trailing whitespace only; avoid transformations that erase meaningful syntax). Report a secondary token-level metric such as edit similarity or exact match at the line level to show partial completion quality.

Where dependencies and tests are available, add a secondary functional metric: insert each completion into the masked program and run a fixed, sandboxed test suite. Report compilation/parse success and tests passed. Do not make execution-based success the sole metric unless the benchmark reliably supplies tests for all examples; missing or flaky tests would bias coverage. Report the number of examples covered by each metric and failures separately. No outcome is presumed.

### Statistical analysis
Evaluate both arms on precisely the same test examples and compute paired per-example differences. For a binary exact-match outcome, report each arm’s accuracy, the paired accuracy difference in percentage points, a confidence interval, and the counts of treatment-only wins versus control-only wins. Use a paired method such as McNemar’s test for the binary outcome, alongside the effect size and interval; do not rely on a significance test alone. For continuous token/edit or test-score outcomes, report paired differences with a repository-clustered bootstrap confidence interval (resampling repositories, then examples within selected repositories) when enough repositories exist. If only a small number of repositories are available, state that cluster-level uncertainty is unreliable and provide repository-wise results rather than implying broad generalization.

Prespecify the primary metric, retrieval method, budget, split, and comparison before test evaluation. Treat analyses across languages, repository types, context availability, and natural-budget conditions as secondary; report subgroup sample sizes and avoid unsupported conclusions from small strata. Account for multiple secondary comparisons if formal claims are made.
