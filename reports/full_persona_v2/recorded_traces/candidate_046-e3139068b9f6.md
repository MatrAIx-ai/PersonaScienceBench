## Experiment design

### Question and estimand
Estimate whether adding cross-file context to a code-completion system changes completion quality relative to using only in-file context. The primary estimand is the mean paired change in top-1 exact-match accuracy across eligible held-out completion sites, under a fixed total prompt-token budget. This tests the practical value of cross-file context when it must share finite model context capacity with the in-file context.

### Experimental conditions
Evaluate the same completion sites in two conditions:

1. **In-file only (control):** supply the target file's permitted prefix and any prespecified same-file context, excluding the missing target span and any unavailable future content.
2. **In-file plus cross-file (treatment):** preserve the same target prefix and completion target, and add snippets retrieved from other files in the same repository using a frozen retrieval policy. Under the assumed fixed context budget, shorten/drop nonessential in-file context as needed to accommodate retrieved snippets; preserve the target prefix and reserve equal space for instructions and output.

The control and treatment must otherwise use the same model checkpoint, tokenizer, prompt template, decoding settings, stopping criteria, completion site, and evaluation code. For each item, use deterministic decoding (e.g. greedy decoding) or exactly matched sampling seeds if sampling is necessary. Freeze retrieval indexes and policies before the test set is evaluated. The treatment's cross-file material must be explicitly marked and separated from the target-file prefix in the prompt.

### Data and split
Use a licensed, versioned corpus of repositories in the language(s) supported by the chosen model. Construct completion examples from real code by masking a prespecified span at valid completion points (for example, function-body or line-level positions; select one definition in advance). Include only examples for which the target is not trivially copied from the prompt and for which the pipeline can form both conditions.

Split by repository, not by completion site, into development and held-out test sets, so files from a test repository do not appear in training or tuning data. If repository-level split is impractical, use a strict temporal or project-level split and document the remaining dependence. Choose repository inclusion criteria and a minimum number of sites per repository before testing. Tune retrieval, prompt, and any thresholds only on development repositories; do not use test completion targets to adjust them.

### Cross-file context policy
Specify and freeze one retrieval method, such as lexical or embedding-based ranking over other files in the same repository. Exclude the target file from the cross-file candidate index. Retrieve only content available at the selected repository revision and obey any temporal cutoff. Deduplicate candidates and remove exact or near-duplicate target content. Record retrieved paths, ranks, and token counts for audit. Do not use external network services or repository files outside the evaluated snapshot. These restrictions are intended to prevent direct target leakage while allowing genuine dependencies such as related definitions, imports, or API usage to be retrieved.

### Controls and validity checks
- Use identical completion sites and target references in both arms; compare paired outputs.
- Fix model, prompt instructions, temperature/decoding, stop rules, tokenizer, and output-length cap.
- Use the same total context-token budget in both arms, with a prespecified allocation rule; keep the target prefix intact and account for any truncation in reporting.
- Freeze retrieval and preprocessing before test evaluation, and ensure no test-target text is indexed or used for tuning.
- Run a prompt-construction audit on a sample (or all examples when feasible) to verify the target span is masked, no future target text is exposed, and retrieved passages are from allowed files/revisions.
- Report the fraction of examples with no retrievable cross-file context and do not silently omit them; include them in the intention-to-treat primary comparison, where treatment then has no added retrieved content.
- Treat repositories as clusters in uncertainty estimates; many sites from one repository are not independent evidence.

### Outcomes
**Primary metric:** top-1 exact match of the generated completion against the held-out reference, using a precisely defined normalization policy (prefer exact source text after only line-ending normalization; do not normalize away meaningful syntax). Report the absolute percentage-point difference, treatment minus control.

**Secondary metrics:** token-level edit similarity (e.g. normalized edit distance or exact-match-at-k if multiple candidates are produced), compilation or parsing success when a reliable language-specific harness is available, and repository-level macro-averaged exact match. For compilability, use a fixed harness and report coverage; compilation does not establish semantic correctness. Optionally report pass@k only if multiple samples are generated under matched sampling and this is declared in advance. Avoid treating secondary metrics as substitutes for the primary endpoint.

### Statistical analysis
For each test site, compute the paired outcome difference (treatment correctness minus control correctness). Report each arm's overall accuracy, the paired absolute difference, and a 95% confidence interval. Because sites are nested within repositories, obtain uncertainty with a repository-cluster bootstrap (resample repositories, retaining all their sites) or an equivalent cluster-robust method. Report the number of repositories and sites, and the distribution of per-repository effects. State the analysis and confidence-interval procedure in advance. If a formal significance test is desired, use a paired test that accounts for repository clustering; do not use an unclustered site-level test as the sole inferential result. Do not stop early based on interim results. Consider a predeclared minimum practically meaningful effect and interpret intervals relative to it, not just a p-value.

### Feasibility
This design requires a code corpus, a completion pipeline/model, and optionally a local retrieval index, none of which are supplied in the inspected workspace. It is feasible in principle with a local model and repository snapshots; execution cost depends on corpus size, model availability, and context length. A small pilot on development repositories can validate masking, token accounting, retrieval, and evaluation code, but its examples must not be included in the final held-out test. Network access and a GPU are not assumed; a CPU-only model or a smaller test set may be used if needed, with limitations reported. The present task is design-only: no experiment has been run and no outcome is claimed.
