## Proposed experiment design (not executed)

### Research question and estimand
Estimate whether making cross-file code context available improves code-completion performance, relative to an otherwise identical in-file-only system. The treatment is context source, not a different model or training recipe. The principal comparison is paired: the same model receives the same completion prompt except for the context block supplied under the two conditions.

### Benchmark and sample
**Proposed choice, not source-confirmed:** Use a public, versioned code-completion benchmark with repository-level source snapshots, such as a carefully filtered subset of permissively licensed repositories from a public code corpus. Include at least one language initially, and report the chosen language and repository-selection rules. If a standard benchmark can provide repository provenance, use it; otherwise construct a held-out repository benchmark from a frozen corpus.

Sample completion sites from valid source files at syntactically meaningful positions, preferably function-body or statement boundaries. Exclude generated/vendor files, files below a minimum size, and examples whose target is not reproducible from the frozen snapshot. For each site, preserve the actual continuation as reference and truncate the input precisely at the completion point. Use a pre-registered, fixed number of examples per repository where possible so a few large projects do not dominate.

Split by repository, not by completion example: assign whole repositories to development/calibration and held-out test partitions before constructing examples. If multiple snapshots/forks or near-duplicate repositories exist, group them before splitting. Deduplicate files and examples using normalized hashes and near-duplicate checks. Keep test references, future file contents, and any benchmark answers inaccessible to retrieval and prompt construction. Freeze repository revisions, preprocessing, example IDs, and split manifests. Any tuning of retrieval parameters or prompts occurs only on development repositories; evaluate the selected protocol once on held-out repositories.

### Conditions and context construction
For every held-out completion site construct two prompts:

1. **In-file-only baseline:** target-file context around the completion site, excluding the hidden continuation.
2. **Cross-file treatment:** the same target-file context plus selected context from other files in the same repository snapshot.

Use a deterministic retrieval procedure that does not inspect the hidden target continuation. A workable proposed procedure is to extract identifiers/imports from the visible prefix and retrieve candidate repository files or snippets using lexical/identifier overlap, with deterministic tie-breaking. Exclude the target file, test/reference files if they expose the answer, generated/vendor files, and any content from later revisions. Keep retrieval corpus and indexing limited to the frozen repository snapshot. Record retrieved paths and scores for audit. A simple lexical retriever is easier to reproduce than an unspecified learned retriever; if learned retrieval is desired, it must be frozen and must not be trained or tuned on test references.

**Budget matching:** Fix one total prompt-token budget per example, including instructions and completion prefix, and use the same tokenizer. Reserve the same number of tokens for the target file in both conditions. In the treatment, use the remaining context allowance for retrieved cross-file snippets; in the baseline, fill that same allowance with additional eligible in-file surrounding context, where available. Thus total input token count and target-prefix exposure are matched while context source differs. If the target file cannot fill its allowance, apply a predeclared padding/unused-budget rule identically or compare only examples where both conditions can meet the common budget. Report actual token counts and truncation rates. Do not allow context overlap with the hidden continuation; strip any repeated target text or answer-containing snippets.

A secondary, clearly labeled practical comparison may contrast cross-file augmentation with the baseline at the same total context budget but without forced in-file fill, reflecting a realistic pipeline policy. Keep it secondary because it confounds context source with amount of useful context unless token budgets are carefully matched.

### Model and inference controls
Use one fixed, documented code-completion model/checkpoint and tokenizer for both arms. No fine-tuning between arms. Freeze system/user prompt wording, completion stop criteria, maximum generated tokens, decoding settings (prefer deterministic greedy decoding for the primary analysis), software/library versions, and hardware/runtime where available. Randomize or interleave condition order per example to avoid order or service drift; if inference is nondeterministic, use paired seeds and repeat each condition under the same predeclared seeds. Ensure each model call sees only its assigned context and has no hidden access to the repository. Cache inputs/outputs with condition labels and log failures, timeouts, truncation, and token usage. Do not tune the model or prompt on held-out outcomes.

### Outcomes
**Primary outcome:** exact match of the generated continuation to the reference after a predeclared normalization that only removes irrelevant formatting differences (for example, line-ending normalization; do not normalize away identifier or semantic differences). Report exact-match rate per completion site.

**Secondary outcomes:** token-level or character-level edit similarity (e.g., normalized edit distance), pass@1 where generation is sampled and repeats are explicitly defined, syntax/parse success for supported languages, and optionally execution or unit-test pass rate only where reliable tests exist and can be run safely. Report invalid/failed generations and latency/token cost as operational outcomes. Avoid treating any one metric as a complete measure of semantic correctness; exact matching may penalize equivalent code and repository test coverage may be incomplete.

### Analysis plan
The primary estimand is the paired per-example difference in exact-match outcome (cross-file minus in-file-only) over the held-out set. Report each arm’s rate, absolute percentage-point difference, relative change as a supplementary quantity, and a confidence interval. Use paired inference, such as a paired bootstrap resampling repositories (with examples nested within sampled repositories) to account for project clustering; alternatively report a repository-clustered regression/standard error. Do not treat all completion sites as independent. Specify the interval method and resampling count before evaluation. A paired test such as McNemar’s test may be supplementary, but repository clustering should remain addressed.

For edit similarity and other continuous/paired outcomes, report paired differences with repository-clustered bootstrap confidence intervals. For pass@1 or sampled decoding, preserve pairing by example and seed. Report the number of repositories, examples, and usable pairs, along with exclusions and missing/failure handling. Present effect sizes and uncertainty, not just significance tests.

### Dependency-based slices and checks
Before looking at test outcomes, define a dependency-present slice using static evidence from the visible prefix and frozen repository: for example, identifiers imported or referenced in the target file that have definitions in another file. Define a no-obvious-cross-file-dependency slice using the same reproducible rules. These are imperfect proxies; manually inspect a small, blinded sample or validate the classifier on development data, not by changing rules after seeing test performance. Report each slice’s size and paired effect, and an interaction between condition and dependency slice as exploratory unless the slice and analysis are preregistered. Additional descriptive slices may include language, repository size, target location, and retrieval hit quality, with multiplicity and small subgroup sizes clearly noted.

Feasibility and pipeline checks before the held-out evaluation: verify context assembly on hand-checked examples, confirm that the continuation and later-version content never enter either prompt or retrieval index, validate tokenizer counts and equalized budgets, ensure deterministic prompt serialization and retrieval ordering, and run a small development-only smoke test for model-call and metric code. These are protocol validation checks, not evidence of performance.
