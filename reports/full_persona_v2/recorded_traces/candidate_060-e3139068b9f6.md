## Complete experiment design (proposed, not executed)

### Supported facts versus proposed choices

**Supported by the available materials:** The task asks whether cross-file context improves code completion over in-file-only context. It is design-only and explicitly says not to claim an experiment was run. The workspace contains `task.json`, which refers to `track.md`; that file is not present, so it provides no evidence. The supplied environment describes bubblewrap, disabled network, `/workspace`, Python 3/system Python with project dependencies not preinstalled, no supplied datasets, no GPU, and CPU affinity count 24. The task metadata also says repositories and compute are not required for this design task.

**Not established by the materials:** No repository corpus, benchmark, language, model/pipeline, retrieval method, context/window limit, inference parameters, metric, statistical threshold, or execution budget is specified. All choices below are a practical proposed protocol and must be selected/confirmed before any actual experiment.

### Question and estimand

Compare completion quality for the same held-out code locations using the same completion system and generation settings, where the sole intended intervention is whether relevant context from other files in the same repository is made available. The estimand is the average paired performance difference per completion target: cross-file condition minus in-file-only condition. This isolates the value of cross-file context under the chosen model, corpus, context policy, and task; it does not establish that every model or repository benefits.

### Benchmark and targets (proposed selection procedure)

1. Select a repository-level benchmark or construct one from a fixed, documented set of repositories. Since no dataset is supplied, this is a required design choice, not an existing resource. Prefer repositories with source history or stable snapshots, clear licenses/usage permissions, and enough code to identify held-out targets and related files. Fix repository names, revisions/commit hashes, languages, inclusion/exclusion rules, and sampling seed before evaluation.
2. Define completion targets from code in the fixed snapshot. A practical target unit is a function/method body or a short contiguous span whose preceding source forms the prompt and whose original withheld span is the reference. Exclude generated/vendor files, malformed examples, trivial empty spans, and targets whose withheld reference is unavailable. Define length and syntax-validity filters before condition runs; avoid choosing targets based on model performance.
3. Keep each target's repository snapshot fixed. Use a repository-level train/validation/test split if any model, retrieval policy, prompt template, or hyperparameter is tuned. If using a pre-existing frozen model with no tuning, reserve a held-out test set of repositories or commit snapshots where feasible. Prevent overlap between tuning and test targets, and check for duplicate/near-duplicate target code across splits. Do not use the hidden target text, later revisions, or files generated from the target during retrieval.
4. Sample a manageable target set using a declared seed and stratify, if feasible, by repository and language. Set sample size through a prospective power/precision calculation based on a pilot or justified expected paired effect and variance; the brief supplies no sample-size or runtime budget. If no defensible effect estimate is available, label the selected size exploratory and report precision rather than implying adequate power.

### Conditions and context construction

For every target, create one frozen prompt prefix from the same target file with the completion span removed. Use identical instructions, formatting, truncation rules, decoding parameters, model checkpoint/version, toolchain, and random-seed policy in both arms. If stochastic decoding is used, use matched seeds where supported and consider repeated generations under a predeclared budget; otherwise use deterministic decoding.

- **In-file-only baseline:** provide the local target-file context permitted by the selected completion setup (normally surrounding preceding code and any explicitly allowed local surrounding lines). Do not provide content from other files. Define exactly whether later lines in the same file are included; a causal completion setup should generally use only source available before the target to avoid future-code leakage.
- **Cross-file treatment:** retain the exact baseline context and add a bounded amount of relevant context drawn only from other files in that same fixed repository snapshot. Use a prespecified, deterministic selection policy (for example references/imports/callers or symbol definitions connected to identifiers in the target); record the policy and ranking/tie-breaking. Exclude the target file, the withheld target span, duplicated prompt material, and any file/version that contains the answer by direct copying. Freeze retrieval/index construction and ensure it uses no test reference text. Record which files and snippets were selected for each example.

To avoid giving the treatment an advantage merely from a larger input budget, use a fixed total context-token budget in both arms. In the treatment, cross-file tokens should replace an equal number of lower-priority in-file tokens if necessary; document truncation and preserve the target-local prefix required by the task. As a complementary analysis, one may report an additional “add context on top” condition, but it is not the primary causal contrast because total context length differs. The main comparison therefore tests cross-file context composition under a matched budget. If the intended intervention is specifically adding context without replacement, define that as a separate secondary contrast.

### Outcomes

Preselect one primary metric and freeze its exact implementation before examining test results. Recommended primary outcome: **exact match of the generated completion span after only a prespecified, semantics-neutral normalization** (for example line-ending normalization; do not remove meaningful whitespace or alter code semantics). Exact match is interpretable but strict. For a less brittle completion measure, report **token-level edit similarity** or normalized edit distance as a secondary outcome. Also report, as secondary diagnostics, parse/syntax validity where a reliable parser exists, and compile/test success only if there is a valid, non-leaking harness and this can be run consistently. Report completion length and invalid/empty output rates. Do not treat BLEU-like similarity alone as proof of functional correctness. If executable tests are used, the tests must be fixed before inference and must not reveal held-out reference implementations to retrieval or prompting.

Report metrics at the target level and aggregate overall and by repository/language/target category, with subgroup results identified as exploratory unless adequately powered. Human judgments can be supplementary only with blinded condition labels, a written rubric, and independent raters; they are not required for the primary design.

### Statistical analysis and uncertainty

The primary comparison is paired: each target is evaluated in both arms. For exact match, report the two condition rates, paired percentage-point difference, a confidence interval, and the discordant-pair counts (treatment-only wins and baseline-only wins). Use a paired binary method such as McNemar's test for a null test, and preferably a confidence interval for the paired difference. For continuous token similarity, compute per-target paired differences and report the mean (and optionally median) difference with a confidence interval using a paired bootstrap clustered by repository, or a suitable mixed-effects model with repository clustering. Resampling targets independently can understate uncertainty when targets within a repository are correlated; therefore cluster resampling by repository is preferred. State the number of repositories and targets, missing/failed generations, and all exclusions. Predeclare the primary metric and contrast; label all additional metrics and subgroup comparisons secondary, and adjust or clearly qualify multiple exploratory tests. Interpret effect size and interval, not only a p-value.

### Controls and validity checks

- **Same-example control:** run both arms on identical frozen targets and verify prompt identity except for the intended cross-file context difference.
- **Leakage audits:** automatically assert target span and target file are absent from retrieval candidates; scan retrieved snippets for exact/near copies of the withheld completion; ensure all files come from the frozen snapshot and only allowed pre-target information is exposed. Audit a sample manually.
- **Retrieval audit:** log retrieved paths, snippets, scores/ranks, token counts, and truncation. Confirm treatment contexts contain other-file material and baseline contexts do not. Include a no-useful-context or shuffled/unrelated cross-file placebo as a diagnostic if feasible, clearly secondary; it checks whether any apparent benefit is simply extra tokens or prompt perturbation.
- **Budget/prompt control:** enforce and verify matched token budgets for the primary contrast; identical system prompt, local context policy, tokenizer, generation limits and decoding settings. Record model and software versions and provider/API settings if applicable.
- **Order/randomness:** randomize or interleave condition execution to avoid time/order effects. Use deterministic decoding or matched random seeds and report repeated-run policy.
- **Benchmark integrity:** freeze split and target list before scoring, deduplicate across splits, and keep the test reference inaccessible to retrieval and prompt-generation code. Avoid tuning based on test outcomes.
- **Failure handling:** predefine handling of timeouts, malformed outputs, rate limits, and parser/test failures. Apply the same policy to both arms and report counts; do not silently drop difficult treatment or baseline examples.
- **Robustness:** optionally compare context selection variants or token budgets in separately predeclared secondary analyses. Do not combine their results into the primary claim.

### Reproducibility and feasibility

Before any run, publish or archive the protocol, target-generation and split scripts, sampling seed, repository revisions, prompt templates, retrieval policy, model/checkpoint and tokenizer versions, decoding configuration, metric code, and environment/package versions. Store per-target condition prompts or reproducible references to the exact context, outputs, retrieval logs, and scoring records subject to repository licenses and privacy/security constraints. Report deviations and dependency failures. The described environment has no provided corpus or dependencies and networking is disabled, so the proposed design is a paper protocol rather than an immediately executable run; any real run needs an approved corpus and model already accessible in the environment or an authorized change to that setup. No GPU is available, but CPU affinity is reported as 24; without model and dataset details it is not possible to estimate whether CPU inference is practical. The task itself says compute is not required for this design task.
