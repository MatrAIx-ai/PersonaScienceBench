## Proposed experiment design

**Question.** On realistic repository-level code-completion tasks, does providing relevant code from other files improve completion quality relative to providing only the target file, when the model, target, and total prompt budget are held constant?

### Benchmark, task, and data split

As a proposed benchmark, use a fixed, publicly available collection of permissively licensed repositories in one language, pinned to immutable commit hashes. Construct completion examples from source files by selecting eligible positions (for example, function-body spans) and masking a contiguous suffix or body span; ask the model to generate that exact held-out span. Include only examples whose target file has meaningful references to other repository files, and record dependency/relevance metadata. This makes cross-file context potentially useful while preserving a realistic completion format.

Split by repository, not by completion instance: use training/development repositories only for tuning retrieval and prompt formatting, and reserve disjoint repositories for final testing. If the chosen model is pretrained and cannot be retrained, the split still governs prompt/retrieval development and leakage control; report that repository contents might have appeared in pretraining as a limitation. Deduplicate repositories and near-identical files across splits. The particular corpus, language, eligibility criteria, and sample size are proposed choices, not specified by the supplied materials; finalize them based on licensing and feasible evaluation scale before testing.

### Paired conditions and context construction

For each held-out completion site, create two prompts with identical system/task instructions and target-file prefix:

1. **In-file-only baseline:** target-file prefix and, where appropriate, the visible target-file suffix after the masked span; no other repository file contents.
2. **Cross-file treatment:** the same target-file material plus retrieved snippets from other files in that repository, selected using a fixed, answer-independent procedure (e.g. static imports/references and symbol-name matches). Exclude the target file itself from retrieved material.

Use the same deterministic retrieval rules for all treatment examples, document ranking and truncation, and retain retrieval provenance. Do not use gold completion text, tests that expose the answer, or post-mask target-file content to choose external context. Prevent direct answer leakage by excluding generated/build/vendor artifacts and exact/near-duplicate target spans; scan retrieved snippets for the gold target and report any excluded or contaminated cases. Keep all repository files at the pinned pre-evaluation commit, and define whether future target-file content is available identically in both arms; the recommended primary setup is to hide the masked span and any later content in both arms, eliminating a potentially answer-revealing suffix.

**Fair budget control:** fix a total input-token budget per example, including instructions, target-file text, and retrieved context, and use the same tokenizer. In both arms preserve the same target prefix and instructions; cross-file snippets replace an equal number of otherwise available non-target context tokens rather than increasing the total. Since the baseline has no other-file context, fill unused budget with no extra information (do not pad with content); instead, define a common cap and ensure each arm receives the same target material while treatment has external tokens only when there is room. For a stricter causal comparison, use a matched-budget primary analysis on examples where both arms can be filled to the same token count using non-answer-bearing in-file context in the baseline, clearly labeling that added within-file material; also report the natural baseline versus treatment at equal maximum context windows. A complementary ablation can compare cross-file snippets against an equal-token amount of additional in-file context. These analyses separate cross-file information value from simply giving the model more input tokens.

### Model and decoding controls

Use one code-capable model with a fixed, recorded version/checkpoint and tokenizer for both arms. This is a proposed choice; no model is specified or installed by the materials. Hold constant prompt template, system instructions, maximum input/output tokens, stop rules, precision, and inference backend. Use deterministic decoding (temperature 0 / greedy where supported) for the primary comparison; if stochastic sampling is intrinsic or pass@k is desired, use identical pre-registered sampling settings and replicate seeds per example in both arms. Randomize/blind condition labels during scoring where feasible. Do not adjust model settings between conditions. Tune retrieval and prompt construction only on development repositories, then freeze them before testing.

### Outcomes

**Primary outcome:** exact match of the generated completion to the held-out span after a pre-specified normalization limited to whitespace/formatting (do not normalize identifiers or semantics). Report the paired absolute difference in exact-match rate, treatment minus baseline, over eligible test sites.

**Secondary outcomes:** token-level edit similarity/normalized edit distance; compile or syntax-parse success when the language/toolchain is available; unit-test or hidden-test pass rate only where such tests are reliable and do not leak the answer; and an adjudicated functional-equivalence metric if test infrastructure supports it. Report context retrieval coverage/relevance and input-token counts to interpret effects, not as success outcomes. Analyze target lengths and examples with/without detected cross-file dependencies as pre-specified subgroups, treating subgroup findings as secondary.

### Statistical analysis

Use paired comparisons at the same completion sites. Estimate the absolute metric difference and relative change, with 95% confidence intervals. For binary exact match, use a paired proportion method such as McNemar’s test and a repository-cluster bootstrap confidence interval (resample repositories, retaining all paired examples within each sampled repository). For continuous similarity scores, use repository-cluster bootstrap intervals and a paired test or hierarchical model. Treat repository as the sampling/cluster unit to avoid overstating precision from many sites within a few projects. Pre-register one primary metric and significance threshold; report effect size and interval regardless of significance. If several secondary outcomes/subgroups are examined, label them exploratory or adjust for multiplicity. Set a minimum practically meaningful effect in advance if a go/no-go decision is required; no threshold is established by the supplied task.

### Validity and implementation checks

Before final evaluation, manually inspect a small development-only sample of retrieved snippets and masked prompts to verify that context is relevant, the target is truly hidden, and conditions differ only as intended. Automated checks should confirm: identical target sites and target prefixes; no gold answer in either prompt; no cross-split duplicates; no target-file leakage through retrieval; matched tokenizer accounting and model settings; and deterministic reproducibility. Report exclusions, retrieval failures, prompt truncation, and missing language/toolchain checks by condition. Include ablations comparing (a) cross-file context to no additional context and (b) cross-file context to equal-token additional in-file context; the latter is especially important for attributing gains to cross-file information rather than extra context quantity. Consider a shuffled/unrelated-file context negative control to test whether any gain comes merely from extra code-like text.

### Feasibility and reporting

The supplied environment has system Python, no preinstalled project dependencies, no datasets, no GPU, and 24 CPUs; the repository itself provides no model, benchmark, code, or empirical setup. Thus this is a design, not evidence of execution. A CPU-only open model may be feasible only at modest scale and with quantization/runtime dependencies, but availability and performance are unknown. Before committing to scale, identify an accessible model/runtime and benchmark licensing, estimate tokens and inference throughput on a small non-evaluation pilot, and reduce the number of test sites or use a hosted/institutional model only if permitted.
