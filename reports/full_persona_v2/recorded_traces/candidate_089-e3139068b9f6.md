## Proposed design-only protocol

### Fixed task-supported facts
- The question is whether cross-file context improves code-completion performance over in-file-only context.
- This is a design-only task; repositories and compute are not required, and no experiment should be reported as run.
- Available project materials do not specify a benchmark, model, language, completion pipeline, retrieval method, or metric. The referenced `track.md` is absent.

Everything below is a proposed protocol choice, not a sourced project fact.

### 1. Benchmark and sampling plan
Use a public, version-pinned corpus of repositories in the language(s) supported by the chosen completion model. Prefer repositories with stable file paths, commits, and enough multiple-file projects to support cross-file retrieval. Exclude vendored dependencies, generated files, binaries, lockfiles, and files that are unavailable to the model at inference time.

Construct completion examples from eligible source files by selecting function/method bodies or other syntactically meaningful spans. For each example, choose a position within the span and provide the preceding target-file text as the in-file context; the held-out continuation is the reference. Sample a fixed number of examples per repository (or cap large repositories) so that large projects do not dominate. Record repository, commit, language, file, span, and prompt identifiers. Set the sample size before scoring, based on available resources and a desired minimum detectable paired effect if an execution study is later approved. If there is no justified power calculation, choose a feasible fixed sample and label estimates exploratory.

Split by repository, not by completion example: retrieval source repositories and any tuning data must not include test repositories. If the study seeks within-project retrieval specifically, use test repositories only for inference-time retrieval while ensuring that the target continuation and any duplicate copies are excluded; report this distinction explicitly. A stronger generalization claim should use held-out repositories and avoid training/test overlap to the extent the model’s training data can be audited.

### 2. Conditions and cross-file context
For every completion point, create a paired input under two conditions:

- **In-file-only control:** target-file prefix, with no content from other files.
- **Cross-file treatment:** the identical target-file prefix plus snippets retrieved from other eligible files in the same repository and commit.

Proposed retrieval definition: index eligible files at the pinned commit, excluding the target file. Retrieve snippets using a fixed, predeclared strategy—e.g., lexical symbol/reference matching to names in the target prefix and completion site, with deterministic tie-breaking; alternatively a fixed embedding retriever if dependencies and model access are available. Select top-ranked snippets, deduplicate, preserve their source-file identifiers, and truncate to the context limit. Freeze retrieval and ranking parameters before test scoring. Do not use the held-out continuation or gold reference in the query, ranking, filtering, or snippet selection. Include only repository content that would plausibly be available at completion time.

To isolate the *source* of context from the *amount* of context, set a shared total prompt-token budget. Reserve an identical allowance for the target-file prefix in both arms. In the treatment, allocate a predeclared portion of the remaining allowance to other-file snippets; in the control, fill that same allowance using additional preceding target-file context where available (or use a separate fixed-budget comparison with padding/unused tokens, clearly reported). The cleanest primary comparison is equal total tokens with the treatment swapping some target-file context for cross-file context. Also report a secondary naturalistic comparison where the baseline uses as much in-file context as fits and the treatment adds cross-file context under the same total model limit, since this answers a practical pipeline question but changes context composition and potentially quantity. Document tokenization and truncation exactly.

### 3. Fairness and generation controls
Use the same frozen model checkpoint/version, system and user prompt template, completion prefix, stop rules, decoding parameters, maximum output length, and tokenization in both conditions. Run each example in paired fashion; randomize or alternate condition order if inference has nondeterminism or shared-resource effects. Prefer deterministic decoding for the primary comparison (e.g., greedy/temperature zero where supported); if sampling is required, use matched seeds and report that stochastic variability remains. Do not fine-tune on test examples. Any retrieval tuning or prompt development must use separate development repositories and be completed before test evaluation.

### 4. Leakage and integrity safeguards
- Keep target continuation and reference text out of retrieval queries, candidate context, prompt construction, and any post-hoc reranking.
- Exclude the target file itself from cross-file retrieval; remove exact and near-duplicate snippets and generated/vendor copies across files where feasible.
- Split tuning and test data at repository level; pin commits and preserve a manifest of files and exclusions.
- Audit retrieved snippets on a sample of examples for target/reference leakage and record retrieval source paths.
- Avoid selecting examples whose continuation is already repeated verbatim in another indexed file; either exclude them by a predeclared duplicate rule or report a sensitivity analysis with them removed.
- Keep metric selection, sample construction, and analysis plan fixed before looking at test-condition outcomes.

### 5. Outcomes
Primary outcome: per-example exact match of the generated continuation against the reference after a predeclared, conservative normalization (e.g., line-ending normalization only; no transformations that erase meaningful code differences). Report the exact-match rate in each arm and paired difference in percentage points.

Secondary outcomes, if implementable without subjective post-selection:
- Syntax/parse validity of the generated completion in its insertion context, using the language parser/compiler version fixed in advance.
- Functional correctness via repository tests only if tests are available and can be run safely and consistently; describe whether these tests actually cover the modified region. Do not treat absence of a test failure as proof of correctness.
- Edit similarity (e.g., normalized edit distance or token-level match) as a diagnostic, not as the sole quality measure.
- Retrieval coverage and token accounting: fraction of examples with retrieved context, number of snippets/files, and context-token distribution.

A human preference or usefulness assessment could be added only with a blinded, randomized annotation protocol and explicit rater instructions; it is not required for the core design.

### 6. Paired analysis and uncertainty
For each test completion, compute the outcome in both arms and the paired difference. For binary exact match, report the paired mean difference and a confidence interval, with a paired test such as McNemar’s test for discordant outcomes. Because examples within a repository are correlated, use a repository-cluster bootstrap for the primary uncertainty interval (resampling repositories, retaining all sampled examples within each repository); also provide repository-level summaries. If feasible, report a mixed-effects logistic model with condition as the fixed effect and repository as a random intercept as a sensitivity analysis. For continuous similarity, use paired differences and repository-cluster bootstrap intervals. Predefine the primary outcome and test to avoid metric fishing; treat secondary outcomes as secondary and account for multiplicity or label them exploratory. Report effect sizes and intervals, not just p-values.

The supplied setup says repositories and compute are not required for the design task, has no dataset specified, and does not establish access to a model or benchmark.
