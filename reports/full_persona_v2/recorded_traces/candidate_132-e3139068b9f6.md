## Experiment design

**Question.** Does adding cross-file context improve code completion relative to using only context from the target file?

### Design and treatment contrast
Use a paired, within-target comparison. For every held-out completion example, construct two prompts to the **same fixed model**:

- **Control (in-file only):** the unchanged target file context up to the completion point, with the target represented by a sentinel or removed span.
- **Treatment (cross-file added):** the identical target-file context plus retrieved context from other files in the same repository snapshot.

Keep completion target, model/version, system instructions, decoding parameters, stopping rules, and maximum **effective input-token budget** fixed. Define the budget before evaluation. Reserve identical capacity for the target-file context in both arms and allocate the same remaining context slots in the control and treatment. In the control, fill cross-file-reserved slots with a neutral, non-informative placeholder or leave them unused while ensuring the model-visible input budget is controlled; preferably use a fixed, explicitly masked placeholder so that the contrast is added cross-file information, not a longer prompt. Document both actual token count and allocated capacity. If the model’s tokenizer and prompt format make exact matching impossible, predefine a narrow tolerance and report it. Never truncate target-file context differently between arms.

### Dataset, task, and split
Proposed instantiation: select a public repository-based code-completion benchmark, or construct examples from versioned repositories. Use a single predeclared completion granularity (for example, next-line or a contiguous masked span) and a declared language set. Each example must have a repository snapshot, target file, completion location, and reference continuation. Include only examples for which the target location and repository state can be reconstructed.

Split at the **repository/project level**, not randomly by completion: all examples and files from a project belong to only one of train/validation/test. Use validation projects for prompt/retrieval tuning and freeze choices before test evaluation. If the selected benchmark has prescribed splits, verify that projects do not overlap; disclose any overlap and deduplicate near-identical repositories or snapshots where feasible. The test set should contain no material used to tune retrieval, prompts, or thresholds. No dataset is present in the supplied workspace, so benchmark selection and availability are assumptions to be resolved before implementation.

### Leakage-safe cross-file retrieval
For each example, retrieve only from other files in the **same repository snapshot at the completion time**. Exclude the target file entirely from the retrieval corpus (including duplicate or renamed copies when detectable), generated outputs, tests or commits that encode the answer, and any files or revisions unavailable at that snapshot. Do not retrieve from other test examples’ targets or from later repository history. Build the retrieval index separately per repository snapshot and split. Use a fixed, predeclared retrieval method (e.g. symbol/import/reference matching, with deterministic lexical ranking as fallback), fixed top-k and truncation rules, and no test-label feedback. Log source paths, revisions, ranks, and included token counts for audit. If no eligible cross-file context exists, keep that example and provide no retrieved material in treatment; report this subgroup separately.

### Outcomes
**Primary metric:** exact match of the generated continuation to the reference, using a fixed normalization policy declared in advance (ideally report both strict exact match and any normalization such as whitespace handling). Compare paired outcomes across the same targets.

**Secondary metrics:** execution- or test-based correctness where a safe, reproducible harness exists; syntax/parse success; edit similarity such as token-level exact match or normalized edit distance; and pass@1 only if the generation protocol and number of samples are fixed. Also report results by language, completion type, availability of eligible cross-file context, and retrieval relevance where these groups are defined before test inspection. Execution-based measures must be clearly distinguished from reference agreement and used only with sandboxed, timeout-limited tests.

### Statistical analysis and reporting
For each target, compute the treatment-minus-control difference for the primary outcome. Report both arms’ scores, absolute percentage-point change, and relative change (where meaningful). Quantify uncertainty using a paired bootstrap clustered by project (resample projects, retaining their examples and paired predictions), with a predeclared confidence level, such as 95%. Because project counts—not just example counts—govern independent information, report the number of projects and examples and avoid treating examples within one project as independent. For a binary primary metric, optionally provide a paired test such as McNemar’s test as a complementary check; cluster-aware inference remains central. Report subgroup estimates as exploratory unless powered and predeclared, and avoid a binary claim of improvement based only on a point estimate: state effect size and interval. Predeclare a practically meaningful effect threshold if a decision rule is needed.

### Controls and ablations
- Verify the two arms have identical target-file content and target spans, and audit prompt/token counts.
- Keep retrieval index, ranking, and target-example order independent of model outputs; freeze all settings before test.
- Include a **shuffled or irrelevant-context control** (same cross-file token volume, sampled from unrelated eligible files) to test whether any gain comes from useful cross-file information rather than merely more code/tokens. Treat this as an ablation, not the main comparison.
- Optionally compare retrieval strategies or remove imports/symbol matches as predeclared ablations; do not use these to select a test-set winner without a separate validation set.
- Report the no-eligible-context subgroup; its treatment should reduce to the control aside from any explicitly defined placeholder behavior.
