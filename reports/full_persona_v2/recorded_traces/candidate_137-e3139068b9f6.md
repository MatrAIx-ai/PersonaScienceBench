## Proposed experiment design

### Research question and estimand
Test whether **relevant cross-file repository context** improves code completion relative to in-file-only context. The primary estimand is the average paired change in completion quality on held-out completion sites when cross-file context replaces an equal number of prompt tokens otherwise allocated to earlier in-file context. This answers whether cross-file context is useful under a fixed model-input budget, rather than whether simply making prompts longer helps.

### Task and data
**Proposed assumption (not specified by the brief):** use repository-grounded, left-to-right next-span completion in Python as a reproducible initial task. At each eligible site, provide a prefix ending at a statement or expression boundary and request the next fixed-size span (for example, up to 32 tokenizer tokens, ending at the first complete syntactic unit at or before that cap). Hide that span and all later code in the target file from the model. Exclude sites with empty targets or targets that cannot be consistently extracted. Preserve line endings and define normalization rules before scoring.

Use a public, permissively licensed collection of Python repositories at fixed commits, with repository IDs, commit hashes, licenses, and file hashes recorded. Select a feasible number of repositories and sites by a predeclared rule; sample sites across repositories, rather than allowing large repositories to dominate. Split by repository into development and test sets; tune retrieval and prompt choices only on development projects, and evaluate once on test projects. If evaluation across unseen projects is not the intended application, a separate within-project, time-separated split may be reported as a distinct secondary setting, not mixed with the primary result. Freeze snapshots before prompt generation and disclose dataset filters and exclusions.

### Model and conditions
**Proposed assumption:** select one completion model that can be run reproducibly within available resources, fix its exact checkpoint/version and tokenizer, and use deterministic decoding (temperature 0; fixed maximum output length and stop rules). The task brief names no model and supplies no model weights or data, so model choice and availability must be confirmed before execution. No experiment is proposed as already run.

For every same test site, query the same model with identical task instruction, language/file metadata, target definition, decoding settings, and input-token ceiling:

1. **In-file baseline (A):** target-file prefix before the completion site, using only preceding code. Do not include the hidden target or suffix.
2. **Cross-file condition (B):** retain the most recent in-file context and add relevant code from other files in the same repository snapshot. Retrieve with a fixed, predeclared method (for example, lexical symbol/import matching, with deterministic ranking and tie-breaking); exclude the target file. Use no labels or target text in retrieval queries or ranking features. Freeze retrieval parameters on development projects.
3. **More-context control (C):** fill the extra token allowance with additional earlier in-file context, rather than cross-file code. This distinguishes a gain from cross-file information from a gain caused merely by adding tokens. It is an information-source comparison and need not have identical recency distribution; describe that limitation.
4. **Optional relevance control (D):** replace retrieved files with same-repository, non-retrieved files matched approximately for length. If feasible, this tests whether any repository code helps versus retrieved relevant context; it is secondary because irrelevant context may actively distract.

### Context construction and fair budget
Set a common prompt-token ceiling based on the chosen model and reserve the same fixed number of tokens for task instructions and generated output in every condition. Measure tokens with the model tokenizer. Apply a deterministic context packing procedure and disclose order, truncation, separators, metadata, and ranking. Keep the prompt envelope constant; all unused allowance should be handled consistently.

There is an unavoidable trade-off: a fixed total input budget means adding cross-file tokens can displace earlier in-file tokens. Therefore, compare both of these pre-specified views:

- **Primary, fixed-total-budget substitution:** B uses a fixed allocation for cross-file material and trims the oldest in-file prefix tokens to fit; A uses the same total context allowance entirely for in-file prefix. This tests whether cross-file material is a better use of limited context. C uses the same allocation as B but devotes those tokens to still-earlier in-file prefix, isolating source from context quantity while keeping total tokens equal.
- **Secondary, additive-context analysis:** keep the in-file context identical to A and append cross-file context up to a declared extra allowance, subject to the model's maximum context. Compare against A and C, while clearly noting that this changes total prompt length and cost. This estimates benefit when more context budget is available, not source quality at a fixed budget.

Record actual total and per-source prompt tokens, truncation, and retrieval yield for each site. If no stable token cap can be afforded, use a predeclared cap derived from model limits and a pilot on development data; do not select it from test outcomes.
