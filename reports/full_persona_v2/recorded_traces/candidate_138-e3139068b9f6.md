## Experiment design

### Question and estimand
Test whether adding cross-file context improves code-completion quality relative to an in-file-only condition. The primary estimand is the average paired difference in completion quality at the same held-out prediction sites under the two context conditions, with all other pipeline settings held fixed. This estimates the effect of the specified cross-file context policy—not a universal effect of every possible retrieval method.

### What is fixed versus recommended
**Fixed task constraints:** This is a design-only task; do not claim an experiment ran. The workspace contains no supported model, corpus, pipeline, retrieval method, or metric, so none is treated as an existing project fact.

**Recommended replaceable operational choices:** Select a model that can be run identically in both arms, a repository-completion benchmark/corpus with licensed and accessible code, a deterministic cross-file selection policy, and a primary metric before evaluation. Record versions/configuration. The protocol below works with any such choices, but effects will be specific to them. A practical primary metric is exact match of the generated completion after a fixed generation procedure; report normalized edit similarity and pass@1/unit tests if the benchmark supports executable tests. For generative completions where exact match is overly strict, predeclare a single alternative primary metric such as token-level edit similarity or test pass rate rather than choosing after seeing results.

### Benchmark and evaluation units
1. Define the unit as a completion site in a repository file: expose a prefix ending at a prespecified cursor location and score the model's completion against the hidden continuation or task tests.
2. Build a held-out set of repositories not used to tune retrieval, prompts, or model settings. If repository-level holdout is impossible, split temporally or by project and explicitly acknowledge weaker generalization. Sample sites by a prespecified rule (e.g., eligible function/body boundaries or benchmark-provided sites), and record repository, file, language, site, and stratum.
3. Exclude sites without enough visible in-file prefix or with ambiguous references/ground truth under predeclared criteria. Determine all exclusions before model outputs are viewed. Do not use the held-out target continuation in either context or retrieval indexing.
4. Deduplicate near-identical repositories/files and benchmark examples across train/dev/test where possible; avoid same-project leakage by grouping splits at repository level. Ensure retrieval corpora contain only permitted, non-held-out content. For within-repository retrieval, the held-out file's visible prefix may be available as the target-file context, but its hidden suffix must be masked from indexing and snippet extraction.

### Conditions
- **A: In-file only.** Supply the target file's allowed prefix/context under a fixed token allocation. No other file or metadata derived from other files is supplied.
- **B: Cross-file augmented.** Supply the same allowed target-file context and augment it with snippets from other files in the same repository, selected by a deterministic, predeclared policy. A viable general default is rank candidate files/snippets by a fixed relevance rule (e.g., direct imports/references first, then lexical or embedding retrieval) with stable tie-breaking. The exact method is a replaceable choice and must be frozen using development data only.

Keep system/developer instructions, cursor marker, output constraints, model/checkpoint, decoding parameters, random seeds where applicable, and evaluation procedure identical. Run both arms at every same site; randomize arm order if online state, caching, or nondeterminism could create order effects. Disable persistent conversational memory and cross-example state.

### Context and token-budget controls
Predeclare the model's tokenizer and total input limit. Use the same total prompt-token budget in both arms. Reserve identical space for instructions and generation; impose a common context budget on the remaining input. In A, fill that budget only with the target file, using a fixed truncation policy (for example, nearest preceding code first, with necessary enclosing scope); in B, preserve the same target-file allocation and replace a predeclared portion with cross-file snippets, or use a fixed allocation such as 75% target-file / 25% cross-file. Choose and freeze the allocation on development data. This prevents B from appearing better merely because it received more tokens, while making the tradeoff explicit. Record actual tokens, truncation, retrieved files/snippets, and retrieval latency. Do not silently exceed context limits. A supplementary unconstrained-budget arm may assess practical deployment value, but it is not the primary causal comparison.

Retrieval must exclude the target file's hidden continuation and any files or generated artifacts containing it. Cache/index construction must be split-safe. Include a retrieval ablation or negative control if feasible: e.g., B with same-sized irrelevant snippets, to distinguish useful cross-file information from token-distribution or added-context effects. Another useful control is a no-extra-context condition if the in-file baseline itself has variable truncation.

### Outcomes
- **Primary:** One prespecified site-level completion score, recommended exact match (binary), with normalization rules frozen in advance (e.g., whitespace policy); alternatively choose an outcome appropriate to the benchmark before test evaluation. Higher is better.
- **Secondary:** token-level exact match or edit similarity; compile/test success or pass@1 where applicable; syntax validity; completion length; retrieval coverage and utilization diagnostics; inference/retrieval latency and token/cost usage. Treat these as secondary and adjust or clearly label exploratory comparisons. Report performance by language, repository size, and whether a site has a direct cross-file dependency as prespecified subgroup analyses, not as replacements for the overall result.

### Execution and analysis
Run inference on identical sites in both arms with fixed decoding (greedy decoding is a simple reproducible default; if sampling is required, use matched seeds and repeat seeds). Save prompts or reproducible prompt manifests, model and tokenizer versions, retrieved snippets and file identifiers, outputs, scores, and errors. Blind scoring to condition where feasible, especially for human judgments. Freeze benchmark, retrieval policy, prompts, budgets, exclusions, metrics, and analysis before opening test results.

Compute the paired site-level difference B−A. For a binary primary metric, report each arm's success proportion, absolute percentage-point difference, relative change as descriptive, and paired discordance counts (A-only successes and B-only successes). Estimate uncertainty using a paired bootstrap clustered by repository (resample repositories, retaining their sites and both conditions), with a prespecified 95% confidence interval; alternatively use a paired test that respects repository clustering. Do not treat sites within a repository as independent. Report the number of repositories/sites, excluded cases and reasons, and interval estimates, not only p-values. For continuous scores, use the same clustered paired bootstrap for mean difference. If multiple primary metrics or many subgroup tests are desired, predeclare multiplicity handling or label analyses exploratory. A practical decision should consider both the interval and a prespecified minimum meaningful improvement, not significance alone.
