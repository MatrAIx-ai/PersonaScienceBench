## Diseño experimental propuesto

**Pregunta:** ¿Mejora la completación de código al añadir contexto de otros archivos, frente a limitarse al contexto del archivo objetivo?

### 1. Diseño y comparación
Usar un experimento pareado: cada punto de completación se evalúa en ambos brazos con el mismo modelo y revisión del repositorio.

- **Brazo A, in-file:** solo contenido anterior al punto objetivo dentro del archivo objetivo.
- **Brazo B, cross-file:** el mismo contexto in-file más contenido recuperado de otros archivos del mismo proyecto.

Congelar modelo/versión, plantilla y orden del prompt, parámetros de generación, reglas de truncamiento y cualquier otra configuración compartida. Aleatorizar el orden de las llamadas o intercalar brazos para reducir efectos temporales/caché. Si el servicio o modelo es no determinista, fijar la semilla cuando sea posible y, si no, hacer repeticiones por punto con idéntica política en ambos brazos; definir antes si el resultado por punto será una única generación o el promedio de varias. No se dispone de configuración real del pipeline, por lo que estas son propuestas, no descripciones de un sistema existente.

### 2. Formación de los puntos de evaluación y prevención de fuga
Como propuesta, muestrear proyectos de un conjunto versionado y definir puntos objetivo a partir de archivos fuente. Para cada punto, usar como entrada el prefijo del archivo hasta una posición de corte; la continuación real después del corte es la referencia. Excluir puntos ambiguos o no evaluables mediante reglas predefinidas, por ejemplo archivos generados/binarios, continuaciones vacías y ejemplos donde la referencia no pueda separarse limpiamente.

Evitar contaminación por respuesta de estas maneras:

1. Construir índice/contexto únicamente desde una instantánea del proyecto anterior o igual al estado de evaluación, nunca desde soluciones, tests o cambios posteriores que revelen el objetivo.
2. Retirar del índice todo el archivo objetivo, no solo el sufijo, para impedir recuperar duplicados de la respuesta desde otra región del mismo archivo. El brazo A usa el prefijo permitido del archivo objetivo por separado.
3. Excluir de la recuperación el sufijo de referencia y cualquier artefacto que contenga la respuesta exacta o una copia obvia; la limpieza debe ser determinista y aplicarse sin consultar resultados del modelo. Registrar exclusiones y sus motivos.
4. Deduplicar repositorios/forks y buscar duplicados de ejemplos entre particiones; separar entrenamiento/desarrollo/prueba por proyecto si el modelo o el recuperador se ajustan con datos propios. No seleccionar parámetros usando el conjunto de prueba.
5. Congelar instantáneas, cortes y referencias antes de generar predicciones. Mantener las referencias ocultas al proceso de construcción de prompts y a quienes ajustan el recuperador.

Conviene preespecificar una unidad de muestreo manejable: cantidad objetivo de proyectos y puntos por proyecto, con estratos por lenguaje u otro atributo disponible. Como no se entregaron datos, no se puede fijar un tamaño responsable sin un piloto de factibilidad ni estimación de variabilidad; cualquier piloto debe ser separado del test final y no utilizarse para reportar el efecto confirmatorio.

### 3. Selección cross-file y presupuesto de contexto
Propuesta reproducible: para cada objetivo, recuperar solo archivos distintos del archivo objetivo, limitados al mismo proyecto e instantánea. Excluir archivos no fuente o generados mediante reglas documentadas. Usar una estrategia fija, por ejemplo búsqueda léxica sobre símbolos/imports del prefijo y puntuación BM25, con desempate determinista por ruta; alternativamente se puede usar un recuperador ya existente si el investigador aporta configuración fuente. Registrar archivos y fragmentos elegidos, puntuaciones y versión del índice.

**Control del presupuesto:** fijar un presupuesto total idéntico de tokens de entrada para ambos brazos (incluyendo instrucciones y delimitadores). En ambos, reservar primero los mismos tokens para metadatos/instrucciones y asignar el resto al contexto de código. En A, llenar el cupo con el prefijo in-file; en B, mantener el mismo prefijo in-file —truncado de forma idéntica si hace falta— y usar únicamente el cupo residual para fragmentos externos. Limitar asimismo la salida generada con idéntico máximo. Esto compara el valor incremental de contexto externo bajo capacidad fija; no confundirlo con una comparación donde B recibe más tokens totales. Documentar límites de ventana y tokenizer reales cuando se elijan modelo y servicio; no están disponibles en los materiales actuales.

Como análisis secundario (no reemplaza la comparación primaria), se podría evaluar una condición de presupuesto ampliado para distinguir beneficio de información externa de beneficio debido simplemente a más tokens. No mezclar ese contraste con el primario.

### 4. Resultados y análisis
**Métrica primaria propuesta:** exactitud de continuación a nivel de ejemplo (exact match de la continuación normalizada según reglas fijadas antes de evaluar). Esta métrica es simple y reproducible, aunque estricta y limitada.

**Secundarias:** similitud basada en tokens o edición, y, si el entorno permite pruebas seguras y dependencias adecuadas, compilación/tests para métricas funcionales. No tratar ejemplos de un mismo proyecto como observaciones independientes. Si hay estratos (p. ej., lenguaje), presentar resultados por estrato de forma secundaria y evitar inferencias excesivas en grupos pequeños. Ajustar por multiplicidad o etiquetar claramente los análisis secundarios como exploratorios.
