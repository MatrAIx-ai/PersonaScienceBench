## Proposed experiment design (design only)

### Fixed by the brief versus proposed choices

**Fixed by the supplied brief:** The question is whether adding cross-file context to code completion improves performance over using only in-file context. This is a design-only task; repositories and compute are not required, and no experiment should be represented as having run. The supplied environment metadata says `/workspace`, Python 3/system Python, no preinstalled project dependencies, no datasets, no GPU, disabled network, bubblewrap, and CPU affinity count 24. Repository inspection found only `task.json`; its referenced `track.md` was absent. There are no source-supported implementation, dataset, model, metric, language, or evaluation-split specifications.

**Recommended choices below (not source-supported facts):** Use a repository-level held-out completion benchmark, a fixed pretrained code model and deterministic inference settings, a retrieval-based cross-file condition, and exact-match plus edit-based metrics. If a particular project pipeline is later supplied, substitute its supported choices while preserving the controlled comparison.

### Conditions

1. **In-file-only baseline:** At each completion target, provide the same file prefix (and any trailing suffix, if the chosen task is infilling) that would normally be available at prediction time. Exclude other files from the prompt.
2. **Cross-file-context treatment:** Use the identical target-file context, plus retrieved context from other files in the same repository. Retrieval must be automatic and use only information available before prediction; exclude the target file and generated/reference continuation. A simple prespecified retrieval method is lexical similarity over file chunks, with deterministic ranking and no manual query-specific curation.

Keep model checkpoint, decoding, system prompt/template, completion location, target text, and all inference settings identical. Prefer deterministic decoding (e.g., greedy) to reduce variance. The causal contrast is the change in completion quality attributable to allowing other-file context under this operational retrieval policy. It does not, by itself, establish that all forms of cross-file context or all models benefit.

### Dataset and split strategy (proposed)

Select a public, licensed corpus of software repositories in the target language(s), with enough repositories and eligible completion points to support repository-level comparison. Freeze dataset/version and preprocessing before evaluation. Split by repository, not by files or completion points: training/tuning repositories, if needed for retrieval or prompt tuning, must be disjoint from held-out test repositories. Ideally use a temporally defined test snapshot or repository-held-out split to reduce near-duplicate contamination. Deduplicate exact or near-identical repositories/files across partitions, and exclude generated/vendor/dependency code and files with inadequate context.

Create completion examples at valid source locations by hiding a fixed continuation (for example, a statement or a short bounded token span) while retaining only the prefix available at that location. Define eligibility and target construction before scoring; sample locations without selecting based on either condition's performance. Keep test examples paired: every selected location is evaluated in both conditions. Report repository and language coverage and the final counts after exclusions. No particular dataset is mandated by the available brief; dataset choice must be finalized as a documented proposal before collection/evaluation.

### Context selection and budget controls

Chunk candidate files using a fixed, language-aware or line-based rule, and retrieve with a prespecified lexical ranking method (for example, BM25 using the target-file prefix as query). Index only files in the same repository and only permissible snapshot contents. Exclude the target file, test continuation, and any chunk overlapping the target location. Apply stable tie-breaking and record retrieved paths, chunk spans, and scores for audit.

Set one common maximum model-input token budget, including prompt and target-file context, for both conditions. Reserve the same generation allowance and fixed prompt overhead. In the treatment, cross-file chunks may use only the remaining context capacity; truncate using the same rule. To avoid the treatment winning merely by increasing total input length, either (recommended primary comparison) reduce/truncate in-file context as needed so total input tokens are matched to the baseline, or define an identical total budget and document that the treatment reallocates some available context from the file prefix. Report actual input lengths and perform a sensitivity analysis at matched input length. The chosen implementation should preserve the same target-file prefix whenever possible; if budget pressure forces its truncation, apply a prespecified rule and disclose it. Include a retrieval-empty fallback that is identical to baseline.

### Outcomes and metrics

**Primary outcome:** exact match of the generated completion to the held-out reference at the defined target span, after only a minimal, prespecified normalization (such as newline/whitespace handling that does not alter identifiers or semantics). Exact match is interpretable but strict.

**Secondary outcomes:** normalized edit similarity (e.g., normalized edit distance), token-level exact-match or edit score, and optionally compilation/typecheck or unit-test success when the corpus has reliable harnesses. Treat execution-based correctness as secondary because coverage and harness availability may be selective. Also report retrieval coverage (fraction of examples with eligible retrieved material), context tokens and retrieval latency as diagnostic/operational measures, not as substitutes for completion quality. Do not choose metrics after examining treatment results.

### Statistical analysis

Use paired per-example comparisons because the same target is evaluated in both conditions. For the primary binary exact-match outcome, report each condition's accuracy, the paired percentage-point difference, and a confidence interval obtained with a repository-cluster bootstrap (resample repositories, retaining examples and paired predictions within each sampled repository). A paired test such as McNemar's test can be reported as a complementary example-level test, but repository clustering should govern primary uncertainty because examples within a repository are correlated. For continuous edit scores, report paired differences and repository-cluster bootstrap intervals. Predeclare the primary metric, direction, confidence level, any minimum practically meaningful effect, and handling of multiple secondary outcomes. Present per-language and repository-stratified summaries as descriptive or prespecified subgroup analyses; avoid interpreting underpowered subgroup differences as definitive.

### Leakage and validity checks

- Verify the held-out target continuation is absent from both prompts and retrieval index; prohibit retrieval from the target file and target span.
- Ensure retrieval indexes contain only the same allowed repository snapshot and no future/test-reference data. If training/fine-tuning is involved, keep test repositories out of training and tuning.
- Detect exact and near duplicates across repositories/splits and remove or flag them; exclude vendored/generated files that can duplicate public source.
- Audit sampled prompts and retrieval results, including retrieval-empty cases, truncation, token counts, and path provenance.
- Confirm conditions differ only in cross-file context availability and its explicitly controlled token allocation; use identical model, decoding, target, and evaluation code.
- Run a baseline-equivalence check: treatment with no eligible retrieval should produce the same prompt/output as baseline. Check reproducibility via frozen data manifests, code/config, model identifier, and deterministic decoding.
- Analyze effects by retrieval coverage and input-length strata as diagnostics, without replacing the primary paired analysis. Report latency separately, since retrieval can add cost even if quality improves.
