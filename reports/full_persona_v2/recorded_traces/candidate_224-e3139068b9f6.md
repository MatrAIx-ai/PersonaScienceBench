## Proposed experiment design

**Status and scope.** This is a design, not a report of an executed experiment. The supplied materials establish only the research question and that repositories and compute are not required for this design-only task. They do not specify an available corpus, model, dependencies, or infrastructure. Accordingly, every concrete protocol choice below is proposed and would require validation before execution.

### Research question and estimand

Estimate the effect on code-completion quality of adding information from other files in the same project to an otherwise identical in-file prompt. The primary comparison is paired: each eligible held-out completion site is evaluated in two conditions, with the same model, target, in-file prompt, and inference settings; only the additional cross-file context differs. This isolates the incremental value of the supplied cross-file context under the selected retrieval policy. It does not by itself establish the effect of every possible cross-file retrieval system or model.

### Corpus, benchmark, and split (proposed)

Use a **project-level, repository-backed corpus** with source files and stable project identities. A public benchmark such as a repository-level completion benchmark may be suitable, but choose it only after verifying that its release includes or permits access to the relevant source snapshots, completion targets, project boundaries, licenses, and split metadata. The supplied workspace does not establish that any named benchmark or data are present or available.

Prefer a pre-existing project-disjoint train/validation/test split. If the selected benchmark lacks one, construct a split by repository/project, never by randomly distributing snippets from the same repository across splits. Freeze commit/snapshot identifiers and split manifests; deduplicate identical or near-identical files across projects/splits where feasible. Use validation data only for selecting prompts, retrieval parameters, or model settings; reserve the test projects and targets for final evaluation. If the model may have seen public repositories during pretraining, report this as a limitation; repository-level split prevents benchmark split contamination but cannot establish pretraining non-exposure.

A feasible initial scope is a single language and a fixed set of repositories, since language-specific parsing and symbol resolution make retrieval more reliable. Choose the language based on benchmark coverage and available parser/tooling, not on an assumption that any specific language is available. Define minimum eligibility rules before scoring: target is in a source file; both conditions can be formed within a fixed context budget; and enough preceding in-file context is present. Report counts and exclusions by reason.

### Completion task and target construction

Use next-span completion at a held-out location in a source file. For each eligible file, select target spans deterministically (for example, fixed seeded sampling over valid locations, with a maximum number per file) to avoid over-weighting large repositories. The target is the exact contiguous ground-truth code span after the cursor, with a predeclared token or line length cap. Exclude targets that are empty, only whitespace, or exceed the cap; establish these rules before test evaluation. The prompt contains source text preceding the target and, if a completion API requires it, a clearly marked cursor. The model must generate the missing span; do not include target suffix text in the prompt. If evaluating multiple sites per file, use the unmodified ground-truth snapshot for all prompt construction so one model completion or hidden target cannot influence another.

### Model and inference assumptions (proposed)

Choose one code-capable base model with documented version/checkpoint and an inference interface that can be used consistently for both arms. No model is identified in the materials. A practical protocol should choose a model that fits the actual available execution environment and record exact model revision, tokenizer, runtime/library versions, and quantization if any. Do not claim that the stated workspace has a model or the capacity to run one. If only an API model is selected, record endpoint/model version and ensure identical settings; API changes or nondeterminism are additional limitations.

Use the same prompt wrapper, tokenization, maximum total input length, maximum new tokens, stopping rules, and decoding in both arms. For a principal deterministic comparison, use greedy decoding (temperature 0 where supported), one completion per condition and target, and a fixed output-token cap. If stochastic decoding is the intended deployment setting, instead pre-register a seed schedule and evaluate the same number of samples in each arm, treating target as the pairing unit and specifying pass@k separately. Ensure cross-file additions do not silently displace in-file content: allocate a fixed context budget and use a predeclared truncation rule that preserves the same most-recent in-file region in both arms, with the additional context occupying only the reserved cross-file portion. Report actual token counts and truncation rates.

### Conditions and context construction

For every site construct two prompts:

- **A — in-file only:** the source file content before the cursor, subject to the common in-file budget and prompt format. Include no other files, repository summaries, retrieved code, or project metadata beyond what the task interface inherently exposes.
- **B — in-file plus cross-file:** exactly the same in-file content and formatting as A, plus a bounded set of snippets from other files in the same frozen project snapshot.

Proposed retrieval policy: use a deterministic, non-oracle lexical/symbol retrieval method over eligible project files. Index other files from the same project snapshot; exclude the target file itself. Rank candidate snippets using query terms available before the cursor (identifiers/imported symbols and surrounding code), with a fixed scoring/ranking implementation and deterministic tie-break. Prefer snippets defining or using referenced symbols (e.g., imported symbols or identifiers in the in-file prefix), and return a fixed maximum number of snippets under a predeclared token budget. Do not use the hidden target, future suffix, benchmark labels, tests that disclose expected output, or manually selected “helpful” files as retrieval inputs. Record retrieved paths, spans, rank scores, and token counts for audit. If parser-based symbol resolution is selected instead, freeze parser versions and define fallback behavior for parse failures in advance. The retrieval policy is a consequential choice: lexical/symbol retrieval is feasible and reproducible, but does not represent all cross-file-context methods; results should be described as evaluating this policy.

Mark inserted material with clear file-path and context delimiters and distinguish it from the target file. Use the same delimiters consistently. Ensure snippets are drawn from files other than the target, do not contain copied target spans, and are truncated at the same fixed boundary policy. The base context remains identical between A and B; context budget accounting should be explicit. Because adding cross-file context consumes finite model context, fix the total input-token ceiling in both arms. Reserve a fixed number of tokens for cross-file snippets in B, and leave that budget unused in A rather than reallocating it to more in-file text; otherwise the comparison confounds cross-file information with additional in-file information. Also report a secondary “natural budget” analysis only if useful, clearly distinguished from the controlled primary comparison.

### Leakage and integrity controls

1. **Temporal/file leakage:** construct prefixes only from bytes/tokens before the cursor. Never expose the target or post-cursor suffix to the model or retriever. Build retrieval indices from the frozen project snapshot, but filter out the target file and any target-bearing duplicate. Audit snippets for exact/near copies of the held-out target.
2. **Split leakage:** split by project; keep all files, targets, retrieval indices, and tuning for a project within its assigned split. Test projects cannot influence prompt/retrieval tuning. Keep a manifest of project IDs, revisions, file hashes, and split assignments.
3. **Oracle leakage:** retrieval queries and ranking features may use only the visible prefix and ordinary project files; do not use target-derived identifiers, expected outputs, test outcomes, or manual annotations unavailable at inference time.
4. **Pretraining contamination:** cannot generally be ruled out for public code models. Record model release/training disclosure when available; prefer post-cutoff or otherwise contamination-resistant snapshots if feasible, and disclose residual uncertainty rather than claiming contamination-free results.
5. **Implementation parity:** test that both arms receive identical prefix bytes, target, model and decoding configuration, and that only B has retrieved snippets. Log serialized prompts or hashes under appropriate data/licensing controls. Run prompt-construction unit checks on synthetic examples with known target boundaries and retrieval exclusions.

### Outcomes and analysis

**Primary outcome (proposed):** exact match of generated completion against the held-out target after a predeclared, minimal normalization policy. Prefer raw exact match as the main headline measure; if normalization is used, define it before evaluation (e.g., line-ending normalization only) and report raw results as well. Exact match is interpretable but strict and sensitive to valid alternative completions.

**Secondary outcomes:** token-level exact match / edit similarity (such as normalized edit distance), BLEU or another code-overlap metric only as a supplementary measure, and syntactic parse/compilation validity where language tooling can be run consistently. If the benchmark has executable tests that genuinely validate the completion in context, report test pass rate and pass@k; do not invent tests or equate compilation with functional correctness. Report completion length and empty/early-stop rates to identify degenerate outputs. Consider a blinded human review on a small, pre-sampled subset only if practical and with a fixed rubric; it is not required for a feasible primary study.

For each target, calculate the paired difference between B and A for the primary metric. Report both condition-level scores, absolute paired effect (percentage-point difference for exact match), and relative change only where meaningful. Use a paired bootstrap clustered by repository/project (resample projects, retaining their sites) to form confidence intervals, since sites within a project are correlated. A paired permutation/sign-flip test on project-level or site-level aggregated differences may be a secondary inferential check; predeclare which is primary. Report number of projects and sites, per-project effects, and variability, not only a pooled score. Avoid treating many targets in one repository as independent observations. If comparing several metrics or subgroups, label secondary/exploratory analyses and control or acknowledge multiplicity. Predeclare useful strata (e.g., whether a referenced symbol was retrieved, target length, project) and interpret them as diagnostic unless adequately powered.
