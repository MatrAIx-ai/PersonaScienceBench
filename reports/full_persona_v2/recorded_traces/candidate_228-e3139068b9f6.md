## Proposed experiment: cross-file context for code completion

### Research question and estimand
For a fixed pretrained code-completion model, does adding relevant context from other files in the same repository improve completion quality over giving the model only the target file’s preceding in-file context?

Estimate the average within-example difference in exact-match performance between the two context conditions on held-out repository examples. The treatment is availability of retrieved cross-file text; all other pipeline components are held fixed.

### Benchmark and task
- **Proposed benchmark:** a pinned release/version of **CrossCodeEval**, using its repository-level Python examples and official train/validation/test partitions if available for that release. - **Task:** fill the benchmark’s designated missing code span from the preceding target-file context; score the generated span against the reference. Use only Python to keep parsing and prompt handling consistent.
- Use the official test split as the evaluation set; validation may be used only for selecting prompt-length limits or other fixed configuration choices. Do not tune on test results. If the chosen release lacks suitable official partitions or the target-span format, document that before proceeding and select a pinned, repository-level benchmark with a clearly defined held-out test split rather than constructing an undocumented split.
- Report the number of examples and repositories after fixed, predeclared filters, and retain example and repository identifiers for paired analysis.

### Model and prompt conditions

The benchmark’s completion format must be compatible; use the same model in both arms. If this model cannot be obtained or run within the stated resources, select and pin a smaller completion-capable model before examining test outcomes. This model choice is not source-supported.
- **In-file-only control:** prompt contains the task’s in-file prefix and a fixed completion marker, with no text from other files. Preserve the target span and prompt template exactly as required by the model’s completion format.

Use a fixed, documented delimiter and label each snippet with its repository-relative path.
- Keep system/instruction text, target-file prefix, tokenizer, truncation policy, maximum input length, and output budget identical across arms. Allocate the same total token budget to each prompt. To avoid giving the cross-file arm a simple prompt-length advantage, reserve a fixed cross-file token allowance in both arms: the treatment fills it with retrieved snippets; the control leaves that allowance empty (or uses a predeclared neutral padding policy that does not contain code or hints). Use the empty allowance as the primary control and report actual prompt-token counts. Do not truncate the shared in-file prefix differently between conditions.

### Cross-file context selection
Use a simple, reproducible, non-learned retrieval baseline to isolate context availability:
1. For each example, index only eligible non-target files from the same repository. Exclude generated/vendor files and files designated as test targets where benchmark metadata permits; apply the same documented repository filters to both arms.

Query terms may use only information available before the completion point (prefix tokens, imports, and identifiers); do not use the missing reference span or post-target text.
3. Select the highest-ranked files, break ties deterministically by path, and take text around matching query terms, with a fixed maximum snippet and total token budget. Exclude duplicate or near-duplicate snippets and target-file content. Define all thresholds, token limits, and tokenizer before evaluation.
4. Build the index separately per repository from permitted repository files. The benchmark test target and reference may be used only to define the evaluation item, never as retrieval query text or indexed content. If benchmark versioning makes the reference span present in a repository snapshot, explicitly mask/remove it before indexing.

This retrieval method is a proposed baseline, not a claim that it is optimal. A later study could compare retrieval strategies, but the primary experiment should avoid that extra factor.
