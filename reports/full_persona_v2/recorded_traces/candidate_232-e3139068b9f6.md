## Proposed experiment design (not executed)

### 1. Question and estimand
Estimate whether access to cross-file source context changes code-completion quality relative to access to in-file context alone, for one fixed model and benchmark. The primary contrast is paired: every completion target is evaluated under both context conditions, with all non-context model and inference settings held constant. This estimates the effect of the *context condition in the proposed pipeline*, not a universal effect for all models, repositories, or retrieval systems.

### 2. Proposed benchmark and task/target
No benchmark, model, or task specification is prescribed by the supplied materials. For a concrete, source-neutral proposal, use a fixed, publicly available, version-pinned repository-level benchmark that provides repositories and held-out completion spans. If selecting a benchmark, require repository identities, language, license, stable revisions, and enough examples for paired comparison to be documented before evaluation; avoid training/test overlap where records permit checking.

Task proposal: single-turn infill completion at naturally occurring function-body spans. For each example, give the model the source file with a contiguous target span replaced by a sentinel; target is the exact original span. Select spans by a predeclared rule (e.g., complete statement or short contiguous block, with valid surrounding syntax), and exclude targets that cannot be aligned or reproduced reliably. This gives an objectively recoverable reference while representing completion. Freeze the target-selection rule and benchmark split before model runs. Report language, repository, target-length distribution, and exclusions. If the intended use case is instead next-token continuation, that should be a separate design rather than silently mixing task types.

Model proposal: choose one code-capable model with fixed checkpoint/version and inference implementation, and report it explicitly. Prefer a locally runnable checkpoint compatible with the available CPU-only environment, or use a documented external inference service only if its access, version stability, and budget are actually available. Do not imply a particular model is already installed or selected.

### 3. Paired conditions and context construction
For each target, prepare the same base prompt containing the identical target file with the same sentinel, instructions, and formatting.

- **In-file-only control:** provide only the target file's permitted surrounding content (excluding the target span). No other repository files are supplied.
- **Cross-file condition:** provide exactly the same in-file context plus a fixed number/token budget of relevant snippets retrieved from other files in that same repository/revision. Exclude the target file itself, generated copies of it, and files that leak the target/reference text. Use a deterministic retrieval method and record retrieved paths, snippets, ranking/scores if used, and all retrieval parameters.

The key contrast is availability of cross-file snippets, not a prompt-size advantage. Set an identical total context-token budget in both arms. In the cross-file arm, if snippets consume budget, remove an equal amount of low-priority in-file context using a prespecified truncation policy; in the control, spend the budget on in-file context. Also report a secondary *additive-context* comparison if desired, where cross-file material is added without removing in-file text, but label it as a combined context-plus-length effect, not the isolated source effect. Keep the prompt template and token counting method identical; prevent truncation from removing the target marker or required target-file framing.

Use the same deterministic retrieval result for a given example on reruns. Retrieval must use repository content available at the pinned revision and must not use target labels, benchmark metadata, or future/test annotations. Define a fallback for no eligible cross-file retrieval (e.g., cross-file condition receives no snippets, and flag such examples); report retrieval coverage. The relevance method is a consequential proposal: a simple lexical/symbol-based retriever is transparent and feasible, while learned retrieval introduces another model and potential data-leakage concerns.

### 4. Generation and controls

Prefer deterministic decoding (greedy or temperature zero where supported) for a clean primary comparison; if sampling is the intended deployment setting, use matched seeds per example and condition and report that choice. Randomize or interleave condition order to avoid time/order effects. Store raw prompts and outputs.

Control contamination by pinning repository revisions and checking retrieved text against target spans. Keep benchmark selection, target filtering, retrieval configuration, and analysis plan fixed before looking at comparative outcomes. Do not tune retrieval or prompts on the test set. If development/tuning is needed, use a separate development split.
