## Proposed experiment design

**Question.** Does adding cross-file context improve code-completion performance over using only in-file context?

**Status of setup.** The available project material is only `task.json`. It identifies the design question and says this is design-only, with repositories and compute not required. It documents no model, code corpus, completion pipeline, runtime budget, retrieval system, metric, or implementation details. The protocol below is therefore a proposed, adaptable design—not a description of an existing setup. No experiment has been run.

### Design and conditions

Use a **paired, within-example ablation**: run the same frozen completion system on each held-out completion location under both conditions.

1. **In-file baseline:** provide the target file's permitted prefix (and any standard task metadata) but no other source files.
2. **Cross-file treatment:** provide exactly the same in-file material, plus retrieved context from other files in the same eligible project/repository.

Fix the model/version, system instructions, completion marker, decoding parameters, stopping rule, and evaluation targets across conditions. If a production pipeline necessarily changes prompt assembly or retrieval behavior, document that difference; otherwise, the only intended intervention is adding the retrieved cross-file content. Use deterministic decoding where available, or use matched random seeds and repeat both conditions identically if generation is stochastic.

### Fair context and token-budget policy

Pre-register one maximum total input-token budget, including instructions, in-file context, cross-file context, and the completion prefix. Reserve the same space for the target prefix and fixed prompt components in both conditions. In the treatment, cross-file material may occupy only the remaining reserved context allowance; do not silently truncate the target prefix or increase the model's total input budget. If there is insufficient room, include no cross-file material for that example. Use the same tokenizer and truncation rules in both arms. This estimates the effect of adding cross-file information **within a fixed model context window**, not the effect of increasing total prompt length. Report the rate and token count of retrieved context and examples where retrieval could not fit. As a sensitivity analysis, if useful and feasible, report a separately labelled variable-total-budget comparison; do not conflate it with the primary fixed-budget result.

### Reproducible retrieval policy

Predefine and record the retrieval procedure before evaluation. A feasible default is: index eligible non-target files from the same repository snapshot; exclude the target file and any evaluation answer material; rank candidates using a fixed lexical relevance method (for example, BM25 over file chunks, with deterministic tie-breaking by path and chunk offset); take the highest-ranked chunks that fit the treatment's cross-file allowance. Fix chunk size/overlap, candidate filters, query construction, maximum chunks, and ordering in the protocol. A query may use the target file's prefix, but must not use the hidden continuation or reference completion. Log repository revision, candidate paths, scores/ranks, selected chunk boundaries, and token counts so retrieval can be reproduced. If this lexical default is unsuitable for the chosen pipeline, substitute a specified retriever and freeze its version, index inputs, parameters, and tie-breaking before test evaluation.

### Evaluation examples and leakage safeguards

Select completion locations from a held-out set that is not used to tune retrieval, prompts, hyperparameters, or stopping rules. Split by repository or another documented project-level partition where data volume permits, rather than randomly splitting adjacent snippets; if only one repository is available, split by file and disclose the reduced generalizability. For every example, expose only the prefix available at the completion point and score against its withheld continuation. Build the retrieval index only from files permitted to be available at that point. Exclude the target continuation, duplicate or near-duplicate copies of evaluation answers, generated artifacts, and any post-cutoff material if temporal availability matters. Check for duplicate/overlapping examples across partitions and inspect retrieval logs for accidental target/answer exposure. Freeze all design choices using development data, then run the held-out comparison once under the predefined protocol.

### Outcomes and analysis

**Primary metric:** exact match of the generated completion to the reference continuation, with normalization rules (if any) fixed in advance. Exact match is interpretable but strict, so it should not be the sole descriptive measure.

**Secondary metrics:** token-level edit similarity (e.g. normalized edit distance or exact-match rate at a fixed prefix of the reference), and optionally compilation/unit-test success if the task corpus and execution harness support safe, consistent tests. Report completion length and invalid/empty-output rates as diagnostic outcomes. Define handling of formatting and stop tokens before evaluation; do not select whichever metric favors a condition after seeing results.

For each example, retain the paired outcomes. Report both condition-level metrics, the paired difference (treatment minus baseline), and its uncertainty. For binary exact match, estimate the paired proportion difference and a 95% confidence interval using a paired procedure such as a cluster bootstrap over repositories (or files if repository-level clusters are unavailable); McNemar's test can be reported as a supplementary test of discordant pairs. For a continuous similarity metric, compute per-example paired differences and use a cluster bootstrap confidence interval. Choose the resampling cluster consistent with the split, and report the number of examples and clusters. If there are too few clusters for reliable cluster-level inference, state that limitation and show the paired example-level results descriptively rather than overstating precision. If the model is stochastic, incorporate repeat runs as a prespecified repeated-measures factor and resample at the example/cluster level while preserving pairing. Treat the primary metric as confirmatory; label other measures secondary and account for multiple testing if making inferential claims across them.

### Controls, feasibility, and decision criteria

Controls include the same held-out examples and reference answers, model/checkpoint, decoding, in-file prefix, fixed prompt content, total input-token ceiling, and evaluation code in both arms. Verify mechanically that the baseline contains no external-file text, the treatment's added text comes only from allowed files, both arms respect the same input limit, and all paired examples receive outputs or a prespecified failure code. Freeze retrieval and scoring code/configuration, retain run logs, and use a small development subset to check that prompts fit and metrics behave as specified; keep this subset out of the final evaluation.

This protocol is feasible with a local code corpus and an available completion system and does not require a GPU by definition; actual cost and runtime cannot be estimated from the supplied materials. If compute is limited, reduce the number of held-out examples or use deterministic inference while preserving the paired design and report the resulting precision limitations. The conclusion should be based on the estimated paired effect and interval, not on an isolated score difference: improvement is supported when the prespecified primary measure favors cross-file context with uncertainty narrow enough to exclude practically negligible effects. Define a practically meaningful effect threshold before evaluation if a deployment decision is intended.
