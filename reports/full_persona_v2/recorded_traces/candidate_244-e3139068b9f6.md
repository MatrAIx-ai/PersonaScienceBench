## Experiment design

### Question and estimand
Estimate whether adding useful cross-file context improves code-completion quality when prompt context capacity is held fixed. The primary estimand is the paired difference in completion performance between a cross-file-context condition and an in-file-only condition, over the same held-out completion targets and with the same total context-token budget.

### Benchmark and split
Use a fixed, versioned benchmark of repositories containing source files and project structure. Define completion targets in advance (for example, masked spans at function, expression, or line boundaries) and retain the exact prefix available to the model at each target. Exclude targets that cannot be evaluated consistently or whose answer/context is unavailable under the chosen benchmark protocol. Split by repository where the benchmark permits, or otherwise by project/version, so test targets and their potentially retrieved files do not leak through training, tuning, or retrieval-policy development. Freeze the target list and split before scoring.

For each target, construct the eligible in-file context from the target file while masking the completion and preventing any future/answer tokens from appearing. Construct eligible cross-file candidates only from files available in the same project snapshot at inference time. Exclude generated evaluation artifacts and any source that would not actually be accessible in the intended completion setting. If benchmark provenance or licenses constrain these choices, follow those constraints and document exclusions.

### Conditions and token allocation
Use one fixed model and tokenizer in all conditions. Fix the task instructions, completion prefix, output-token allowance, decoding method and parameters, stop rules, and all non-context prompt content. Define a context-token budget B, measured with the model tokenizer; the non-context prompt portion is identical and does not count toward B. No prompt may exceed B context tokens.

1. **In-file-only baseline:** Fill B with eligible target-file context only. Use a prespecified deterministic policy (for example, nearest surrounding lines first, with a defined balance of preceding/following context if both are used), subject to answer masking and truncation at token boundaries.
2. **Cross-file treatment (primary comparison):** Reserve a prespecified share of B for selected other-file context; use the remainder for target-file context. Specify the share before testing. Select other-file material using a fixed, inference-available retrieval policy and deterministic tie-breaking. For example, rank candidate files/snippets by a declared lexical/symbol-overlap score against the target prefix and retain the top material, with stable path and position tie-breaks. Do not use the hidden completion or test labels in retrieval. Truncate snippets deterministically to fit their allocation. If eligible content does not fill an allocation, define in advance whether unused tokens are backfilled from the other context type or left unused; preferably prespecify a backfill rule so actual prompt budgets remain comparable.
3. **Token-matched in-file control (recommended where feasible):** Use exactly the same reserved share and context-token accounting as the treatment, but fill the reserved portion with additional eligible target-file context under a separate fixed policy (for example, next-nearest nonoverlapping context). This controls for the allocation/reformatting procedure and tests whether other-file information helps beyond simply changing which in-file tokens are shown. Avoid duplicate tokens/snippets. If the target file cannot supply enough distinct valid context, either use the prespecified backfill rule and report actual budgets, or omit that target from this secondary comparison under a preregistered eligibility rule; do not silently duplicate content.

For all arms, define stable ordering and separators/metadata for snippets, and include these formatting tokens in the budget. The primary contrast is between the baseline and cross-file treatment, with actual context token counts equal whenever feasible. Report any targets where equality cannot be achieved and apply the same preregistered eligibility or backfill rules rather than post hoc exclusions. A useful sensitivity analysis varies the cross-file allocation share while maintaining B, but designate one share as primary in advance to avoid selecting the best result after observing test performance.

### Model execution and leakage controls
Run inference offline on the frozen test targets. Keep model checkpoint/version, tokenizer, prompt template, decoding parameters, random seeds (if sampling), and output budget identical across conditions. Prefer deterministic decoding for reproducibility; if sampling is required, use matched seeds or repeated draws per target and account for that dependence. Cache inputs/outputs with condition and target identifiers. Ensure that retrieval uses only project files available before completion and excludes the masked span, future file content where inappropriate, benchmark answers, and any test labels. If retrieval has tunable parameters, tune only on a separate development split, then freeze them before the test set.

### Outcomes and analysis
Choose one primary metric before the test. Exact match on the masked completion is a transparent primary measure, but can be overly strict; report at least one complementary metric such as normalized edit similarity or a language-appropriate code similarity measure. If feasible, add compile/test or static-validity outcomes, but treat them as secondary because executable test infrastructure may not exist or may be costly. Apply identical normalization and scoring to every condition, and make the reference span and scoring rules explicit.

For each target, score all conditions and calculate paired differences. Report the mean/median paired change and uncertainty interval; use a paired bootstrap clustered by repository (rather than treating every target as independent), or a suitable mixed-effects analysis with repository-level structure. Report sample counts, exclusions, per-target context-token counts, and results by relevant prespecified strata such as language or repository, without turning exploratory subgroup results into the primary conclusion. Do not infer causality from unpaired aggregate scores when targets differ across arms.

### Feasible checks and reporting
Before any main evaluation, validate the prompt builder on a small non-test set: check tokenizer-based budget accounting, exact equality of fixed prompt components, masking of answers, deterministic retrieval/tie-breaking, truncation behavior, and no duplicate snippets in the token-matched control. Confirm that every test target is present in every compared arm and that no arm exceeds B. These are design feasibility checks, not evidence of results.

In reporting, state the benchmark and model versions, split method, target definition, retrieval policy and parameters, context allocation, token accounting convention, fallback behavior, decoding, scoring, exclusions, and uncertainty method. Report the primary paired estimate and uncertainty, not just a single aggregate score. Do not characterize the design as showing improvement unless an experiment is actually run and the preregistered analysis supports that conclusion.
