## Proposed experiment design

### Objective and estimand
Estimate whether adding cross-file context improves code-completion quality relative to in-file-only context, for the same fixed model and set of completion sites. The primary estimand is the paired mean change in exact-match completion accuracy across eligible held-out sites; also report results aggregated by repository so conclusions are not driven only by large repositories. This is a benchmark proposal, not an assertion that any experiment was run.

### Task and sampling/splitting
- **Proposed task:** infill completion at a deterministic location inside a source file. Define each example by the visible prefix and suffix surrounding a held-out target span; ask the model to generate exactly that span. This gives a reproducible comparison, though it does not represent every form of interactive completion.
- **Proposed source:** use a repository-level code benchmark with license-compatible, buildable or parseable source snapshots. No benchmark or language is selected in the supplied project materials. Choose one benchmark and language before evaluation, and document snapshot dates, filters, and exclusions.
- **Sampling:** sample eligible completion sites across repositories, stratifying by repository and language where relevant. Deduplicate identical or near-identical examples and cap each repository's contribution or use repository-level aggregation. Define eligibility before model calls (e.g., target is nonempty, source parses, and the prompt fits the predeclared token policy). Report counts excluded at each filter.
- **Splitting:** keep evaluated repositories disjoint from any repository-level training, tuning, or prompt-development set where feasible. Freeze benchmark snapshots and split before selection or evaluation. Since pretrained model training corpora may be unknown, use a post-training snapshot or benchmark split when available, disclose possible pretraining contamination, and avoid using evaluation targets to tune prompts, retrieval, or thresholds. If repository-disjoint training separation cannot be established, state this limitation rather than implying it is solved.

### Conditions and controls
Run both conditions on every same eligible completion site, using the same model checkpoint, target, target-file context, prompt template, decoding settings, output stop rules, and evaluation script:
1. **In-file-only baseline:** provide only the permitted target-file context around the completion site (visible prefix and suffix, or prefix only if the chosen benchmark is prefix completion). No content from other files is included.
2. **Cross-file condition:** provide exactly the same target-file context, plus a bounded selection of other files from that example's repository snapshot. The target file itself and generated target span are ineligible for retrieval. Label file boundaries and paths consistently.

The primary controlled comparison uses a fixed total input-token budget. Reserve a fixed allowance for the target-file context and prompt in both conditions; use the remaining context allowance for retrieved files only in the cross-file condition. Thus adding files does not silently change target-file visibility or exceed model limits. Also report a secondary, clearly labeled *unconstrained-baseline* comparison if desired: baseline may use its available window for more in-file context, while cross-file reallocates some window to other files. This answers a different practical trade-off and should not replace the controlled primary comparison.

Use deterministic decoding (e.g., greedy decoding), fixed maximum generated tokens, and identical stop criteria. Pin model/version, tokenizer, prompt template, and inference settings. Randomize or interleave condition order to mitigate service or cache drift; cache identical requests if appropriate. Keep evaluators blind to condition where human review is used.

### Retrieval, truncation, and missing context
- **Proposed retrieval:** for each completion site, rank eligible same-snapshot files using a frozen, deterministic lexical or symbol-based procedure that does not inspect the hidden target. A simple feasible default is symbol/import/reference matching based on visible target-file text and repository metadata; exclude generated/build/vendor files using predeclared rules. Record ranking method and selected paths. Do not tune the ranker on evaluation outcomes.
- **Truncation:** tokenize with the chosen model tokenizer. Keep the target-file allocation identical across conditions. Add retrieved files in ranking order until the reserved cross-file allowance is exhausted; truncate only at safe boundaries (e.g., whole declarations where possible, otherwise deterministic token boundary), and record token counts. Apply a fixed rule for oversized target files in both conditions, such as retaining a window around the hole with nearest context first. Never exceed model context limits; count unusable examples consistently rather than selectively dropping a condition.
- **No retrieved candidates:** retain the example in both arms, with the cross-file addition empty and a recorded zero-retrieval indicator. This preserves paired denominators; report the proportion with no candidate and a sensitivity analysis on examples with at least one eligible candidate. Missing or unreadable files follow a fixed exclusion/skip rule applied before condition construction.
- **Optional ablations:** a shuffled-file or irrelevant-file control can test whether any gain is due to extra tokens rather than useful cross-file information. Treat this as secondary and apply the same token budget. It is not required for the primary answer.

### Leakage safeguards
Construct prompts from immutable repository snapshots. Retrieval may access only files in the same snapshot that are permitted as context; it must not access the target span, post-snapshot files, benchmark reference solutions, tests or metadata containing the answer, or other evaluation examples. Mask the completion span before ranking and ensure target-derived identifiers from the hidden span are unavailable to retrieval. Audit prompt assembly with automated assertions and sampled manual inspection: target file excluded from cross-file candidates, target span absent from all inputs, paths/snapshot identifiers correct, and no test/answer directories included. Keep evaluation labels separate from prompt-generation code. Freeze all design decisions and retrieval parameters before scoring. Document unavoidable uncertainty about model pretraining contamination.

### Outcomes and statistical analysis
- **Primary metric:** exact match of normalized generated target span (normalization limited in advance, e.g., line-ending and trailing-whitespace normalization; do not normalize away semantic differences). Report raw exact-match rate in each condition and paired difference in percentage points.
- **Secondary metrics:** token-level exact match / edit similarity, compile or parse success when well-defined, and pass rate on available hidden tests only if tests are legitimate independent evaluation artifacts and never included in prompts. Report completion length, truncation, and retrieval coverage as diagnostics, not as substitutes for quality.
- **Paired inference:** compute per-example outcome differences; report the paired mean difference and a 95% confidence interval using a repository-cluster bootstrap (resample repositories, retaining paired observations within each sampled repository). If enough repositories are available, also show per-repository changes and a paired test as a secondary check. Predeclare the primary metric and analysis; avoid treating all examples as independent when clustered. Report sample sizes, number of repositories, ties, missingness, and subgroup results (e.g., language or retrieval availability) as exploratory unless powered and predeclared.
- Interpret gains alongside retrieval coverage and token allocation. A null result does not establish that all cross-file strategies fail; it applies to the chosen model, task, retrieval rule, and budget.

### Feasibility plan
The project materials do not specify a benchmark, model, dependencies, or execution target, and `track.md` is described as design-only with repositories and compute not required. Accordingly, these are proposed choices, not fixed project setup. For a feasible future run, first select a licensed benchmark and an available fixed model that can be run within its inference/context limits; conduct a small pilot on a separate development set solely to validate prompt construction, token accounting, retrieval, and scoring, then freeze the configuration.
