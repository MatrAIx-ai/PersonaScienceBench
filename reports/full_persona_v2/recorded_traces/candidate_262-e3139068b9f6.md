## Recommended experiment design

### Question and estimands
Test whether adding cross-file information improves code completion relative to in-file-only context.

**Primary estimand:** the average paired change in completion performance when cross-file context is introduced under the *same total prompt/context-token budget* as the in-file-only baseline, on a held-out population of eligible completion cases from unseen repositories. This estimates the value of reallocating a fixed context budget to cross-file information, not the effect of increasing context capacity.

**Optional secondary estimand:** performance change when cross-file context is added while retaining the baseline in-file context and allowing a larger total budget. This estimates the combined effect of added information and additional capacity; it should not be conflated with the primary estimand.

### Dataset and leakage-safe split
Select a dataset of real code completion sites with repository identity and enough surrounding source to reconstruct contexts. Define target sites and eligibility rules before evaluation (for example, a held-out span in a source file, with the target excluded from all prompts and retrieval inputs). Split by repository, not randomly by completion example: use training/development repositories for prompt or retrieval-policy decisions and disjoint test repositories for final evaluation. If repository forks, duplicated snapshots, or mirrors occur, group them together or deduplicate to prevent cross-split leakage. Freeze the test set and any retrieval index before scoring. In particular, ensure no target text, future code, held-out test examples, or evaluation labels can enter retrieval results.

If a repository-held-out benchmark is unavailable, report that limitation and use the strongest feasible grouping by project/repository; do not describe a file-level random split as repository-generalization evidence.

### Conditions and controls
For each eligible test completion, construct a matched pair:

1. **Baseline:** only permitted in-file context (such as preceding and, if the chosen task permits, surrounding file content), excluding the target completion.
2. **Primary treatment:** the same completion task and model, with cross-file context retrieved from other permitted files in the same repository. Keep the *total context-token budget* equal to the baseline budget. Use a prespecified allocation rule to make room for retrieved material, such as replacing a fixed, predeclared portion of in-file context; retain the same target location and completion prefix. State the allocation explicitly and apply it consistently rather than tuning it on test outcomes.

For an optional **added-capacity treatment**, preserve all baseline context and append cross-file material, allowing a larger total context up to a predeclared model limit. Compare it with the same baseline and label this as the combined information-plus-capacity contrast.

Hold constant across paired cases: model/checkpoint, system and task instructions, prompt formatting, completion stopping rule, decoding parameters (prefer deterministic decoding where supported), target span, scoring implementation, and execution/software versions. Do not tune either condition on test repositories. If the production pipeline is itself the object of study, freeze its version before scoring and record it for reproducibility.

### Cross-file retrieval policy
Specify a retrieval policy before test evaluation, including eligible files, query construction, ranking/retrieval method, number or token limit of retrieved snippets, and tie-breaking. Restrict candidates to the same repository and exclude the target file by default for a clear cross-file contrast; exclude generated, vendored, or test-only files if they are outside the intended use case, and state any such exclusions. Use only repository content that would be available at the completion point. Avoid use of future revisions or commits unless the task explicitly represents that setting. Apply the same retrieval policy in development and test, without access to test completions or labels. Record retrieval availability and basic diagnostics (e.g., whether a nonempty result was available and retrieved token count). Do not selectively omit difficult cases from treatment scoring: if no suitable cross-file result exists, use a prespecified empty-retrieval treatment and retain the case for an intention-to-treat comparison; also report the availability rate.

### Outcomes
Predeclare one primary automatic outcome suitable to the dataset. A practical default for exact-span code completion is **exact match** after a fixed, documented normalization policy (preferably no semantic-changing normalization). Report its per-case paired difference, with the percentage-point change as an interpretable summary. If completions have variable lengths or exact match is too brittle, predeclare token-level exact match or edit-based performance (such as normalized edit similarity) as an additional metric, not a replacement selected after seeing results. For valid compilable units with an applicable harness, compilation or test pass rate can be a useful secondary outcome, but should not be treated as available unless the dataset supports it. Also report completion failures, invalid/truncated outputs, and cross-file retrieval availability. Any metric based on reference similarity measures agreement with the dataset reference, not all functional correctness; state this limitation.

### Analysis and reporting
Score both conditions for every same test case and compute paired differences. Report the primary metric for each condition, paired effect estimate, and a 95% uncertainty interval. Account for clustered observations within repositories: preferably use a repository-cluster bootstrap, resampling held-out repositories and preserving paired cases within each sampled repository; alternatively use an appropriate hierarchical model with repository effects. Give the number of repositories and cases, not only example counts. Predefine treatment of decoding/scoring failures and missing cases; report exclusions and denominators by condition. For secondary language/task strata, report estimates with uncertainty and describe them as exploratory unless adequately powered and prespecified. Avoid interpreting a small point estimate without its interval as evidence of a reliable improvement. No numerical result or direction should be presumed.

### Feasibility and checks
This design is method-agnostic and does not require an experiment to be run here. Before any future run, feasible checks include validating that target spans are absent from both prompts and retrieval candidates; auditing a sample of retrieved snippets for repository membership, target/future leakage, and correct file exclusion; verifying exact total context budgets for the primary pair; confirming identical model and decoding configuration; testing the scoring code on hand-checked examples; and checking that repository grouping has no obvious duplicate projects across splits. A small pilot on development repositories can establish prompt construction and runtime feasibility, but must not be used to adjust choices based on held-out test scores. With no GPU or dependencies specified as available in the task metadata, practicality of a particular model/run cannot be asserted; model access, runtime, data licensing, and evaluation harness need confirmation before implementation.
