## Experiment design

### Question and estimand
Estimate whether adding relevant cross-file context improves code-completion accuracy over an in-file-only prompt, with all other inference and evaluation choices fixed. The estimand is the paired change in exact-match success on a prespecified set of held-out completion locations.

### Proposed assumptions—not source-confirmed setup
No corpus, model, pipeline, or dependencies were supplied. For a concrete, feasible design, assume a licensed code corpus containing projects with multiple source files and a locally runnable code-completion model. Select projects and repositories before evaluation, and split at the repository level (rather than randomly splitting snippets) to reduce repository overlap and memorization. Pin the model checkpoint, tokenizer, prompt construction, and software versions. These are protocol proposals, not facts about the available project.

### Data and completion task
1. Build a held-out set of repositories and choose completion locations by a reproducible sampling rule, such as eligible function-body positions sampled from held-out files. Exclude generated/vendor files, malformed examples, and locations where the target continuation cannot be determined.
2. For each location, define a fixed target span of the next 20 non-whitespace lexical tokens (or all remaining tokens if the file ends sooner); exclude examples with fewer than 5 target tokens. The exact span definition must use the corpus tokenizer/parser consistently and be fixed before evaluation.
3. Construct the input using only material available before the completion point in the target file. The ground-truth span and all later text in that file are hidden from both arms. The suffix must not enter prompts, retrieval indexes, filenames/metadata, caches, or candidate selection. Exclude held-out target files from the cross-file candidate pool; candidate files may come only from other files in the same held-out repository, and must also be checked not to contain a copied target answer. This gives the treatment access to the repository’s other files without exposing the answer itself.

### Arms
- **Control (in-file only):** target-file prefix up to the completion point, plus a fixed instruction/template and any necessary language/file metadata. No other file contents.
- **Treatment (cross-file + in-file):** exactly the same target prefix/template, plus selected content from other files in the same repository. Use a deterministic, prespecified retrieval method (e.g. lexical symbol/reference matching against identifiers in the prefix), excluding the target file and target suffix. Define a maximum cross-file token allowance and selection/ranking rule before scoring.

Use identical model, checkpoint, tokenizer, decoding (prefer greedy decoding, temperature 0), stop rules, and completion-token cap in both arms. Run each item in both arms, randomizing arm execution order or interleaving to avoid time/order effects. Do not tune retrieval, prompts, or thresholds on test outcomes; use a separate development set if tuning is needed.

### Fairness and controls
Use the same overall model-input token budget in both arms, including prompt overhead: reserve a fixed allowance for the target prefix and template, then allow the treatment to replace otherwise-unused budget with cross-file tokens. The control receives no cross-file tokens and should not be artificially padded with code; report the actual input-token distributions and, as a secondary practical comparison, a natural unbudgeted in-file baseline if the fixed-budget constraint materially shortens its prefix. Keep the output-token cap identical. If cross-file tokens displace target-prefix tokens under the chosen budget, report this explicitly and consider a prespecified sensitivity run that fixes the target prefix and gives both arms the same maximum total budget, interpreting that as additional context cost rather than equal-budget evidence.

Controls include identical examples and target spans, context construction rules, prompt wrapper, model and decoding, output truncation/stop rules, and evaluation script. Deduplicate repositories or near-duplicate files where possible; audit a sample of retrieval results and prompts for target-suffix leakage, answer duplication, and malformed context. Cache keys must distinguish arms and input content.

### Outcomes and analysis
**Primary metric:** per-location exact match: generated continuation, after only a prespecified normalization of line endings and trailing whitespace, equals the complete fixed target span. A truncated or overlong/mismatched continuation counts as incorrect. Avoid aggressive normalization that could erase meaningful code differences.

**Secondary metrics:** token-level exact match (fraction of target tokens matched at corresponding positions), normalized edit similarity, compile/parse success where applicable, and performance by language, repository, and target type. Report actual prompt tokens, generated tokens, latency, and any inference failures; these characterize cost but do not replace the accuracy endpoint.

For each location compute treatment-minus-control exact-match outcome, summarize arm accuracies, paired absolute percentage-point difference, and relative change. Quantify uncertainty with a paired bootstrap resampling repositories (cluster level, preserving paired examples within each repository) and report a 95% interval; avoid treating correlated locations in one repository as independent. Also report paired discordant counts (treatment-only successes versus control-only successes). Prespecify sample size or, absent a defensible power estimate, collect a fixed number of repositories/examples and state that uncertainty may be wide. Do not stop based on interim significance. Report exclusions and missing/inference-failure handling by arm.

### Feasibility and practical limits
The proposed experiment is design-only: no experiment or computation is claimed. It is feasible if a multi-file licensed corpus and an inference-accessible model can be obtained, since the core comparison requires only paired prompts and completion scoring. Results would establish performance only for the selected model, retrieval strategy, corpus, and context budget; they would not by themselves prove that all cross-file methods improve completion.
