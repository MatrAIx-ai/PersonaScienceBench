## 2. Workload और context checks
प्रस्तावित पूर्ण grid, प्रत्येक model और विधि के लिए:

| आयाम | मान |
|---|---|
| Batch B | 1, 4, 8 |
| Prompt tokens P | 128, 512, 2048, 3584 |
| Generated tokens G | 128, 512 |

यह 24 generation cells और 12 unique prefill cells है। Primary aggregate में prefill cells को G के कारण दो बार न गिनें। समान cell की प्रत्येक sequence समान P रखे, ताकि padding का प्रभाव न मिले। Attention mask और position IDs समान हों।

प्रस्तावित nominal context budget 4096 है; वास्तविक checkpoint/tokenizer/config का limit execution से पहले जांचें। सभी cells के लिए conservatively P+G ≤ verified context limit अनिवार्य हो; BOS आदि P में गिने जाएं। 3584+512=4096 boundary cell विशेष रूप से validate करें। Limit छोटा निकले तो incompatible cells हटाकर संशोधित grid timing से पहले freeze करें, न कि चुपचाप RoPE scaling लगाएं।

Held-out text corpus से पर्याप्त लंबी deterministic token windows बनाएं; split, hash, seed और exact token arrays सुरक्षित रखें। कोई corpus उपलब्ध न हो तो पहले acquisition आवश्यक है; synthetic token benchmark संभव है, लेकिन उसे अलग microbenchmark कहें, quality या realistic text evidence नहीं।

Primary workload static batches, greedy generation, fixed G और EOS early-stop disabled रखे। दोनों implementations को समान prompts और token count मिलें; उत्पन्न token values अलग हो सकती हैं। जरूरत पड़ने पर common forced-token stream का अलग control जोड़ें, उसे वास्तविक free generation से न मिलाएं। Continuous batching, speculative decoding, prefix-cache reuse और request overlap बंद रहें।

## 3. Phase timing की स्पष्ट परिभाषा
**Prefill GPU time:** empty KV cache से P-token forward pass, cache writes और अंतिम prompt position के logits बनने तक। Input token IDs GPU पर पहले से हों; online rotations, quantization/dequantization, scales और सभी आवश्यक cache/layout operations शामिल हों। G से स्वतंत्र एक prefill माप लें। Throughput = B×P / prefill seconds।

**पहला generated token:** prefill के अंतिम logits से चुना जाता है; उसके लिए अलग single-token decode forward नहीं होता। Token selection time को अलग दर्ज करें, और user-facing TTFT में शामिल करें।

**Decode GPU time:** generated token 1 उपलब्ध होने के बाद, token 1 को cache सहित feed करके token 2 निकालने से शुरू; token G निकलने तक **G−1 single-token forward steps** हों। उनकी token selection सहित loop की GPU work गिनी जाए; final token G को अनावश्यक रूप से फिर feed न करें। हर step के rotations, activation quantization, quantized cache read/write, attention, scale/layout और dequantization overhead शामिल हों। शुरुआती cache length P है; अंतिम measured step से पहले P+G−2, और उसके बाद P+G−1 होगी।

Decode throughput = B×(G−1) / decode seconds। एक batched step का औसत समय = decode seconds/(G−1); इसे प्रति sequence inter-token service time समझें, B से दोबारा भाग न दें। Cache growth का प्रभाव देखने के लिए अलग instrumented pass में शुरुआती/मध्य/अंतिम steps की latency लें; हर step पर host synchronization लगाकर मुख्य throughput को विकृत न करें।

**GPU और user-facing boundaries:**
- GPU events तथा phase-end synchronization से device phase timing लें; सभी auxiliary streams की dependencies सुनिश्चित हों। Phase timers में आवश्यक online transformations रहें। Loading, offline quantization/calibration, compile और warm-up बाहर हों और उनका समय अलग खर्च के रूप में दर्ज हो।
- एक अलग, phase-boundary instrumentation रहित wall-clock pass में local request arrival से TTFT और completion latency मापें: tokenization, host/device transfer, dispatch, first-token selection, output transfer और detokenization सहित। Server/network/queueing शामिल न हों तो स्पष्टतः 'local user-facing' कहें।
- User-facing decode interval पहले token के observable होने से आखिरी तक है; उसका denominator भी G−1 है। पृष्ठभूमि asynchronous GPU work को timer समाप्त होने से पहले पूरा होना चाहिए। Phase timings को जोड़कर user latency का दावा न करें।

## 4. Controls और repetitions
FP16 baseline भी optimized हो: समान framework, attention backend जहां compatible हो, compiler/CUDA graph policy, allocation policy, tokenizer, checkpoint, context, batch, inputs और device। FP16 cache FP16 रहेगा; QuaRot cache का वास्तविक dtype precision map में रहेगा। Runtime-specific आवश्यक scratch/cache preparation phase में शामिल हो; generic allocations दोनों के लिए समान policy से preallocate किए जा सकते हैं, पर wall-clock request path का वास्तविक overhead न छिपाएं।

प्रत्येक cell/variant में compilation के बाद 5 untimed warm-up requests और 20 timed paired requests प्रस्तावित हैं। पांच निश्चित prompt batches पर चार repetition blocks रखें। दो variants एक साथ GPU पर न रखें। हर block में variant order randomized/balanced हो; reload/init के बाद फिर warm-up करें। तापमान, power/throttling और अन्य processes दर्ज हों। यदि warm-up पर्याप्त न हो तो दोनों के लिए बढ़ाकर अंतिम count report करें। Cold-start अलग विषय है, steady-state में न मिलाएं।

Kernel/backend बदलना आवश्यक हो तो optimization knobs और अंतर की table दें। ऐसी स्थिति में causal दावा केवल 'इस QuaRot implementation बनाम इस FP16 implementation' तक सीमित हो; अंतर को केवल bit-width या rotations का प्रभाव न कहें। समान backend वाला अतिरिक्त control तभी जोड़ें जब वह वास्तव में supported हो।

## 5. Analysis और uncertainty
हर matched cell और paired request i के लिए phase-specific speedup:
**S_i = T_FP16,i / T_QuaRot,i**; S>1 तेज, S<1 धीमा। Prefill और decode अलग रखें। समान token count होने से throughput ratio यही होगा। Absolute latency, tokens/s, speedup और 95% interval साथ दें; ratios मात्र नहीं।

प्रति cell paired log-speedups के mean का exp अर्थात geometric mean मुख्य ratio हो। Prompt batch को cluster मानकर उसके भीतर repetition blocks की paired bootstrap से 95% interval दें; 20 repeats को 20 स्वतंत्र input samples न मानें। Batch/length-wise plots मुख्य परिणाम हों। Optional overall geometric mean केवल सभी common-fit cells पर बराबर cell weights के साथ हो; workload weighting का औचित्य स्पष्ट हो।

Median, variability और wall-clock p95 दिखाएं, पर इतने छोटे sample में tail estimates exploratory हैं। Repeat बढ़ाने की आवश्यकता interval की चौड़ाई से बताएं; संकीर्ण CI या target speedup पहले से मानकर न चलें। Bootstrap intervals run/input variation बताते हैं, दूसरे GPUs/models पर generalization नहीं।

## 6. Memory, OOM और capacity अलग प्रश्न हैं
हर variant/cell में loaded-model footprint, peak allocated/reserved device memory, process/device memory और prefill/decode peak अलग दर्ज हों; peak counters phase से पहले reset हों। Cache और scratch buffer footprint जहां उपलब्ध हो अलग दें।

यदि FP16 OOM और QuaRot fit हो, उस cell का paired speedup **undefined** है—अनंत speedup नहीं। वह capacity benefit है। दोनों fit हों तभी matched-workload latency ratio दें। वैकल्पिक capacity sweep में fixed P/G पर batch बढ़ाकर verified maximum-fit batch खोजें; उसकी throughput को अलग chart में रखें, क्योंकि batch बदलने से latency comparison बदल जाता है। Failures, OOM, unsupported kernels और retry protocol की log रखें।

## 7. Quality और calibration
Calibration corpus और evaluation corpus अलग documents/splits से लें; deduplication तथा hashes से overlap जांचें। प्रस्तावित calibration budget 128×2048-token training windows है, लेकिन documented recipe अलग हो तो उसे अपनाकर बदलाव दर्ज करें। Calibration पर settings tune की जा सकती हैं; held-out evaluation पर नहीं।

Held-out quality check के लिए उदाहरणतः WikiText-2 test perplexity, fixed tokenizer और declared window/stride तथा label masking के साथ FP16 और QuaRot दोनों पर मापें। Corpus उपलब्ध न होने पर acquisition या समान रूप से versioned alternative execution prerequisite है। पर्याप्त संसाधन हों तो अलग held-out downstream task जोड़ें। Calibration और quality/timing evaluation के documents न मिलें।

Absolute तथा relative perplexity change और corpus-block uncertainty report करें। कोई सार्वभौमिक स्वीकार्य quality threshold या expected speedup ज्ञात तथ्य नहीं है; deployment stakeholder threshold चाहिए तो evaluation से पहले तय करे। Quality खराब निकले तो speed findings छिपाएं नहीं, उन्हें accuracy trade-off के साथ प्रस्तुत करें।

## 8. Feasibility और विस्तार
**कम-संसाधन प्राथमिक विकल्प:** केवल 7B, B=1, P={128, 2048}, G=128, वही 5 warm-ups और 20 paired requests; एक समर्थित 24-GB या अधिक VRAM GPU पर पहले FP16+cache+scratch fit जांचें। 24 GB fit की गारंटी नहीं है। Sequential variant loading, सीमित profiler validation और एक held-out perplexity check से लागत घटेगी। परिणाम इस छोटे grid तक सीमित होगा।

13B पर single-device memory fit सत्यापित करके वही grid; 70B FP16 के लिए पर्याप्त aggregate VRAM और supported model/tensor parallelism चाहिए। 70B में दोनों variants का GPU count, parallel topology और interconnect समान रखें। यदि QuaRot उसी sharding/communication path को support न करे, 70B extension स्थगित करें या अलग implementation comparison घोषित करें। QuaRot का कम GPU पर fit होना अलग resource/capacity result होगा, matched speed नहीं।

स्थानीय GPU-विहीन environment में latency benchmark उपयुक्त नहीं और CPU emulation से GPU INT4 speed का निष्कर्ष नहीं निकलेगा। भविष्य के execution से पहले checkpoint/context, data, precision map, kernel dispatch, common-fit memory और multi-GPU compatibility की checklist पूरी करनी होगी। इसका अभाव डिजाइन को नहीं रोकता, केवल निष्पादन की शर्तें तय करता है।
