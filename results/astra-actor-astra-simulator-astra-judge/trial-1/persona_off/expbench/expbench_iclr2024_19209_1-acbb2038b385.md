# Experiment design: OPRO instructions versus two BBH baselines

## 1. Question, evidence, and scope

The experiment will ask whether frozen, task-specific OPRO instructions improve accuracy over each of two instruction conditions on a fixed BBH suite:
1. `Let's think step by step.`
2. The empty string, meaning no added instruction.

The supplied materials establish the question and the design-only requirement. They do not provide optimized instructions, instruction provenance, BBH data, an OPRO implementation, model identities, or the historical evaluation protocol. No experiment has been run, and this design makes no claim about the answer.

**Approved design defaults—not established facts about the original OPRO setup:** include every task in a pinned BBH release; use task-specific instructions, one fixed scorer model, and a common no-demonstration wrapper. The primary estimand is the difference in macro-averaged accuracy across this fixed suite under fixed inference settings. Model transfer, generalization to new tasks, and average reliability of the discovery procedure are outside the primary claim.

## 2. Source gate: two distinct routes

### Route A: evaluate externally supplied instructions

Before any evaluation, obtain exact instruction texts for every task and an auditable provenance manifest: source/version, task mapping, optimizer and scorer identities if known, discovery and selection data, demonstrations, feedback sources, and any subsequent manual selection. Hash and freeze the instructions.

Proceed confirmatorily only if that provenance supports a test set in the pinned suite that was not exposed during instruction discovery or selection. Reserve any wrapper-development examples separately. Establish the eligibility rule and test IDs before examining test predictions. Instructions need not have been discovered with the chosen scorer, but the resulting claim is about these instructions evaluated with this scorer—not necessarily a reproduction of their original evaluation.

**A new random split cannot repair historical exposure.** If discovery used all available examples, or provenance cannot support an unexposed test set, Route A cannot yield the proposed confirmatory claim. A same-data assessment could be explicitly labeled descriptive and potentially contaminated, but not used to answer the confirmatory question. Missing instructions for even one task also prevent an all-task Route A analysis unless the scope is formally changed before evaluation.

### Route B: prospective, documented OPRO discovery

If Route A is unavailable, conduct a separate future discovery experiment. Label it an implementation-specific OPRO experiment, not a reproduction of historical instructions or results. First pin a source-documented OPRO implementation/procedure and its optimizer prompt. The following are proposed operational defaults, subject to data and resource checks before preregistration:

- Within each task, allocate approximately **20% optimization / 20% validation / 60% test** using a fixed seed and stable example IDs. Group duplicates and near-duplicates into the same partition, including cross-task duplicates where present; stratify on answer categories where meaningful. Record actual counts and any grouping-induced deviations.
- Use one primary discovery run per task, with seeds fixed in advance. Use **20 optimizer rounds producing four candidates each**, for at most **80 generated candidate slots per task**.
- The optimizer receives the task description, optimization-only material, its fixed meta-prompt, and previously scored instructions. Maintain a deterministic history of the top 20 scored instructions; rank ties by shorter instruction length and then stable candidate ID. Validation and test information never enter the history.
- Evaluate each distinct admissible candidate on all optimization examples using the same scorer configuration as the final comparison. Deduplicate candidate strings. Score the two baseline strings on the optimization partition as initial reference entries, but exclude them from the generated-instruction finalist pool.
- Fix admissibility rules before search: plain instruction text, no per-example answer table, no demonstrations or tool calls, and at most 256 scorer-tokenizer tokens. Invalid or duplicate generations consume candidate slots; there is no performance-driven replenishment.
- After the search, take the top five distinct admissible generated candidates by optimization accuracy, or all if fewer than five exist. Score these once on the validation partition. Select the highest validation-accuracy candidate, resolving ties by optimization accuracy, shorter token length, and stable candidate ID. Freeze it before unlocking test evaluation.
- Stop after 20 rounds or an independently fixed resource cap, not after observing validation/test success. Validation is consulted only for final selection. If no admissible candidate exists for any task, report discovery failure rather than silently replacing it with a baseline or dropping the task.

Implementation details that must be pinned before execution include optimizer/scorer model identifiers and dated versions, access provider, optimizer meta-prompt and initial state, sampling parameters, score formatting, history rendering, and context-truncation policy. These defaults do not purport to describe the original OPRO configuration.

**Replication:** one preregistered discovery run defines the primary set of frozen instructions. If resources permit, preregister two additional independent discovery runs as secondary sensitivity analyses. Complete all discovery and selection before any test results are revealed, report all runs, and never choose the best test-performing run. These few runs are not a primary estimate of general discovery reliability.

## 3. Leakage controls and data custody

Maintain a manifest of release checksum, task names, example IDs, duplicate groups, partition assignments, and seeds. The optimizer process must not have access to validation or test files; the selection process may access validation only; the final evaluation process receives frozen artifacts. Keep test labels, model outputs, and aggregate scores inaccessible until all task instructions, scoring code, hypotheses, and analysis settings are locked.

Use optimization/validation examples only for prompt debugging, evaluator checks, token-budget calibration, and precision planning. Do not change instructions, extraction rules, stopping criteria, task inclusion, or decoding settings after reviewing test failures. A correction to a genuinely broken protocol must be disclosed; reusing the same test set after adaptive correction is no longer an untouched confirmatory evaluation.

These safeguards address experiment-induced leakage. Undocumented scorer or optimizer pretraining exposure to public BBH remains a separate limitation and must be disclosed.

## 4. Controlled paired evaluation

Use a common wrapper, for example:

`Question:\n{verbatim BBH input}\n\n{instruction block if nonempty}End your response with Final answer: followed by the task answer.`

For nonempty instructions, the instruction block is the exact instruction string followed by two newlines. For the empty condition, omit that block entirely. Preserve any formatting or options already contained in the BBH input. The shared final-answer request is an experimental formatting control, not an optimized instruction. No few-shot demonstrations are added. Freeze the exact rendered template and verify that condition diffs affect only the instruction block.

Evaluate all three conditions on exactly the same held-out examples. Pin and hold constant:
- scorer model/version, tokenizer, system message, role structure, and tool availability (tools disabled);
- temperature, top-p, seed where supported, context limit, maximum output tokens, and stop sequences;
- shared answer-format requirements and extraction/scoring rules;
- caching, batching, retry, and logging policy.

Proposed default: temperature zero and one completion per example-condition. Select a generous common output limit using development data, leaving room for every admissible instruction. The primary question is accuracy under this fixed cap, not equal realized token expenditure. Report actual token use and truncation rates. Provider nondeterminism may persist despite temperature zero; record that limitation rather than promising deterministic inference.

## 5. Scoring and endpoints

Pin official BBH task-specific evaluation rules where available. Otherwise preregister an explicit task-specific equivalence rule based on the dataset answer format. Apply the same deterministic extraction code to all conditions: use the last well-formed `Final answer:` field, then apply only the pinned task-specific normalization. Missing or ambiguous fields count as incorrect; no discretionary semantic grading after seeing outputs.

Check parsers on synthetic examples and development responses, including option labels, free-text answers, multiple answer fields, malformed output, and reasoning containing misleading intermediate answers. The parser must be condition-blind. Retain raw outputs for audit.

For task t with n_t test examples, let Y_tic be binary correctness for example i and condition c. Report each task's accuracy A_tc = mean_i(Y_tic). With T fixed tasks, the primary macro accuracy is A_c = (1/T) sum_t A_tc. The two primary effects are:
- Δ_step = A_optimized − A_step-by-step;
- Δ_empty = A_optimized − A_empty.

Report effects in percentage points and absolute accuracies. Example-weighted accuracy is secondary. A positive macro effect does not imply improvement on every task.

## 6. Paired uncertainty and decision rule

The uncertainty analysis is conditional on the frozen instructions, scorer configuration, and included tasks. It represents finite-example uncertainty within those tasks, not task sampling or search-run uncertainty. On the exact fixed test items themselves, the measured macro differences are descriptive quantities; inferential interpretation additionally assumes those held-out examples represent their task-specific item populations.

Use this fully specified paired, task-stratified bootstrap:
1. Form each example's joint correctness triplet for the three conditions.
2. For each of **50,000 replicates**, independently sample n_t example indices with replacement within each task, carrying the whole triplet together. Keep all T tasks and their equal weights fixed. If multiple test examples belong to a dependent duplicate group, use group resampling and the original task-level accuracy estimator instead; fix that choice from the manifest before evaluation.
3. Recompute both macro differences jointly. Pin the random seed, numerical library, and empirical-quantile convention.
4. For each contrast k, compute bootstrap errors e_bk = Δ_bk − Δ_hat_k. Construct a **97.5% two-sided basic bootstrap interval**:
   [Δ_hat_k − q_0.9875(e_k), Δ_hat_k − q_0.0125(e_k)].

Bonferroni across the two contrasts gives nominal simultaneous coverage of at least 95%, subject to bootstrap approximation. This is not an exact finite-sample guarantee, especially for small or nearly degenerate samples; retain discordance counts and flag unstable intervals.

**Preregistered primary success rule:** both simultaneous lower bounds must exceed zero. Otherwise do not conclude that optimized instructions outperform both baselines.
- Positive point estimates but an interval crossing zero: insufficient precision, not proof of no effect.
- Evidence of improvement against only one baseline: a baseline-specific conclusion, not overall success.
- An upper bound below zero against a baseline: evidence of inferiority to that baseline under this setup.
- Mixed task-level effects: describe heterogeneity even if the aggregate succeeds.

Report every task's three accuracies, paired differences, sample size, optimized-only-correct and baseline-only-correct counts, and wins/ties/losses by point estimate. Task-level intervals may be shown as explicitly descriptive, unadjusted intervals; do not make dozens of uncorrected task-specific significance claims. No task-population bootstrap or cross-model claim is part of this primary analysis.

## 7. Precision planning without invented pilot results

Before unlocking the test set, choose a practically meaningful improvement δ in percentage points and desired probability of satisfying the joint success rule (for example, 80%). These are planning targets, not assumed effects.

Estimate within-task paired discordance and the joint triplet distribution from validation/development predictions, acknowledging that finalist selection can make those estimates optimistic. Use the variance identity Var(Δ_hat_k) ≈ T^−2 sum_t Var(Y_optimized − Y_baseline,k)/n_t to check attainable precision. Then simulate joint paired outcomes over plausible effect sizes and discordance rates and apply the planned simultaneous interval rule to estimate power. Include pessimistic scenarios rather than relying on a single selected-candidate estimate.

The pinned release limits available test counts. If precision is inadequate, revise allocations or resource plans before preregistration and rerun discovery under the revised partitions; otherwise retain the feasible design and state the smallest effects it can resolve. Do not inspect test performance or drop difficult tasks to reach significance. Repeated calls on the same examples do not create new independent test examples.

## 8. Feasibility and cost accounting

This is a future model-backed experiment, not runnable from the supplied offline materials alone. It requires the pinned dataset, instruction artifacts or a documented optimizer implementation, model access, and a token/cost budget. No local GPU is necessary if hosted inference is used, but access and data-handling approval must be secured.

Budget input tokens from actual frozen prompts, including growing optimizer history; bound output tokens by calls times the pinned cap, and refine expected usage using development data only. The 80-candidate and 20/20/60 settings are illustrative operational commitments to be accepted or revised before preregistration, not known historical OPRO budgets. A binding resource cap and failure policy must be fixed before discovery.
