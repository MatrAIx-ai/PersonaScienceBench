# Experiment design: Adam fusion, graph complexity, and interpretability

**Status:** Design only. All setup values below are proposed, not established TorchOpt behavior. No experiments have been executed and all outcomes remain unmeasured.

## 1. Question and estimands
TorchOpt supplies the optimizer implementation; TorchViz visualizes autograd graphs. Use TorchViz for every condition rather than compare it against TorchOpt as an optimizer.

Estimate separately whether fusion changes (a) visible autograd topology and (b) human understanding. Distinguish tracing dependencies across optimizer steps from understanding Adam’s internal computations. A smaller visible graph can reflect an opaque abstraction boundary rather than simpler mathematics or less computation.

The primary object is the autograd dependency graph rooted at an outer loss evaluated after differentiable Adam updates, traced back to initial parameters. It is not the graph of the training loss before an ordinary optimizer step. A graph rooted at a scalar probe of the outer gradient is a separately reported, derivative-support-dependent secondary diagnostic.

## 2. Feasibility gate and implementation branches
Before any future data collection, record software versions, source revisions, device support, Adam update equations, and graph-visualization settings. Determine whether the candidate implementation actually provides operation fusion, what it fuses, whether it preserves autograd history, and whether it supports differentiation through gradients and optimizer updates. Kernel fusion and custom-autograd encapsulation need not have the same graph consequences. No specific TorchOpt version or API is assumed here.

Branches:
1. **Same-implementation toggle available:** Compare fused and unfused modes differing only in that toggle. Subject to numerical validation and inspection for other changes, this permits attribution to the toggle’s fusion/encapsulation behavior in the tested implementation.
2. **No toggle, but inspectable fused implementation available:** Construct a source-matched unfused functional reference with the same equations and update ordering. Report it as an implementation comparison. Agreement reduces semantic concerns but does not eliminate confounding from implementation structure, custom backward design, or graph bookkeeping; results do not uniquely identify a causal fusion effect.
3. **No equivalent differentiable pair:** Report the comparison as infeasible for that setup. Do not substitute a standard detached/in-place optimizer and call the result a fusion effect.

CPU is the proposed device. If the fused mode requires another device, the CPU comparison is unsupported; a separately scoped device-matched study would be needed. If the primary outer derivative is unsupported, a rendered forward dependency graph alone does not qualify as a successful differentiable-optimizer comparison. Unsupported further derivatives only remove the secondary diagnostic if the primary checks pass.

## 3. Reproducible proposed cases
Use CPU float64, a fixed RNG algorithm/version, and seeds 11, 22, 33, 44, and 55. Save generated tensors as artifacts so RNG-version differences do not alter reproduction. Use a local generator; draw tensors in the order specified within each case. Treat seeds as paired fixtures, not as evidence of independent graph topologies.

**Case A: smooth four-parameter quadratic.** Draw a 6-by-4 standard-normal matrix X, a six-vector y, an independent 6-by-4 matrix Z, a six-vector v, then theta0 = 0.1 times a standard-normal four-vector. Define inner loss as ||X theta − y||²/(2·6) + 0.05||theta||²/2, and outer loss as ||Z theta − v||²/(2·6). This is a transparent optimizer-focused case with a nontrivial Hessian.

**Case B: tiny smooth nonlinear model.** Draw an 8-by-2 standard-normal input matrix X, eight-vector y, independent 8-by-2 matrix Z, and eight-vector v. Use f(x) = aᵀ tanh(Wx+b)+c, with W of shape 3-by-2, b and a of length 3, and scalar c (13 parameters). Draw initial W, b, a, c in that order from 0.1 times standard normals. Use mean squared error divided by two for both inner and outer losses, with inner and outer data distinct. Keep the four parameter tensors separate in both implementations.

For each case and seed, perform K in {1, 3, 10} full-batch inner updates on the same inner data. These 30 paired configurations probe single-step structure and modest unroll scaling without asserting a resource budget.

Proposed Adam settings: learning rate 0.01; beta1 = 0.9; beta2 = 0.999; epsilon = 1e−8 outside the square root; zero initial first and second moments; first update indexed t=1; bias correction enabled; no weight decay, AMSGrad, clipping, scheduling, or stochastic layers. Reference equations are m_t=beta1 m_(t−1)+(1−beta1)g_t, v_t=beta2 v_(t−1)+(1−beta2)g_t², and theta_t=theta_(t−1)−lr·[m_t/(1−beta1^t)]/[sqrt(v_t/(1−beta2^t))+epsilon]. If the candidate cannot express these semantics, document and freeze a shared supported specification before collecting outcomes, or declare it unmatched.

Inner gradients must retain differentiability. Initial moments are constants; subsequent state dependencies are retained through all steps. Match parameter grouping, tensor shapes, dtype, device, gradients, state, epsilon placement, update ordering, and all graph-retention settings. Avoid detachments, numerical-state resets between steps, and in-place modifications that sever history.

## 4. Graph construction and counting
For every matched configuration:
- Build L_outer(theta_K), with theta_K depending on theta0 through all updates. This is the **primary graph root**. Traverse its reachable autograd dependencies and visualize with one pinned TorchViz configuration, identical naming, orientation, annotation flags, and layout settings.
- Compute dL_outer/dtheta0 for validation. If supported, construct it with differentiable history and define the secondary root s = uᵀ dL_outer/dtheta0, where u is the all-ones unit vector over the flattened initial parameters. Render s separately; do not combine primary and secondary counts.

Count unique reachable autograd function objects once, including leaf-accumulator functions, and report leaves separately. For raw topology, an edge is a non-null dependency link between function objects; report both link count including repeated links and unique source–target pairs. Compute longest dependency path in edges, degree distribution and maximum degree, and operation-type counts. Report disconnected expected parameter paths as failures/diagnostics, not small-graph successes. Cross-condition names or object identities are not used to match nodes.

Keep three layers separate:
1. **Raw autograd topology:** primary complexity endpoints are function-node count and dependency-link count, with depth and branching secondary.
2. **Rendered additions:** count parameter labels, saved-tensor boxes, annotation edges, and layout dimensions separately; they are not additional computations. Save both the extracted topology and DOT output.
3. **Hidden implementation:** record visible fused/custom nodes and their source-described responsibilities. Any internal expansion is a source-based explanatory diagram, not an observed TorchViz graph. Unknown internals remain unknown.

Tag optimizer-attributable nodes only where provenance can be established consistently, e.g. instrumentation plus source inspection. Otherwise report whole-graph counts and explicitly omit optimizer-only attribution. No inference about FLOPs, memory, or speed follows from node counts.

## 5. Visualization control
In addition to native fused and native unfused graphs, create a **collapsed-unfused** rendering from the same unfused topology. Group optimizer-internal regions at documented boundaries corresponding as closely as possible to fused interfaces. Preserve exposed parameter, gradient, state, and output dependencies, use neutral group labels, and disclose the grouping rule. Verify interface reachability is preserved. If an exact mapping is unavailable, label the control approximate rather than manufacture equivalence.

This control tests whether human benefits arise from visual grouping alone. Its rendered node count is not a change in the underlying autograd node count. Native graphs remain primary for the topology comparison. All figures use equal viewport and zoom tools; record layout-engine version and settings.

## 6. Numerical and structural validation
Before interpreting complexity differences, compare parameters and both moments after every step, outer losses, and outer gradients for every paired configuration. Proposed float64 criterion is componentwise |a−b| ≤ 1e−10 + 1e−7·max(|a|,|b|), together with finite values and reported maximum absolute/relative errors. Thresholds are fixed before outcome inspection; failure is not repaired by post-hoc tolerance inflation.

Independently check the outer directional derivative against centered finite differences of the entire unrolled outer objective. Use the normalized all-ones direction and a normalized alternating-sign direction; try step sizes 1e−4, 1e−5, 1e−6. Require error ≤ 1e−7 + 1e−4·max(|analytic|,|finite difference|) at two adjacent sizes. Near-zero moment/square-root behavior may create conditioning issues; report inconclusive checks and inspect them rather than silently dropping fixtures. Finite differences validate these directions, not all derivative components.

For the secondary diagnostic, require supported finite derivatives and paired scalar-probe agreement under the primary tolerance. Verify expected parameter reachability and repeat graph extraction from a fresh identical construction once to detect unintended retained history or unstable counting. Numerical mismatch invalidates matched-semantic causal interpretation; preserve and report the mismatch.

## 7. Proposed human-reader study
Recruit a modest target of 18 readers, aiming for nine with practical autograd/optimizer-implementation experience and nine with basic neural-network training experience but little graph-debugging experience. Record expertise with a short questionnaire and comprehension pretest rather than treating job titles as expertise. This is an exploratory estimation study, not a powered confirmatory claim.

Use six base stimuli: the two cases at K=1, 3, 10 using seed 11, selected in advance. Each reader sees six graphs, two per visualization condition, and never sees the same base stimulus in multiple conditions. Use a balanced assignment across readers so every stimulus appears equally often in each condition and, where possible, within each expertise stratum. Counterbalance presentation order and task-block order. Use neutral condition labels; readers and scorers are masked to implementation names/hypotheses, while acknowledging that visible structure may reveal grouping.

Give a common brief autograd primer, notation legend, Adam equations, and unrelated practice graph, but no source code. Ask two separately scored task families:
- **Dependency tracing:** identify whether an initial parameter affects the outer loss through the update, follow a specified state dependency across steps, and identify the relevant graph route or interface.
- **Adam-internal understanding:** locate moment updates, bias correction, and epsilon use, and explain their placement using graph evidence. Accept “not identifiable from this graph” as an accurate visibility judgment, but score successful localization of internals separately so hidden detail is not rewarded as full understanding.

Freeze concrete questions and answer keys after source/interface verification but before readers are tested. Score against known program dependencies, not superficial node-name matching. Collect question correctness, completion time (proposed four-minute cap per task family), explicit uncertainty, and a secondary 1–7 clarity rating. Have two masked scorers use a fixed rubric for open answers and report disagreements. Mark timeouts as incomplete; do not treat fast incorrect answers as improved efficiency.

## 8. Analysis and uncertainty
Report paired absolute and relative topology differences for each case, seed, and K, alongside full counts and scaling plots. Do not interpret repeated seeds with identical topology as independent replications. Separate annotation effects and collapsed rendering counts from raw topology. These fixtures support conclusions about these graphs, not all models or optimizer implementations.

Predeclare fused-versus-unfused as the primary reader contrast and fused-versus-collapsed-unfused as the abstraction-control contrast. Analyze dependency and internal-understanding accuracy separately. Use a logistic mixed model for question correctness, with condition, case, K, task family, and expertise as predictors, and participant and stimulus/question effects to account for repeated observations. With only six base stimuli, stimulus-level uncertainty is weakly estimated: also provide stimulus-wise contrasts and participant-cluster bootstrap intervals conditional on these stimuli. If models are unstable, use descriptive paired reader summaries and clustered intervals instead of overfitted significance claims. Report expertise interactions as exploratory.

Analyze completion times with correctness and timeout rates alongside them; report time-to-correct-completion descriptively if too few successful trials support a model. Provide effect sizes and 95% uncertainty intervals, rather than equating nonsignificance with equivalence. Discuss selection, learning, imperfect masking, and expertise imbalance. No-reader fallback reports complexity and explicitly labeled proxies/qualitative visibility judgments only, not demonstrated human interpretability.

## 9. Predefined interpretations and deliverables
- **Smaller visible graph and better dependency performance:** evidence for useful abstraction on these tasks; claim better internal understanding only if that endpoint also improves.
- **Smaller graph, unchanged/worse internal understanding:** reduced visible complexity with potential opacity, not unqualified simplification.
- **Collapsed-unfused matches fused reader performance:** consistent with grouping explaining the benefit; not evidence that computational fusion is necessary.
- **No topology difference:** fusion may operate below autograd visibility; no support for visible graph simplification. Wide reader intervals remain inconclusive.
- **Numerically inequivalent pair:** report diagnostic differences only; do not attribute them to semantics-preserving fusion.
- **Unsupported primary derivatives:** differentiable comparison infeasible. Unsupported secondary derivatives with a valid primary comparison limit higher-order conclusions only.
- **Reference-implementation branch:** describe evidence as a comparison of specified implementations, not a clean toggle-based causal fusion result.

Preserve a manifest, equations, fixture tensors, validation results, graph-extraction code, raw adjacency lists, DOT files, display settings, group mappings, reader materials, anonymized responses, exclusions, and analysis scripts. A future implementation should begin with one quadratic fixture at K=1, then expand only if the gate passes. The proposed models and unroll counts are modest, but actual CPU support, runtime, graph size, and recruitment feasibility are unknown. This design neither requires further retrieval to be complete nor claims that its implementation feasibility has already been established.
