# RepoBench Python `cross_file_first`: design-only प्रयोग योजना

**स्थिति:** केवल डिजाइन; कोई model inference, dataset evaluation या performance experiment नहीं चला है। अभी परिणाम अथवा विजेता बताना संभव नहीं है।

## 1. प्रश्न और तुलना का अर्थ
मुख्य प्रश्न: समान Python completion उदाहरणों और समान दिखाई देने वाले code/context पर `openai-community/gpt2` और `codellama/CodeLlama-7b-hf` base की exact-match performance में कितना अंतर है?

दोनों checkpoint revisions और tokenizer revisions execution से पहले pin होंगे। GPT-2 लगभग 124M और CodeLlama लगभग 7B parameters के checkpoint प्रस्तावित हैं; यह **इन मॉडल प्रणालियों की तुलना** है, model-size के अकेले causal प्रभाव की नहीं। Training data, code specialization, architecture और tokenizer भी बदलते हैं। कोई fine-tuning, instruction tuning, model-specific few-shot prompt या test-set prompt search नहीं करेंगे।

## 2. स्रोत स्थिति और अनिवार्य verification gates
स्थानीय `task.json` प्रश्न और design-only उद्देश्य की पुष्टि करता है, लेकिन benchmark specification नहीं देता। निम्न defaults **provisional** हैं:

| विषय | प्रस्तावित default | execution से पहले gate |
|---|---|---|
| Track | code-completion के लिए RepoBench-C | official paper/README से C, retrieval और combined track का अंतर, input तथा target unit सत्यापित करें |
| `cross_file_first` | दूसरे file के symbol के प्रथम उपयोग से जुड़ा completion उदाहरण | ‘प्रथम’ का scope, imported symbol की पहचान, file-level filtering और target semantics official schema/code से सत्यापित करें |
| Dataset | pinned release का आधिकारिक Python test split, केवल निर्दिष्ट setting | release/revision, split, schema, licenses, repository/example IDs और hashes रिकॉर्ड करें; मनमाना split test नाम से न बनाएँ |
| Target | next-line completion | official target एक line, multiple lines या दूसरी इकाई है, यह सत्यापित करें; preprocessing उसी अनुसार freeze करें |
| Evaluator | exact match primary, normalized edit similarity secondary | official normalization, target extraction, edit-distance implementation और aggregation की compatibility जाँचें |
| Models | ऊपर दिए base checkpoints | configs, context limits, special-token handling, licenses, weights/tokenizers की revisions और precision तय करें |

स्रोत मिलने पर इन gates का समाधान लिखित manifest में होगा। किसी consequential बदलाव—जैसे next-line के बजाय multiline target—को evaluation से पहले amendment में दर्ज करेंगे। Official evaluator भिन्न endpoint देता हो तो official scores अतिरिक्त रिपोर्ट करेंगे और primary exact-match endpoint की परिभाषा स्पष्ट रखेंगे; असंगत scores को official benchmark score नहीं कहेंगे। Gates unresolved हों तो डिजाइन तैयार माना जा सकता है, लेकिन benchmark-संगत execution का दावा नहीं होगा।

## 3. Cohort, eligibility और बजट
**Primary cohort:** सत्यापित split/setting के सभी eligible उदाहरण, या scores देखे बिना लिया गया reproducible probability sample। दोनों मॉडल ठीक उन्हीं IDs पर चलेंगे। Long-context की अनुपलब्धता primary cohort को छोटा नहीं करेगी।

Inclusion: Python, सही setting, उपलब्ध reference और prefix, वैध repository/example ID, तथा primary prompt निर्माण योग्य record। Empty target का व्यवहार official schema से तय होगा; उसे मनमाने ढंग से हटाएँगे नहीं। पहले से दर्ज exclusion reasons: corrupt/missing required fields, गलत setting/language, असंगत duplicate ID, स्पष्ट target leakage जिसे सुरक्षित रूप से हटाना संभव न हो, अथवा nonempty completion prefix के लिए भी shared context budget अपर्याप्त होना। Exclusion count और कारण प्रकाशित होंगे; inference output या किसी मॉडल की क्षमता देखकर exclusion नहीं। Exact duplicate records को freeze करने से पहले deduplicate करेंगे; cross-split overlap audit अलग दर्ज होगा।

**कम-बजट विकल्प:** fixed seed के साथ eligible examples का simple random sample, बिना replacement, जिसकी N उपलब्ध wall-time/token budget से पहले तय होगी। इससे example-weighted estimand बना रहता है। Repo coverage और counts बताएँगे। बहुत कम repository clusters मिलने पर sample बढ़ाएँगे, या uncertainty को exploratory कहेंगे; precision पाने का दावा नहीं करेंगे। Primary budget बचाने के लिए optional long-context condition पहले घटेगी। IDs, seed और sampling frame hash सुरक्षित रखें। Split contamination तथा pretraining में benchmark code की मौजूदगी को पूरी तरह नकारना संभव नहीं होगा।

## 4. Conditions और paired controls
1. **Primary shared-context:** दोनों models को byte-for-byte समान prompt text, समान cross-file snippets और क्रम। Model-specific tokenization तथा आवश्यक special tokens अलग हो सकते हैं और manifest में दर्ज होंगे।
2. **No-cross-file ablation:** primary prompt से केवल cross-file snippet block हटाएँ; उसका स्थानीय prefix बिल्कुल वही रखें। खाली जगह अधिक local code से न भरें। प्रत्येक मॉडल में paired exact-match अंतर cross-file context जोड़ने का contribution बताएगा। यह सूचना जोड़ने का कुल प्रभाव है; prompt length और positioning के प्रभाव से पूर्णतः अलग causal estimate नहीं।
3. **Optional CodeLlama long-context:** केवल CodeLlama को उसी source pool से अधिक context। यह अलग practical-capability condition है, बराबर-सूचना model comparison नहीं। उपलब्ध long-context IDs पर CodeLlama shared बनाम long paired अंतर और subset coverage दें; इन्हीं IDs के primary scores फिर से subset में रिपोर्ट करें। अतिरिक्त context न उपलब्ध होना primary से exclusion नहीं।

## 5. दोहराने योग्य context निर्माण और leakage नियंत्रण
Official context protocol मिलने पर उससे compatibility सर्वोपरि होगी। तब तक निम्न deterministic default:

- केवल record में अधिकृत local prefix और cross-file candidates लें; target-file suffix, reference target और अनधिकृत repository content न दें। Retrieval pipeline मुख्य तुलना में नहीं बदलेंगे। Benchmark द्वारा oracle/relevance-selected context दिए जाने पर उसे स्पष्ट oracle condition कहेंगे।
- Cross-file candidates का supplied order सुरक्षित रखें। Order undefined हो तो normalized relative path, start line और stable snippet ID के अनुसार sort करें। Exact duplicate candidate हटाएँ। Absolute machine paths न दिखाएँ।
- एक स्थिर plain-code template: cross-file blocks को relative-path Python comments से अलग करें, फिर local-file marker और local prefix; अंत ठीक completion boundary पर हो। कोई chat wrapper, FIM token, natural-language instruction या answer example नहीं।
- प्रस्तावित shared total budget **1,024 tokens प्रति tokenizer**, वास्तविक supported limits से पुष्टि के अधीन। Next-line default के लिए **128 generated tokens reserve**, अतः प्रत्येक tokenizer में special tokens सहित prompt अधिकतम **896 tokens**। दोनों tokenizers से पूरी rendered string की length दोबारा जाँची जाएगी; समान token count नहीं, समान text सुनिश्चित होगा।
- शुरुआती local allocation अधिकतम 448 tokens प्रति tokenizer: prefix की नवीनतम पूरी lines रखें; यदि एक line ही अधिक लंबी हो तो उसका सबसे लंबा Unicode-character suffix रखें जो दोनों budgets में फिट हो। Remaining budget में candidates को frozen order में जोड़ें; overflow पर candidate की leading complete lines लें और अधूरा block स्पष्ट marker से दर्शाएँ। जो block एक पूरी content line सहित नहीं फिट होता, उसे छोड़कर अगले candidate पर जाएँ। सभी wrappers बजट में शामिल हों। अंत में जगह बचे तो local prefix की पुरानी lines boundary की ओर निकटतम-first prepend करें। कोई target/reference देखकर relevance चयन नहीं। Final prompt hash और retained line ranges रिकॉर्ड हों।
- मूल local prefix को source से verbatim लें; indentation और line breaks अनावश्यक normalize न करें। Character-level fallback हो तो flag करें। बिना किसी retained cross-file content के records को primary cross-file cohort में include न करें; pre-inference exclusion और coverage दें।
- Optional long-context default: 4,096 total और वही 128 output reserve, config सत्यापन के अधीन। Shared prompt में retained content हटाए बिना original local allocation सुरक्षित रखें, candidates को उसी क्रम से extend/add करें, फिर बचे budget में पुराना local prefix जोड़ें। अलग prompt hash दर्ज हो।

**Leakage audit:** prompt builder को reference target field न दें। Candidate provenance, file ranges और completion position के आधार पर target span तथा post-target same-file code हटाएँ; reference का accidental concatenation रोकें। Cross-file file में वैध समान text अपने आप leakage नहीं है—सिर्फ string match से relevant code न हटाएँ। Audit tool prompt में reference match flag कर सकता है, लेकिन निर्णय provenance से होगा और evaluation से पहले freeze होगा। Training/test overlap तथा target-सचेत oracle selection का शेष risk अलग बताएं।

## 6. Generation, output extraction और failures
Primary तथा ablation में greedy decoding, sampling off, temperature अप्रासंगिक, beam search नहीं; batch padding, attention mask, EOS और tokenizer settings versioned रखें। एक ही frozen generation implementation जहाँ संभव हो। Prefix के लिए raw text ही दें; GPT-2 को chat शैली या CodeLlama को FIM advantage नहीं।

Next-line provisional rule: EOS, पहला decoded newline अथवा 128 generated-token cap पर stop; score केवल newline से पहले generated text पर, prompt echo शामिल नहीं। मॉडल शुरुआत में newline देता है तो prediction empty है—उसे ‘ठीक’ करने के लिए आगे न बढ़ें। UTF-8 decoding और `\n`/`\r\n` handling तय करें। Multiline official target होने पर compatible stopping और reserve pre-execution बदलें। लंबा reference होने पर उदाहरण न हटाएँ; cap hit दर्ज हो और truncated prediction सामान्य रूप से score हो। अलग tokenizers में 128 tokens का character budget अलग होने को सीमा मानें; cap-hit rates साथ रिपोर्ट करें।

Transient infrastructure failure के लिए अधिकतम एक identical retry; OOM होने पर वही model/precision रखते हुए batch size घटाना अनुमत, context या dtype बदलना नहीं। Persistent failure, crash या timeout को denominator में रखें: primary failure-inclusive EM=0 और edit similarity=0, साथ failure type/rate दें। EOS/empty output valid generation है, infrastructure failure नहीं। Invalid Python को स्वतः failure न मानें; completion target से सामान्य scoring करें। Successful-output-only scores केवल labelled diagnostic होंगे। Timeout और retry policy hardware pilot से freeze हों, scores देखकर नहीं।

## 7. Metrics और analysis
**Primary endpoint:** प्रति-example exact match और उसका mean। Provisional canonicalization केवल newline convention harmonization तथा target/prediction का एक terminal line delimiter हटाना; indentation, spaces और case सुरक्षित रखें। Official normalization अलग निकले तो official-compatible companion metric और इस अंतर का दस्तावेज दें।

**Secondary:** character-level Levenshtein normalized similarity `1 - d(pred, ref)/max(len(pred), len(ref))`; दोनों empty हों तो 1। इसे 0–100 scale पर दिखाया जा सकता है। Official evaluator अन्य formula/library देता हो तो compatibility जाँचकर नाम अलग रखें। Raw token perplexity प्राथमिक तुलना नहीं होगी, क्योंकि tokenizers अलग हैं।

Primary estimand example-weighted `EM(CodeLlama shared) - EM(GPT-2 shared)` है, percentage points में। सभी IDs paired रहेंगे। **95% repository-clustered paired bootstrap CI:** repository IDs को replacement के साथ resample करें; चुने cluster के सभी sampled उदाहरण और दोनों मॉडल outputs साथ लें; हर replicate में example-weighted means और difference दोबारा निकालें। Fixed seed और प्रस्तावित 10,000 cheap resamples; percentile interval दें। Cluster count तथा size distribution प्रकाशित हों; एक या बहुत कम clusters पर dependable population CI का दावा नहीं।

इसी तरह प्रत्येक मॉडल का shared-minus-no-cross-file अंतर, और इनके differences का exploratory comparison दें। Long-context का shared-minus/long अंतर केवल long-eligible paired subset पर। Edit similarity तथा subgroup/length analyses secondary/exploratory हैं; अनेक post-hoc comparisons को confirmatory significance नहीं कहेंगे। Repository-macro mean sensitivity diagnostic हो सकता है, example-weighted primary का प्रतिस्थापन नहीं।

## 8. Feasibility और QC
वर्तमान network/dataset/GPU के बिना manifest, prompt-builder pseudocode/spec, evaluator contracts और synthetic unit-test cases तैयार किए जा सकते हैं; execution अनिवार्य नहीं है। भविष्य में पहले offline cached assets, tokenizer lengths, one-record schema और hand-constructed scoring cases सत्यापित करें। Tests: दोनों context limits, reproducible hashes, target-field access निषेध, ablation में local text समान, CRLF/indentation/empty output, cap hit, failure accounting और paired IDs। ये benchmark result नहीं हैं।

**अनुमान, measured requirements नहीं:** GPT-2 FP32 weights लगभग 0.5 GB और 7B FP16 weights लगभग 14 GB decimal हो सकते हैं; KV cache, activations, framework और loading अतिरिक्त memory लेते हैं। छोटे batch के लिए लगभग 24 GB GPU एक संभावित starting point है, विशेषकर longer context पर guarantee नहीं। CPU पर 7B execution बहुत धीमा हो सकता है। Primary में दोनों के लिए समर्थित समान numeric precision, संभवतः FP32, अधिक साफ control है लेकिन महँगा; practical FP16/BF16 choice को दोनों के लिए verify और freeze करें। केवल बड़े model को quantize करना primary का silent बदलाव नहीं—अलग labelled resource-constrained condition होगा। Latency/throughput तभी तुलनीय होंगे जब hardware, batch, precision और implementation समान हों; quality analysis के लिए इन्हें अनिवार्य endpoint नहीं बनाएँगे।
