## 4. Test sampling, repetitions और scoring
- प्राथमिक sampling default: प्रत्येक task से अधिकतम 200 eligible clean items, या उपलब्ध सभी यदि कम हों। यदि किसी task में 50 से कम हों तो सभी लें, पर low precision prominently बताएं; छोटे task को सिर्फ इस कारण हटाएं नहीं। Fixed seed और frozen item list प्रयोग करें। Baselines और सभी optimized mappings समान items पर चलें।
- प्राथमिक decoding choice: temperature 0 और एक call प्रति item/arm, यदि API यह regime support करता हो। यह पूर्ण determinism की गारंटी नहीं है। यदि source-matched regime stochastic हो, या deployment target stochastic तय किया जाए, तो पहले से R=3 independent repetitions प्रति item/arm रखें। Repetitions को response accuracy के औसत के रूप में उपयोग करें, majority vote या best-of-R नहीं। Supported होने पर seed schedule साझा रखें; seeds से समान randomness की गारंटी न मानें।
- Answer extraction task-specific, deterministic और सभी arms के लिए समान होगी। Official scorer उपलब्ध हो तो version freeze करें; अन्यथा non-test examples से बनाए parser के unit tests freeze करें। Condition-blind scoring हो; test outputs देखकर parser सुधारना primary analysis में निषिद्ध हो।
- Parse failure, missing answer या truncated response को primary score 0 दें, भले कुछ पाठ उत्तर जैसा लगे। कोई answer-regeneration call नहीं। Failure rates arm/task के अनुसार अलग रिपोर्ट करें। Output cap को shared non-test pilot से पहले तय करें; कार्यकारी प्रारंभिक cap 2,048 output tokens है, context/API limits और pilot के आधार पर test से पहले संशोधन संभव है।
- Timeout/rate-limit/server error पर अधिकतम दो retries, उसी request configuration और frozen backoff policy के साथ। Final persistent API failure को accuracy में 0 देकर operational primary score निकालें। सभी arms में API-success वाले complete paired items की secondary sensitivity analysis दें; इसे selective availability की सीमा के साथ पढ़ें। यदि किसी arm में persistent API failures 1% से अधिक हों या model version बदल जाए, superiority निष्कर्ष रोकें, technical issue दर्ज करें और पहले से तय पूरी affected evaluation block को दोहराएं; favorable calls चुनकर न रखें।

## 5. Estimand और uncertainty
Task t, item i, arm a के लिए y_tia repetitions में correctness का औसत होगा। Multiple optimized candidates होने पर optimized y candidates पर भी औसत होगा। Baseline b के विरुद्ध item difference d_tib = y_ti,opt − y_ti,b लें।

Task effect: Δ_tb = mean_i(d_tib)। प्राथमिक effect: Δ_b = (1/T) Σ_t Δ_tb, अर्थात प्रत्येक clean task को बराबर weight। Percentage-point units में दोनों differences रिपोर्ट करें। Micro-average, absolute arm accuracies, candidate-wise और task-wise effects secondary होंगे। T, item counts और eligible/excluded/uncertain coverage साथ दें।

**ठोस uncertainty method:** 10,000-replicate paired, task-stratified cluster bootstrap। हर task के भीतर n_t item IDs replacement के साथ sample करें; प्रत्येक sampled item के सभी arms, candidates और repetitions साथ रखें। हर bootstrap draw में task means और फिर macro differences दोबारा निकालें। इससे pairing बनी रहेगी और repetitions को independent प्रश्न समझने की गलती नहीं होगी। यह finite-R item-averaged protocol की uncertainty estimate है; R=1 पर independent model-call variance अलग से पहचानी नहीं जा सकती। Task set fixed रखा जाएगा, इसलिए interval इन tasks पर item-distribution inference का है, unseen tasks पर generalization का नहीं। यदि पूरे finite eligible set को deterministic तरीके से evaluate किया हो, observed finite-set difference exact descriptive quantity है; bootstrap interval को broader item-population interpretation तक सीमित समझें।

**दोनों baselines पर superiority का पूर्वनिर्धारित नियम:** प्रत्येक Δ_b के bootstrap distribution का 2.5th percentile lower bound लें। ये दो one-sided 97.5% bounds Bonferroni द्वारा लगभग family-wise 95% simultaneous lower confidence देते हैं। केवल दोनों lower bounds > 0, clean provenance और technical validity checks पास होने पर कहें कि optimized instructions प्राथमिक macro metric पर दोनों baselines से बेहतर हैं। एक comparison पास हो तो दोनों पर superiority नहीं; न पास होना equivalence या baseline श्रेष्ठता का प्रमाण नहीं। Zero margin statistical superiority है, practical importance का दावा effect size देखकर अलग होगा। Discrete/tiny samples में bootstrap approximation और degenerate intervals की सीमा स्पष्ट करें।

**Task-wise multiplicity:** task results exploratory रहें। Confirmatory task-specific superiority के लिए 2T comparisons का पूरा परिवार पहले freeze करें और paired item-level sign-flip/randomization tests के one-sided p-values पर Holm correction, family-wise α=0.05, लागू करें; randomization interpretation के लिए paired exchangeability assumption स्पष्ट करें। आवश्यकता होने पर 100,000 fixed-seed draws और Monte Carlo p=(k+1)/(B+1) उपयोग करें। Unadjusted plots केवल descriptive होंगे; adjusted evidence के बिना किसी विशेष task पर superiority का दावा नहीं। Candidate-specific या additional-model claims इस primary family में स्वतः शामिल नहीं होंगे; exploratory label या अलग preregistered multiplicity family चाहिए।

## 6. Feasibility, खर्च और precision
अतिरिक्त sources, dataset और API access execution prerequisites हैं; इनके अभाव से यह design अमान्य नहीं होता। वर्तमान offline, dataset-विहीन environment में execution अपेक्षित नहीं है। Credentials मिलने पर छोटा non-test integration pilot करें: template equivalence, tokenizer/context fit, parser tests, retries/logging और prompt hashes जांचें। Pilot से instruction selection या test tuning न करें।

एक optimized mapping प्रति task पर nominal calls C = 3R Σ_t n_t। Task t में K_t candidates होने पर shared baselines के साथ C = R Σ_t n_t(K_t+2)। Pilot calls और retries अलग जोड़ें; दो retries के नियम में worst-case attempts nominal का तीन गुना तक हो सकते हैं।

Tokens: input = Σ_calls L_in(call), output = Σ_calls L_out(call), upper output bound लगभग C × output_cap; retries और pilot अलग। API price से cost = input_tokens × input_rate + output_tokens × output_rate, उचित प्रति-token units में। Longer optimized strings और longer generated reasoning से arms की actual cost अलग हो सकती है, भले settings समान हों।

Budget पहले उपलब्ध हो तो pilot की token estimates से R और n तय करें। सभी mappings का coverage बचाएं, stochastic target हो तो R=3 बनाए रखें और equal-per-task n को budget के अनुसार घटाएं; छोटे pools का बचा allocation deterministic water-filling से वितरित करें। यदि न्यूनतम उपयोगी coverage वहन न हो तो study को low-precision pilot label दें, power का दावा न करें। Test परिणाम देखकर sample बढ़ाने/रोकने की अनुमति नहीं; विस्तार चाहिए तो अलग preregistered phase हो।

Precision outcome-dependent है। मोटे planning approximation में macro SE ≈ sqrt[Σ_t s²(d_tb)/n_t]/T; d ∈ [−1,1] से pessimistic variance bound 1 मिलता है। इससे budget के लिए conservative scale मिल सकता है, guaranteed power नहीं। अधिक repetitions मुख्यतः stochastic noise घटाते हैं; कम unique items या सीमित tasks की कमी दूर नहीं करते। Non-test pilot के variance estimates यदि मिलें तो pre-test sensitivity calculations दें, किसी ज्ञात power का दावा नहीं।
