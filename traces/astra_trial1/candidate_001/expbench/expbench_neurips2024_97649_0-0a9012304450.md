## 2. Algorithms और implementation contract

**IPPO:** parameter-sharing recurrent decentralized policy; local-observation critic; PPO clipped objective, on-policy rollout updates।

**QMIX:** parameter-sharing recurrent agent Q-networks; monotonic centralized mixing network; replay, target networks और off-policy TD learning; decentralized greedy action selection। Mixer को environment का global state मिलेगा, actor/agent Q-networks को नहीं।

पहले JaxMARL revision pin करें और implementation audit में recurrence, parameter sharing, legal-action masks, critic/mixer inputs, losses, target updates, replay तथा termination/truncation handling जाँचें। उपलब्ध implementation इस contract से अलग हो तो adaptation तथा correctness tests दर्ज हों; बिना audit के उसे अपेक्षित variant न कहें।

जहाँ संभव हो shared agent-observation encoder और recurrent width समान रखें; प्रस्तावित default width 128 है। कुल parameter counts अलग से रिपोर्ट हों—QMIX mixer के कारण counts को कृत्रिम रूप से बराबर नहीं करेंगे। Feed-forward या अन्य architecture में बदलाव अंतिम benchmark से पहले दोनों की documented configurations में freeze हो।

**मुख्य limitation:** IPPO को local critic information और QMIX mixer को global state मिलने से तुलना algorithm family के साथ training-information access भी बदलती है। इसे शुद्ध PPO-versus-TD causal effect नहीं कहा जा सकता।

**IQL diagnostic:** संसाधन मिलने पर उसी recurrent agent-Q architecture, replay और optimizer pipeline से mixer हटाकर independent Q-learning चलाएँ। QMIX–IQL से centralized mixing/credit assignment का योगदान समझने में सहायता मिलेगी; IPPO–IQL अपेक्षाकृत समान local-information comparison देगा। यह सूचना के प्रभाव का पूर्ण isolation नहीं है, क्योंकि objectives और sample reuse भी बदलते हैं। IQL को primary comparator का विकल्प न बनाएँ; उपलब्ध होने पर पूरे suite तथा समान seed protocol पर अलग diagnostic allocation दें।

## 3. Scenario selection: performance-independent नियम

प्रस्तावित suite आकार **6 scenarios** है। Pinned SMAX registry से built-in scripted opponent और supported discrete legal actions वाले scenarios लें। Custom maps और runtime-generated scenarios बाहर रखें।

Selection code केवल scenario metadata उपयोग करे:
1. Total participating unit count से candidates को तीन rank-based size bins में बाँटें; ties scenario ID के lexical order से हल हों।
2. हर bin से दो अलग scenarios चुनें। प्राथमिकता एक homogeneous और एक heterogeneous unit composition की हो।
3. उपलब्ध जोड़ियों में पहले balanced और asymmetric ally/enemy counts दोनों का coverage अधिकतम करें, फिर उस bin के median total-unit count से दूरी न्यूनतम करें; अंतिम tie lexical IDs से तोड़ें।
4. किसी category के न होने पर दूसरी category से यही distance/tie rule अपनाएँ। छह से कम eligible maps होने पर सभी लें और suite छोटा होने का कारण लिखें।

Selected IDs, unit counts/types और opponent settings **किसी learning score को देखने से पहले** manifest में freeze हों। Size/composition difficulty के proxies हैं, प्रमाणित difficulty labels नहीं। यह छोटा suite coverage देता है, सभी SMAX tasks का representative probability sample नहीं।

## 4. Outcome और evaluation

### Primary score

इस अध्ययन की प्रस्तावित normalized success score परिभाषा:

**S = 100 × (स्पष्ट environment-declared wins / evaluation episodes).**

Win = 100; loss, draw या episode-limit timeout बिना स्पष्ट win = 0। यदि अंतिम permitted step पर environment स्पष्ट win घोषित करे, वह win गिना जाएगा। Simultaneous elimination को environment convention के अनुसार draw/non-win रखें; success flags का truth-table test करें। Evaluation crash को game loss न बनाएँ—वह missing/failed measurement है।

यह bounded **normalized success score** है, किसी मूल paper का प्रमाणित normalized-return formula नहीं। Raw return और draw/timeout rates secondary diagnostics होंगे। कोई observed-best-score normalization नहीं होगी।

### Evaluation protocol

- प्रति algorithm–scenario **10 स्वतंत्र training seeds**; paired seed IDs प्रयोग करें, पर दोनों algorithms की trajectories identical होने का दावा न करें।
- प्रत्येक checkpoint पर **256 evaluation episodes**, training से अलग fixed evaluation RNG bank। Scenario और seed ID के लिए bank दोनों algorithms में समान हो। Training seeds, tuning seeds और evaluation RNG namespaces अलग हों।
- Greedy evaluation: IPPO logits का argmax, QMIX legal Q-values का argmax; exploration बंद और recurrent states episode boundaries पर reset। Tie-breaking deterministic हो। यह greedy-policy deployment की तुलना है; stochastic-policy performance अलग प्रश्न होगा।
- Intermediate evaluation हर **2 million joint transitions**, तथा initialization और दोनों primary endpoints पर। Training में evaluation feedback का उपयोग नहीं होगा; early stopping या best-score checkpoint selection नहीं होगा।
- Evaluation episodes को training replicates न मानें।

## 5. Budgets, pilot और checkpoint rules

### प्रस्तावित defaults

- Sample endpoint: **20 million joint environment transitions** प्रति run। Parallel environments के एक vector step के transitions उनकी संख्या के बराबर होंगे; agent count से दोबारा multiply नहीं करेंगे। Agent-transitions भी supplementary log में हों।
- Wall-clock endpoint: **2 hours** प्रति run।
- Resources: एक dedicated, एक ही model का GPU; वही CPU allocation, memory limits, software stack और precision। यह भविष्य के benchmark का प्रस्ताव है, अभी उपलब्ध hardware का दावा नहीं। Mixed precision off रखना default है।

### Performance-independent feasibility pilot

Final hardware मिलने पर अलग engineering seeds से प्रत्येक algorithm–scenario configuration के **दो 5-minute** probes करें। Pilot में learning scores से budget, scenarios या hyperparameters नहीं चुनेंगे; केवल throughput, compile time, memory और evaluation/checkpoint overhead देखें। Pilot samples final analysis से बाहर होंगे।

एक benchmark run दोनों endpoints तक आगे बढ़ेगा: 2-hour snapshot सुरक्षित करने के बाद जरूरत हो तो sample endpoint तक चले, या sample endpoint पहले आए तो wall endpoint तक जारी रहे। Endpoints के पार का data दूसरे endpoint को बदल नहीं सकता। प्रस्तावित per-run engineering safety cap **6 hours** है।

यदि pilot conservative throughput पर 20 million steps को इस cap के भीतर infeasible बताए, सभी primary cells के लिए साझा transition budget 20, 10, 5, 2, 1 million की descending सूची में सबसे बड़ा feasible विकल्प चुनें। Conservative estimate = दोनों probes में कम throughput, plus observed compilation और आवश्यक evaluation/checkpoint overhead। Evaluation transition cadence तब sample budget का दसवाँ भाग हो। कोई विकल्प feasible न हो तो hardware/allocation revise करें; silently अलग per-algorithm budgets न दें। Pilot से actual runtime guarantee नहीं मिलती; बाद के cap hits censored होंगे।

### Wall endpoint का checkpoint

Training-only elapsed clock में evaluation को हटाकर ठीक 2-hour endpoint तय होगा; operational timing नीचे परिभाषित है। हर completed update boundary पर synchronized timestamp और immutable policy version दर्ज करें। Deadline से पहले समाप्त हुए **latest completed update** की policy चुनें, highest-scoring policy नहीं। Deadline पार करने वाला incomplete या बाद में पूर्ण update eligible नहीं होगा; retained previous version उपयोग करें। Endpoint से checkpoint lag तथा overshoot दर्ज हों। इस fixed snapshot को deadline के बाद evaluate किया जा सकता है; उससे training clock नहीं बढ़ेगी, evaluation cost अलग जुड़ेगी।

Sample endpoint पर aligned rollout/update boundaries को प्राथमिकता दें। यदि exact alignment संभव न हो, target तक उपलब्ध latest completed policy लें, exact transition count और lag report करें; algorithm-specific rounding छिपाएँ नहीं।

## 6. Timing और fair compute accounting

एक monotonic host timer तथा explicit JAX device synchronization (`block_until_ready` या equivalent) उपयोग करें। केवल asynchronous dispatch time को runtime नहीं कहें।

दो clocks दें:
1. **Training-system time, primary:** fresh run start से imports/initialization, cold JIT compilation, rollout, replay warm-up, replay operations, updates, routine logging/checkpointing और synchronization सभी शामिल; केवल evaluation blocks घटाएँ। Replay warm-up के transitions sample count में भी शामिल हों।
2. **Total elapsed time:** उपरोक्त plus scheduled और endpoint evaluation तथा उसकी compilation/synchronization। यह वास्तविक delivery cost बताएगा।

हर component का breakdown तथा post-compilation steady-state transitions/second भी दें। Compilation अलग दिखाना उसे primary training cost से हटाना नहीं है। Fresh process और isolated/disabled persistent compilation cache उपयोग करें; warm-cache result हो तो केवल अलग secondary condition में।

समान wall-clock primary comparison clock (1) पर होगा ताकि fixed-transition evaluation cadence से अधिक-throughput algorithm को अधिक evaluation cost के कारण अनुचित training penalty न मिले। Clock (2) की plots से इस लाभ की operational कीमत स्पष्ट होगी। समान **total elapsed** budget वाला निष्कर्ष केवल उस clock पर उपलब्ध eligible checkpoints से निकलेगा, training-clock endpoint को relabel नहीं करेंगे।

एक समय पर एक run, समान accelerator, CPU thread limits, precision और environment implementation रखें। Run order scenario और algorithm के भीतर randomized/interleaved हो। Parallel-env count, batch sizes, replay ratio, warm-up और update counts log करें। Equal compute का अर्थ समान hardware/time allowance है, समान update count या समान replay samples नहीं।

## 7. Hyperparameter selection और controls

Primary results equal-resource tuned configurations के हों; audited bundled configs अलग untuned reference बन सकते हैं, यदि अतिरिक्त budget उपलब्ध हो।

प्रस्तावित tuning allowance प्रति primary algorithm **12 accelerator-hours**, compilation और evaluation सहित, और अधिकतम **6 candidate configurations**। समान allocator, trial scheduler और tuning objective रखें। तीन size bins में metadata से सबसे पहले selected scenario को tuning subset बनाएँ; **3 अलग tuning seed IDs** उपयोग हों। Equal short trial quotas का कुल योग allowance से बाहर न जाए। Selection objective tuning-bank endpoint success का equal-scenario average हो; final-bank scores अदृश्य रहें। Ties में audited default से कम विचलन, फिर candidate ID चुनें। एक algorithm का unused budget दूसरे को न दें।

Candidate ranges implementation audit के बाद, tuning outcomes से पहले manifest में तय हों: IPPO के learning rate, clip और update epochs; QMIX के learning rate, target-update interval और replay/update ratio। Architecture और observation access tuning knobs न हों। Tuning subset अंतिम suite में हो सकता है, पर final seeds/evaluation banks disjoint होंगे; नए scenarios पर generalization का दावा नहीं होगा। Tuning hours final-run runtime से अलग तथा whole-study compute में शामिल हों।

दोनों के लिए environment revision, reward, opponent, episode limits, action masks, agent ordering, death-agent treatment और observation fields समान रखें। Recurrent replay की sequence/burn-in handling और IPPO rollout resets सही होने के tests रखें। Critical bug मिलने पर प्रभावित comparison cells एकसाथ दोबारा चलें; पहले के invalid results retained audit log में रहें।

## 8. Statistical analysis और unsuccessful runs

Primary contrasts, हर scenario और equal-weight suite average पर:
- समान transition endpoint पर score difference: IPPO minus QMIX, percentage points में।
- समान training-clock endpoint पर score difference।
- sample endpoint तक training-system और total elapsed time, तथा paired runtime ratio।

Training seed experimental unit होगा। Paired seed-ID bootstrap से **95% confidence intervals** दें; suite aggregate में fixed scenarios के भीतर seed pairs resample करें और फिर equal-weight mean लें। इससे चुने हुए suite पर uncertainty मापेंगे, सभी maps की population पर नहीं। Training-seed spread दिखाएँ; within-checkpoint evaluation uncertainty के लिए paired episode-bank resampling या binomial intervals supplementary हों। Rankings और multiple endpoints देखकर अकेला favourable p-value न चुनें; प्राथमिक interpretation effect sizes और intervals पर हो।

Secondary metrics: score-versus-time/steps curves, common-support normalized area under curve और **50 तथा 80 score** तक first observed time। Threshold times checkpoint cadence के कारण interval-censored हैं; पहला measured crossing sustained convergence नहीं है। Never-reaching runs right-censored हों, endpoint time को success time न लिखें।

Hardware interruption पर logged identical-seed restart permissible है; consumed compute अलग दर्ज हो। Algorithmic NaN, reproducible OOM या divergence को seed बदलकर न छिपाएँ। Failure rate और कारण दें। Last valid policy से endpoint score तभी दें जब पूर्वनिर्धारित ‘training stopped, frozen policy deployed’ rule लागू हो और label स्पष्ट हो; deployable policy न हो तो missing score और aggregate के 0–100 best/worst bounds दें। Complete-case परिणाम supplementary होंगे। Safety-cap exhaustion में time-to-budget censored होगा और exact achieved steps/score report होंगे।

## 9. Feasible checks और deliverables

बड़े runs से पहले: action-mask validity; win/draw/timeout truth table; terminal versus truncation bootstrapping; recurrent resets और sequence replay; loss/gradient finiteness; same-seed short-run reproducibility; checkpoint round trip; synchronized timer sanity; transition counters; evaluation RNG isolation; और दो budgets पर snapshot-selection test। ये future checks हैं, सफल होने का वर्तमान दावा नहीं।

अपेक्षित outputs:
1. **Setup table:** revision, hardware, scenario metadata, information access, parameters, configs, all budgets और timing definitions।
2. **Endpoint table:** scenario × algorithm के score/CI, training व total time, transitions, compilation/warm-up cost, failures और censored counts।
3. **Learning curves:** score versus joint transitions, training-system time और total elapsed time; seed traces/uncertainty bands सहित।
4. **Trade-off plot:** endpoint score versus compute cost; paired difference/ratio forest plots; threshold attainment/censoring table।
5. **Whole-study cost table:** tuning, pilot, final training, evaluation और reruns अलग-अलग।

उच्च equal-time score operational advantage का evidence होगा; उच्च equal-step score sample efficiency का; समान score तक कम uncensored time speed advantage का। एक method जल्दी सीखकर plateau करे और दूसरा देर से बेहतर score पाए तो स्पष्ट time-dependent trade-off रिपोर्ट होगा। Broad overlap, failures या scenario-specific reversals पर परिणाम inconclusive/heterogeneous कहेंगे—एक universal winner नहीं गढ़ेंगे।
