# अंतिम experiment design

यह **प्रस्तावित protocol** है, निष्पादित प्रयोग नहीं। नीचे की सभी संख्याएँ design choices हैं, empirical findings नहीं।

## 1. प्रश्न, rationale और hypotheses
TorchOpt optimizer implementation है; TorchViz visualization tool है। सही प्रश्न है: **semantically matched fused और unfused Adam को एक ही TorchViz pipeline से देखने पर क्या visible autograd graph छोटा होता है, और क्या उसे समझना आसान होता है?**

दो प्रकार की fusion अलग रखें:
- **Kernel fusion:** कई गणनाएँ एक execution kernel में होती हैं। इससे autograd nodes कम होना आवश्यक नहीं है।
- **Autograd-node fusion:** कई primitive operations एक custom autograd boundary में दिखाई देते हैं। Visible graph छोटा हो सकता है, लेकिन छिपी गणना समाप्त नहीं होती।

पूर्वनिर्धारित hypotheses:
- **H1, structural:** matched computation में fused condition के visible operation nodes और dependency edges कम होंगे। Depth और degree secondary descriptors होंगे; घटने की धारणा नहीं करेंगे।
- **H2, dependency tracing:** fused graph से parameter-to-loss dependencies पहचानने की accuracy बेहतर होगी अथवा accuracy noninferior रखते हुए समय कम लगेगा।
- **H3, mechanism understanding:** moments, bias correction और epsilon की भूमिका समझने पर अलग प्रभाव होगा। यह two-sided hypothesis है: abstraction मदद या नुकसान दोनों कर सकती है।

ये hypotheses केवल observable graph और निर्धारित tasks के लिए हैं; runtime speed या intrinsic computational complexity के दावे इस experiment के scope में नहीं हैं।

## 2. Source/API feasibility gate

1. Exact fused entry point, version/commit और fused operations की boundaries।
2. क्या fusion kernel-level, autograd-node-level या दोनों है; source locations सहित प्रमाण।
3. उसी version का matched unfused path/flag और उसका implementation।
4. CPU/dtype, out-of-place differentiable updates, state differentiation और double-backward support।
5. Adam equations: epsilon placement, bias correction, state-step convention तथा optional behaviors।

प्राथमिक pair same-version fused/unfused TorchOpt होगा। ऐसा pair न मिले तो explicit primitive-operation Adam reference बनाया जा सकता है, लेकिन source-equation matching और अतिरिक्त validation के बाद ही। इसे **reference-versus-fused comparison** कहा जाएगा, pure switch ablation नहीं। सामान्य `torch.optim.Adam` को बिना प्रमाण matched control न मानें।

Source या usable fused path उपलब्ध न होने पर TorchOpt-specific test feasible नहीं है। Synthetic custom-node illustration केवल methodology demonstration हो सकती है; उसे TorchOpt evidence न माना जाए।

## 3. छोटा concrete setup
प्रस्तावित baseline:
- CPU, float64, single-thread execution और deterministic settings, जहाँ दोनों paths supported हों। Environment, library versions और supported determinism flags दर्ज हों।
- Smooth MLP: `Linear(2,4) → tanh → Linear(4,1)`, biases सहित कुल 17 trainable scalars।
- Fixed training inputs: `(-1,-1), (-1,1), (1,-1), (1,1)`।
- Fixed outer inputs: `(-0.75,0.25), (0.25,-0.75), (0.5,0.75), (-0.5,-0.25)`। दोनों sets के targets `y = 0.4*x1 - 0.2*x2 + 0.1*x1*x2`। Inner और outer loss mean squared error होंगे।
- Initial weights और biases `Normal(0,0.1)` से एक recorded generator द्वारा; primary seed 17, sensitivity seeds 23 और 41। Exact initialized tensors archive होंगे, केवल seed नहीं।
- Unroll lengths `K = 1, 3, 5`; **primary structural case K=3**, बाकी scaling checks। प्रत्येक step में वही full training batch।

हर inner step में training gradient को `create_graph=True` से निकालें, functional Adam update करें और graph-connected state अगली step को दें। अंत में updated parameters पर outer loss `L_out` निकालें। Parameters या state detach न हों। प्रारंभिक model tensors अलग immutable leaves हों; दोनों conditions में cloned, equal-valued inputs और state उपयोग हों, पर graph identities साझा न हों।

## 4. Adam और state controls
प्रस्तावित settings: learning rate `0.01`, betas `(0.9, 0.999)`, epsilon `1e-8`, zero weight decay, AMSGrad off, maximize off, initial moments zero और initial step zero।

ये settings implementation को थोपने का प्रमाण नहीं हैं: feasible pair के exact equations source gate में तय होंगे। Reference में bias correction, square-root/epsilon ordering, first-step convention, tensor grouping, parameter order, state dtype और option defaults उसी तरह होंगे। यदि required semantics किसी path में उपलब्ध न हों, comparison रोकें या scope स्पष्ट रूप से बदलें।

Compiler, automatic mixed precision, gradient clipping तथा unrelated optimizer acceleration बंद रहें, जहाँ configurable हों। Implementation-mandated tensor packing या auxiliary bookkeeping को दर्ज करें; उसे चुपचाप fusion effect न कहें। हर K की run fresh state से शुरू हो।

## 5. Numerical और differentiation equivalence gate
Graph claims से पहले हर seed/K pair पर जाँच प्रस्तावित है:
- हर step पर gradients, updated parameters, first और second moments, step state और inner loss।
- अंतिम outer loss तथा `dL_out/dtheta_initial`।
- Floating values finite हों; NaN/Inf matching को pass न मानें। Discrete state exact match हो।

**पूर्वनिर्धारित tolerance rule:** componentwise `|a-b| ≤ atol + rtol*|reference|`; maximum absolute error और normalized relative error भी report हों। Supported dtype देखकर नीचे की row चुनें, observed disagreement देखकर नहीं:
- float64: primal/state `atol=1e-10, rtol=1e-8`; outer gradients `atol=1e-9, rtol=1e-6`।
- float32 fallback: primal/state `atol=1e-6, rtol=1e-4`; outer gradients `atol=1e-5, rtol=1e-3`।

ये छोटे smooth setup के लिए प्रस्तावित acceptance bounds हैं, universal guarantees नहीं। विफलता पर bug, semantics और numerical conditioning जाँची जाए; thresholds पीछे से ढीली करके उसी test को pass घोषित न करें। संशोधित protocol और नई confirmatory evaluation अलग दर्ज हों।

Independent check: float64 में outer loss की central finite differences से initial parameters के सभी 17 partial derivatives जाँचें; perturbation `h=1e-5*max(1,|theta_i|)`, साथ में `h/2` तथा `2h` stability check। Proposed agreement `atol=1e-7, rtol=1e-4` है। Step-size instability को inconclusive validation मानें। Float32-only होने पर finite differences अधिक सीमित होंगी; float64 primitive reference सहायक हो सकता है लेकिन fused higher-order correctness का पूर्ण विकल्प नहीं।

Optional secondary derivative endpoint: fixed normalized direction `v` के लिए Hessian-vector product और scalar `s = vᵀ(dL_out/dtheta_initial)` का graph। केवल support पुष्ट होने पर, float64 derivative agreement `atol=1e-8, rtol=1e-5` से अलग validate करें। इसे primary endpoint की अनिवार्य requirement न बनाएँ।

## 6. Graph extraction और counting
**Primary root:** final scalar outer loss का `grad_fn` graph, parameters की named mapping में initial leaves। यह differentiable inner-gradient और optimizer-update computation शामिल करेगा; केवल pre-update training-loss graph पर्याप्त नहीं है। Primary graph outer gradient निकालने से पहले capture करें। Secondary derivative graph अलग artifact हो।

एक pinned TorchViz version और Graphviz engine से दोनों conditions render हों। Proposed baseline `show_attrs=False`, `show_saved=False`; API support gate में confirm हो। Node labels, name mapping, orientation, fonts, spacing, image scale और zoom/pan सुविधाएँ समान हों। Pruning, manual node collapsing और condition-specific label cleanup न हो। Larger graph को छोटे fixed canvas में दबाकर unreadable न करें। Optional expanded-attribute views दोनों के लिए समान settings में अलग secondary artifacts हों।

Counting rules:
- Root से reachable autograd functions को object identity द्वारा एक बार गिनें। Initial-leaf accumulation nodes अलग category हों।
- हर non-null `next_functions` dependency slot को edge गिनें; repeated slots को multiedges के रूप में रखें। Unique node-pair edge count भी दें।
- Raw DOT artifact पर display nodes/edges अलग count हों: functions, leaf tensors, output tensor और optional saved/attribute nodes। इससे displayed graph और autograd topology मिलाए जा सकेंगे, लेकिन उन्हें एक count न समझें।
- Report: function-node count, leaf-node count, dependency-edge count, longest root-to-leaf path, maximum/median degree और operation-type histogram। Raw function class names सुरक्षित रखें; categories की mapping preregister हो।
- Custom fused node को एक visible operation मानें; उसके internals को शून्य computation न कहें। Primitive-equivalent internal count केवल source-supported expansion से, अलग table में, उपलब्ध होने पर।
- Whole-graph count primary हो। Optimizer-specific count तभी दें जब manual/source-assisted attribution reliable हो; ambiguous nodes अलग रखें, arithmetic subtraction से attribution न गढ़ें।

K=1 graph पर manual node/edge audit तथा TorchViz DOT बनाम autograd traversal reconciliation extraction का sanity check होगा। Negative control में एक ही unfused construction दो बार render कर topology समान होने की जाँच करें; image bytes identical होना आवश्यक नहीं।

हर paired case में absolute difference और fused/unfused ratio report हों। Counts **deterministic paired comparisons** हैं: seeds और K को independent statistical replicates बनाकर significance test न करें। Seeds topology robustness के checks हैं; topology अपरिवर्तित हो तो यह स्पष्ट लिखें।

## 7. अलग human interpretability assessment
### Stimuli और निष्पक्ष सहायता
Validated graphs से anonymous A/B conditions तैयार हों। Appearance से पूर्ण blinding संभव नहीं; participants को library identity और expected advantage न बताया जाए। दोनों conditions को समान संक्षिप्त Adam primer, notation legend तथा source-confirmed equations वाली reference sheet दें। Fused node की input/output meaning और primitive-node aliases उसी shared sheet में हों; केवल fused group को अतिरिक्त teaching न मिले।

दो outcomes अलग रहें:
1. **Dependency tracing:** किस initial parameter/state से outer loss तक dependency है, कौन-से updates cross-step जुड़े हैं, या highlighted paths का संबंध क्या है। केवल visible या shared legend से resolvable tasks score हों।
2. **Internal-mechanism understanding:** first/second moments, bias correction, epsilon और state carryover समझाना; shared reference का उपयोग अनुमत हो। यह *graph plus equal documentation* की understanding है, unaided graph readability नहीं।

यदि कोई internal detail fused node में नहीं दिखती, उसके location को graph में pinpoint करने पर गलत अंक न दें। ऐसे प्रश्न में सही उत्तर “यह graph में exposed नहीं है” हो सकता है, और information-visibility score अलग report हो। Mechanism explanations के लिए fixed rubric और condition-blind scorers हों; दो scorers का agreement भी दें।

### Participants और counterbalancing
प्रस्तावित pilot 6 participants से task ambiguity और floor/ceiling effects जाँचें; pilot confirmatory analysis में न जोड़ा जाए। प्रारंभिक confirmatory target **40 completers**, लगभग 46 recruitment slots, paired design है। यह paired standardized effect लगभग 0.45 के लिए 80% power के सामान्य approximation के आसपास है; binary accuracy, item dependence और multiple outcomes के लिए power की guarantee नहीं। Pilot से variance/accuracy estimates लेकर mixed-model simulation द्वारा final sample size freeze करें, confirmatory outcomes देखने से पहले। उपलब्ध संख्या कम हो तो precision-limited study कहें।

Participants को basic autodiff knowledge आवश्यक हो; prior optimizer expertise दर्ज करें। Proposed session: common practice, फिर दो छह-question blocks—हर condition में तीन tracing और तीन mechanism tasks। Items K=1,3,5 और matched question forms से balance हों। AB/BA order, condition-to-item assignment तथा graph-length assignment Latin-square/counterbalanced schedule से बाँटें। Exact same question दोनों conditions में दोहराकर learning advantage न दें। Proposed per-item cap 180 seconds; timeout incorrect/uncompleted तथा time right-censored दर्ज हो।

### Analysis और uncertainty
Tracing और mechanism के लिए accuracy तथा time अलग report हों। Accuracy को participant/item effects वाले mixed model से; time को censored log-time model से analyze करें। Correct-response-only time secondary हो, क्योंकि उस subset में selection bias संभव है। Condition के साथ order, K और expertise का prespecified adjustment हो; participant और item effects, जहाँ estimable हों, शामिल हों। Report absolute accuracy differences, time ratios और 95% confidence intervals; participant-level paired bootstrap sensitivity check उपयोगी होगा। Items या screenshots को स्वतंत्र participants न मानें।

Confirmatory accuracy comparisons की multiplicity दोनों outcome families में Holm adjustment से नियंत्रित हो; time-based superiority claims accuracy gate के बाद hierarchical हों। Proposed meaningful bounds: accuracy noninferiority −5 percentage points और time noninferiority ratio 1.10। श्रेष्ठता का नियम: accuracy improvement का adjusted interval शून्य से ऊपर और time noninferior, **या** accuracy noninferior और time-ratio upper bound 0.90 से नीचे। Sample छोटा होने से bounds पार न हों तो inconclusive कहें, no-effect नहीं।

## 8. निर्णय नियम और fallback
- **केवल visible graph छोटा:** equivalence pass हो और primary case में function nodes तथा edges दोनों कम हों। एक metric घटे, दूसरा न घटे तो mixed structural result कहें। सभी K पर direction consistent हो तभी cross-length claim करें। इसे मानव interpretability या hidden computation reduction का प्रमाण न मानें।
- **Dependency tracing बेहतर:** human tracing outcome ऊपर का gated superiority rule पूरा करे। Mechanism outcome अलग report हो।
- **व्यापक interpretability बेहतर:** tracing बेहतर हो और mechanism accuracy/time prespecified margins पर noninferior हों। Mechanism भी superiority rule पूरा करे तो दोनों dimensions में improvement कहें। किसी dimension में harm होने पर trade-off स्पष्ट करें।
- **Inconclusive:** source pairing अपुष्ट हो, primary equivalence fail हो, graph extraction ambiguous हो, अथवा human intervals useful benefit और harm दोनों की अनुमति दें।
- **Kernel fusion, nodes समान:** इस setup में visible graph reduction का समर्थन नहीं; kernel fusion को अप्रभावी या slow न कहें।
- **CPU unsupported:** वर्तमान supplied environment में fused test feasible नहीं। Future GPU study अलग amendment और matched device controls माँगेगी; CPU primitive demonstration उसका substitute नहीं।
- **float64 unsupported, float32 supported:** घोषित float32 gate लागू करें और independent numerical assurance की सीमा report करें।
- **Differentiable optimizer/double backward unsupported:** required primary unroll gradients नहीं बनते तो primary research question इस implementation से test नहीं हो सकता। Static update graph या first-order-only visualization का सीमित वर्णन संभव है, equivalent meta-gradient graph का दावा नहीं। Optional higher-order endpoint अकेले unsupported हो तो केवल वही हटे।
- **Participants unavailable:** deterministic structural results और expert rubric/pilot की सीमित qualitative observations तक निष्कर्ष रखें; human interpretability बेहतर होने का दावा न करें।
