## 4. Представление данных и общие параметры обучения
Предлагаемый единый текстовый шаблон для Base-модели, без chat-template и few-shot демонстраций:

```
Solve the following math problem. Show your reasoning and put your final answer in \\boxed{...}.

Problem:
{question}

Solution:
```

При обучении после него следует исходное решение и EOS. Для программных решений сохраняется исходный целевой код, даже если он не заканчивается boxed-ответом; это явно документированная неоднородность MathInstruct, общая для обеих процедур.

| Параметр | Предлагаемое значение |
|---|---|
| Базовые веса / матричные операции | BF16, без квантования |
| Максимальная длина train-последовательности | 4 096 токенов, если ревизия модели поддерживает её |
| Эффективный batch | 65 536 непустых токенов, с детерминированным остаточным batch |
| Microbatch | первоначально 1 последовательность на GPU; accumulation по схеме параллелизма |
| Основная экспозиция | один полный проход по подготовленному train-потоку |
| Scheduler | линейный warmup 3% шагов, затем cosine до 10% стартового LR |
| Adam-параметры | β1=0,9; β2=0,999; ε=10⁻⁸ |
| Weight decay | 0,01 для матриц; 0 для norm/bias |
| Gradient clipping | глобальная норма обновляемых градиентов 1,0 |
| Экономия активаций | одинаковый activation checkpointing и совместимый attention backend |

Loss вычислять только на токенах решения, включая EOS; prompt и padding маскировать. При накоплении градиентов нормировать по общему числу целевых токенов, а не усреднять средние loss микробатчей с разной длиной.

**Truncation/packing:** до разбиения исключить примеры, в которых полный prompt и решение не помещаются в 4 096 токенов; не отрезать конец решения. Удаления по длине показать отдельно. Предпочтителен packing с EOS, отдельной attention-маской между примерами и сбросом positions. Поддержку такого packing проверить; если она отсутствует, использовать padding без packing для обоих методов. Не разрешать скрытое внимание между соседними задачами.

В каждой паре seed совпадают порядок данных, разбиение batch и число непустых **и целевых** токенов. Scheduler привязан к общим optimizer steps. Равные токены не означают равные FLOPs или время.

## 5. Конкретизация методов

### LoRA + AdamW
- Базовые веса заморожены, неквантованы, BF16.
- LoRA на `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj` всех transformer layers.
- Четыре кандидата: **rank ∈ {16, 32} × LR ∈ {1×10⁻⁴, 3×10⁻⁴}**.
- scaling α/r=2, то есть α=2r; dropout=0; bias не обучать; embeddings и output head не адаптировать.
- Стандартная начальная нулевая добавка: одна факторная матрица случайная, другая нулевая. AdamW обновляет только адаптеры; FP32 optimizer states.
- Для оценки использовать зафиксированную процедуру unmerged adapters в BF16; не менять путь вычислений между seed.

Это именно LoRA, **не QLoRA**. Число обновляемых параметров не уравнивается с BAdam: сравниваются практические процедуры адаптации.

### Предлагаемый блочный BAdam
Это **операционное предложение, а не подтверждённая спецификация найденной библиотеки**. До запуска необходимо установить источник BAdam и проверить, что реализация поддерживает указанный режим. Если нет, согласовать и перерегистрировать поддерживаемый режим до просмотра test-результатов, а не выдавать собственную модификацию за эталонный BAdam.

- Разделить параметры на непересекающиеся блоки: один transformer layer — один блок; embeddings — отдельный блок; output head вместе с final norm — отдельный блок. Для типичной конфигурации из 80 слоёв получится около 82 блоков. Число слоёв и tied weights проверить по config; общие веса должны принадлежать только одному блоку.
- Обновлять один блок за раз; все остальные заморозить, включая weight decay. Сохранять точный градиент активного блока через последующие замороженные вычисления — не делать detach, разрывающий нужный путь градиента.
- Четыре кандидата: **LR ∈ {5×10⁻⁶, 2×10⁻⁵} × период переключения K ∈ {10, 50} optimizer steps**.
- Порядок блоков — случайная перестановка без повторения внутри цикла, новая перестановка каждый цикл. Отдельный воспроизводимый RNG от seed. Переключать блок только после полного шага с accumulation, не между микробатчами.
- Активные параметры обновляются AdamW с общими β, ε и weight decay. Глобальный LR schedule общий по времени обучения; счётчик bias correction для параметра учитывает его собственные обновления.
- Предложенная политика состояний: **сохранять** FP32 first/second moments между посещениями блока; выгружать неактивные состояния в CPU RAM; при повторном входе восстанавливать их и локальные step counters. Не обновлять моменты неактивных параметров нулевыми градиентами. Если используются FP32 master weights, сохранять и их. Сброс состояний при переключении — другая процедура и не допускается незаметно.

До фиксации поиска рассчитать число посещений каждого блока на одном проходе. Если кандидат K=50 не обеспечивает хотя бы одного полного цикла, заменить его на наибольший K из {20, 10, 5}, обеспечивающий цикл; при необходимости аналогично уменьшить K=10. Это правило зависит только от числа шагов, не от качества. Документировать фактическую неравномерность посещений и неполный последний цикл. Если даже K=1 не даёт полного цикла, общий горизонт обоих методов пересогласовать до запуска.

## 6. Настройка, токены и checkpoint
Использовать один отдельный tuning seed, не входящий в пять финальных. Для каждого метода — четыре заранее заданных кандидата, одинаковый фиксированный горизонт токенов **T_search**, по возможности полный train-проход. Validation — teacher-forced token-weighted loss по целевым токенам; отдельно логировать текстовую и программную части. Это стабильный критерий для короткого поиска, хотя он не гарантирует оптимальной benchmark accuracy; ограничение указать в выводах.

**Равный бюджет настройки:** выделить каждому методу одинаковый потолок B_search GPU-часов и разделить его на четыре равные квоты. Будущее короткое профилирование даст консервативную скорость q для каждого кандидата. До поиска выбрать общий T_search, который все кандидаты смогут завершить в своих квотах с резервом на validation/checkpoints. Неиспользованную квоту не превращать в дополнительные trials более быстрого метода. Таким образом равны доступный бюджет, число кандидатов и токены на кандидата; фактически потраченные GPU-часы могут различаться и должны быть показаны. Если полный проход не помещается, общий сокращённый горизонт фиксируется для всех; он должен оставлять полноценный цикл BAdam, иначе поиск по данному бюджету не реализуем.

Выбирать кандидата по **конечному** validation loss при T_search. При равенстве в пределах 10⁻⁴ nats/token использовать заранее фиксированный порядок кандидатов. Никакого подбора по GSM8K/MATH.

После выбора — пять новых запусков каждого метода с seed **{11, 23, 37, 53, 71}**, каждый на полном общем train-проходе. В основном сравнении оценивать **только конечный checkpoint при одинаковом числе токенов**, не лучший промежуточный checkpoint своего метода. Промежуточные snapshots служат для диагностики и восстановления; досрочная остановка по validation запрещена. При сбое восстанавливать модель, optimizer, scheduler, RNG, позицию данных и активный блок. Численная дивергенция — результат стабильности процедуры, а не повод тихо менять LR или удалять seed.

## 7. Zero-shot оценка
Оценить исходную Base-модель и десять финальных checkpoints одним и тем же кодом и prompt из раздела 4. Prompt содержит только текущую задачу и общую инструкцию, без примеров решений. Разрешено пошаговое рассуждение, но не внешние инструменты, исполнение кода, self-consistency или повторные попытки.

- Greedy decoding, `do_sample=false`, до **4 096 новых токенов**, остановка по EOS. Проверить предел контекста; при его превышении сокращать доступный лимит вывода по единому правилу, не обрезая условие. Таких случаев и их распределение показать отдельно.
- Извлекать последний синтаксически корректный `\\boxed{...}` сбалансированным парсером. Если его нет, разрешить только явно заданный fallback: последняя строка, начинающаяся с `Final answer:`. Не брать произвольное последнее число из рассуждения.
- GSM8K: эталон из официального финального поля; сравнение численного значения после удаления разрешённых разделителей/единиц, через точное рациональное представление, где возможно; не вводить свободный допуск округления.
- MATH: сначала нормализация LaTeX и точное совпадение, затем зафиксированный безопасный symbolic checker для поддерживаемых выражений. Учитывать тип ответа, множества, интервалы, знаки и ограничения; не считать численное совпадение в одной точке доказательством эквивалентности. Таймаут или неподдержанный случай без совпадения — ошибка основного автоматического score.
- Код в генерации не исполнять. Если в нём есть явный корректный финальный ответ по общему формату, оценить его; иначе ошибка. Это сознательная оценка без инструментов, в том числе для модели, обучавшейся на программных решениях.
- Нераспознанный или незавершённый ответ засчитывать как неверный, а не исключать из знаменателя.

До оценки методов проверить оценщик на искусственных примерах чисел, дробей, вложенных boxes, множеств и неэквивалентных выражений. После оценки провести одинаковый для методов слепой аудит случайной выборки parser failures и спорных ответов. Любая исправленная версия оценщика применяется ко всем моделям; показать исходный и исправленный scores, не делать выборочные ручные прибавки.

## 8. Статистический анализ
Сохранить бинарные результаты на уровне **метод × seed × задача** и исходные генерации.

Основной интервал: 10 000 повторов парного bootstrap по двум пересекающимся измерениям:
1. выбрать с возвращением пять **пар seed**;
2. независимо выбрать с возвращением задачи внутри GSM8K и внутри MATH;
3. один и тот же выбранный набор задач каждого benchmark использовать для **всех выбранных seed и обоих методов**;
4. вычислить среднюю парную разность и равновесовой агрегат.

Взять 2,5-й и 97,5-й процентили. Нельзя независимо ресемплировать задачи для каждого seed: это разрушает общую зависимость от трудности задач. Если аудит выделит тестовые семейства почти дубликатов, дополнительно провести кластерный bootstrap по этим семействам, сохраняя веса задач.

Представить также пять парных Δ, их стандартное отклонение, диапазон, интервалы только по задачам условно на seed и только по seed на фиксированных тестах. Bootstrap-интервал трактовать как приближённый: при пяти seed хвосты распределения вариативности обучения оцениваются ненадёжно, а настройка проведена только один раз. Он не включает неопределённость альтернативного поиска гиперпараметров и не делает два выбранных benchmark случайной выборкой всех математических задач.

Сокращённый вариант — три пары seed, с явной маркировкой ограниченной точности; один seed пригоден только для разведочной оценки. Не обещать выявление эффекта 1 п.п. без данных о дисперсии и межметодной согласованности. Увеличивать число seed по заранее согласованному бюджету, а не только после незначимого результата.

## 9. Реализуемость и память
В текущей среде эксперимент невыполним: нет GPU, весов и данных, сеть отключена. Нужна внешняя инфраструктура.

Оценки порядка величин, **десятичные GB**, без активаций, временных буферов и запаса:
- 70 млрд параметров × 2 байта BF16 ≈ **140 GB** только базовых весов.
- Обычное полное Adam-обучение: BF16 веса и градиенты плюс два FP32 момента ≈ **840 GB**; с отдельной FP32 master-копией ≈ **1 120 GB**.
- Предложенный BAdam: активный слой примерно 0,8–1,2 млрд параметров; его градиенты ≈ 1,6–2,4 GB, моменты ≈ 6,4–9,6 GB, master-копия при наличии ≈ 3,2–4,8 GB. На GPU нужны базовые веса, активные состояния и активации; детали зависят от sharding. При сохранении моментов для всех блоков CPU-хранилище постепенно достигает примерно **560 GB**, либо **840 GB** с полными master weights, сверх прочих нужд процесса.
- Для типичных размеров Llama 3-70B LoRA на всех семи линейных проекциях даёт приблизительно **0,21 млрд** параметров при r=16 и **0,41 млрд** при r=32. Их веса/градиенты/моменты/master-копии при 16 байтах на параметр требуют порядка **3,3–6,6 GB**, дополнительно к базовым весам и активациям. Точный подсчёт сделать по config.

**Условный внешний сценарий:** один узел 8×80-GB GPU с быстрым GPU interconnect, примерно 1,5–2 TB CPU RAM и быстрым локальным хранилищем. Необходимы sharding базовых весов и проверенная совместимость с динамически активными блоками; 140 GB не помещаются на одной 80-GB карте даже для LoRA. Этот сценарий — кандидат для профилирования, а не гарантия достаточной памяти или скорости. CPU offload BAdam может стать узким местом; измерять стоимость каждого переключения, а не только установившиеся шаги. Для хранения десяти полных BF16 checkpoints потребуется около 1,4 TB, плюс snapshots и состояния для восстановления; предусмотреть несколько TB свободного диска.
