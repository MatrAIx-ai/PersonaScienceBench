## 5. 确定性的上下文构建

### 5.1 输入格式
采用普通代码续写，不使用 FIM。默认跨文件片段放在本文之前，转换成 Python 注释行：

```text
# Cross-file context
# File: relative/path.py
# <一行跨文件代码>
...
# Current-file prefix
<原始本文后缀>
```

跨文件各行仅在行首添加固定 `# `，本文不注释、不去缩进。仅本文条件保留相同两段标题，跨文件区域为空。相对路径仅来自允许的输入字段；禁止从目标元数据构造提示。两模型看到相同 Unicode 文本，但使用各自 tokenizer 和必要的模型特殊 token。

冻结 UTF-8 解码与换行转换规则，默认将 CRLF/CR 转为 LF，保留其他空白。前缀截止位置必须经 schema 核验，不能自行补上或删去会改变续写位置的换行。

### 5.2 同时满足两种 tokenizer 的共同预算
- 从配置核实两个上下文上限，记为 `L_G`、`L_C`；主实验使用 `L = min(1024, L_G, L_C)`。
- 默认每模型预留 `R = 128` 个生成 token，提示上限为 `B = L - R`。若配置不能支持该设置，在执行前修订，而不是运行中临时变更。
- 对每个候选**完整提示**分别用实际推理 tokenizer 编码，计入实际 BOS 等特殊 token。要求两者长度都不超过 B；不能分别截断后称其输入相同，也不能靠片段 token 数相加忽略边界效应。
- `128` 是计算与长度安全上限，不代表两个 tokenizer 覆盖相同字符量；记录输出 token 数、字符数及触顶率，以识别此限制。

### 5.3 确定性裁剪算法
1. 固定跨文件片段顺序：优先保留数据给定顺序；若原格式没有顺序，以相对路径及片段起始位置排序，不按测试答案重排。
2. 构造空跨文件区，选择本文前缀的一个公共后缀，使两个 tokenizer 对完整提示的长度都不超过 `floor(B/2)`。从完整本文开始，先逐条删除最早的完整行；若只剩一条行仍过长，从左侧逐 Unicode 字符删除，保留靠近目标的后缀。每次重新编码验证，不假设 token 数严格单调。
3. 固定这个本文片段，将所有可用跨文件片段按固定格式加入。若任一 tokenizer 超出 B，从跨文件区的末尾逐行删除；遇到片段被删空时同时移除对应文件标题，直至完整提示满足两模型约束。剩余本文不再扩展。
4. 空区框架若连半预算都无法容纳，视为配置校验错误，在任何评测前修订；不要按样本临时改格式。
5. 仅本文条件删除跨文件有效载荷，保留第 2 步的本文片段及固定框架。禁止用释放的预算填充本文，否则对照同时改变了两类信息。

该 50% 本文保留规则是透明、可复现的默认折中，不声称最优。记录两种 tokenizer 下的提示长度、保留本文字符比例、跨文件保留行数/片段数及完全裁空比例。

**跨文件完全裁空时仍进入全部主指标和收益分析，不删样本。** 该样本两条件输入相同，确定性生成原则上应一致；可以复用同一模型的同文本输出，但保持两条件记录。额外报告“至少保留一行跨文件内容”的描述性子集结果，不能用它替代总体结论。

### 5.4 原生上下文补充
对模型 m 使用 `B_m = L_m - 128`，按同样半预算本文、剩余跨文件的算法，只检查自身 tokenizer。本文对照依然固定对应本文片段。若资源不足以使用原生上限，则跳过该补充，或预先另定并命名为“扩展预算条件”，不能把任意资源上限称为原生上限。这组结果包含上下文能力与输入差异，独立于共同文本主结论。

## 6. 生成、输出提取与失败处理

- `do_sample=False`，单束贪心解码，`max_new_tokens=128`，禁用框架隐式输入截断；固定种子并尽可能开启确定性计算。
- 每步对新生成 token 解码，使用不清理空白的固定解码方式。在首次生成 LF、EOS 或达到 128 token 时停止。若一个 token 解出换行及其后字符，仅保留首个 LF 之前的文本。
- 预测默认是新生成文本的第一行，不去前导/尾随空格；若第一字符是换行，预测为空。若核实前缀已包含目标行的部分缩进，则冻结相应目标对齐规则，例如将已给定的行前缀拼回预测再按完整行评价；不能在看模型输出后选择更有利的规则。
- EOS 或 token 上限前未生成换行时，将已有文本作为该行预测，并分别标记 `eos_without_newline` 或 `length_cap`；这不是基础设施失败，不自动判零，仍按指标评分。
- OOM、加载错误、异常中断等生成失败不能被当作正常空行。先以完全相同语义配置、batch size 1 重试并记录；不以更少上下文或不同精度“补救”个别模型。
- 仍失败的记录保留在分母：EM=0，ES=0，单独报告失败率。另可报告两模型均成功样本的敏感性结果，但不得替代主分析。若出现系统性失败，应判定评测实施不可用并修复/重新冻结，而不是把大面积基础设施故障宣称为模型能力。

## 7. 泄漏与污染防范

- 目标字段仅进入评分，不进入提示、裁剪、排序或样本抽选。本文严格截止于预测点，不包含目标及其后续代码。
- 跨文件使用该任务允许的输入；清除错误混入的目标文件后续内容。合法依赖文件中自然出现的相似代码不因与目标相似而事后删除，但记录明显重复风险及输入来源。
- 所有协议调试使用非测试开发样本或人工构造例子；没有开发集时使用人工例子，不用测试分数优化格式、预算或指标。
- 保存输入与制品 hash、样本清单和过滤日志；核对重复记录并按官方规则处理，不根据结果选择去重策略。
- 公开仓库可能进入模型训练集。记录可取得的数据时间与模型资料，但即使检查不到重叠也不能证明无污染。因此结果不能直接证明对全新私有仓库的泛化能力。

## 8. 评价定义与冻结流程

**EM 是拟定主指标、Edit Similarity 是次指标，这是设计选择，并非已核实的官方要求。**

默认定义：
- 参考目标去掉其行终止符，除此之外保留空白；预测使用第 6 节提取规则。
- `EM_i = 1[pred_i == target_i]`，样本平均后乘 100，差值以百分点报告。
- `ES_i = 100 × (1 − Lev(pred_i,target_i) / max(len(pred_i),len(target_i)))`，按 Unicode 字符计算；两者都为空时 ES=100。生成失败覆盖为空字符串的正常评分规则，固定记零。

执行前与官方评价器核验：冻结其 revision、依赖、规范化及测试例，包括缩进差异、尾随空白、空行、换行和截断。如果官方定义不同，在生成前将官方指标作为另行明确的正式定义并保存修订记录；默认严格指标可作为补充保留。若官方根本不用 EM/ES，可仍用它们回答本设计问题，但同时报告官方指标，不能声称 EM/ES 是官方分数。所有模型使用同一冻结评价器，保存原始输出以便审计。

## 9. 配对分析、样本量与精度规划

### 主分析
对每个指标，报告共同预算＋跨文件条件中两个模型的样本平均分及：

`Δ = score(CodeLlama) − score(GPT-2)`。

以仓库为重采样单位做 **10,000 次配对 bootstrap**，固定分析随机种子，例如 20260929：每次有放回抽取与原来相同数量的仓库，携带被抽仓库的全部样本及所有模型/条件结果；重复仓库按抽中次数计权。每次重算样本加权分数差，以 2.5% 和 97.5% 分位数给出 95% 区间。

该方法保持样本内配对并承认仓库内相关性。若仓库很少或单仓库占比很高，应报告区间不稳定；单仓库无法提供有意义的跨仓库 bootstrap 区间，不能伪造。可补充仓库宏平均，明确它与样本加权指标的目标不同。官方聚合若不同，另外按官方规则报告。

### 次分析
对每个模型 m，定义同样本跨文件收益：

`G_m = mean(score_m,cross − score_m,local)`。

报告两个 `G_m` 及模型间收益差 `G_CodeLlama − G_GPT2`，用同一仓库配对重采样计算区间。原生上下文分析单列，长度分层、裁空子集等标记为次要或探索性分析；不通过多个子集挑选结论，也不把多个名义 95% 区间当作同时覆盖保证。

### 全量优先及资源受限方案
- 先以完整合格测试集为目标，不虚构样本量或统计功效。
- 若预计成本超预算，先用公开固定的随机种子均匀抽取仓库，再纳入这些仓库全部合格样本，尽量保留仓库数并保持 cluster bootstrap 的抽样单位一致。在不看测试输出的前提下冻结仓库清单、样本清单与预算，所有条件共用同一清单。
- 在开发数据的小型可行性评测上估计配对差的仓库间变异与仓库大小分布，以重采样评估不同仓库数下区间半宽；研究者预先指定希望达到的百分点精度。若没有可用先验/开发数据，则只做假设范围的精度敏感性规划，最终如实报告实际区间，不承诺某一功效。
- 不依据中途测试结果的方向或显著性追加/停止采样；如需要成本修订，在正式测试开始前冻结。

## 10. 资源可行性与实施检查

当前离线、无 GPU、无权重/数据/依赖的环境不能产生有效评测结果。设计工作不依赖这些资源；后续须通过允许的离线导入方式提供制品和依赖。

粗略内存依据是 `参数量 × 每参数字节数`：约 7B 参数的模型仅权重 FP32 约 28 GB（十进制），FP16/BF16 约 14 GB；约 124M 参数 GPT-2 对应约 0.50 GB / 0.25 GB。精确值须核对检查点配置，这些不是本环境实测。实际进程还需 KV cache、激活、临时缓冲、tokenizer 及加载开销；避免同时加载两个模型，关闭梯度、按 batch size 1 开始，并为加载峰值留余量。GPU 可提高吞吐但不是定义上必需，30 个 CPU 亲和核也不等于已知 RAM 或可保证的速度。

后续先在非测试或人工构造的短、中、长输入上做小规模计时与内存测量：分别记录加载/预热时间、每例 prefill、decode、生成长度和峰值内存；共同预算与原生条件分开测。按正式清单的输入长度分层，用各层样本数乘对应每例时间求和，再加加载和合理调度开销，形成总成本估计范围，不承诺运行时间。原生长上下文可能显著增加 cache 和 prefill 成本，单独决定是否可行。

正式运行前的轻量检查包括：两个 tokenizer 的完整提示长度断言；跨/仅本文条件本文字节完全相同；目标不进入构建函数；换行与 EOS 提取单元测试；评价边界例；失败计分；仓库配对重采样实现；相同输入重复解码一致性。人工例子上的检查不构成实验结果。
