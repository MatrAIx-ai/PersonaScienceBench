- 报告 FP16 与量化困惑度、绝对变化及相对变化，并对同一窗口的损失做配对分析。校准参数不得据 test 结果反复调优。

## 6. 计时边界、输出计数与缓存协议

### 6.1 每个完整请求的状态
每次请求从空的逻辑 KV cache 开始，不复用前一请求的任何有效键值。输入已驻留 GPU，模型已加载并预热。缓存采用双方尽可能一致的稳态内存管理策略：允许预先创建内存池或预分配最大缓存缓冲区；其容量计入显存。每次请求必需的逻辑重置、索引初始化和实际缓存分配/扩展若未由预分配消除，均在计时内。框架测试夹具的对象清理在请求之间完成，不允许借此将真实推理所需的缓存转换移出计时。

### 6.2 预填充
起点：GPU 同步后开始计时，尚未进行该请求的缓存初始化及提示 forward。
终点：完成 L 个提示 token 的 forward、在线转换及缓存写入，并用最后位置 logits 在 GPU 上贪心选择第一个输出 token y1，随后同步 GPU。

该阶段结束时，每序列 KV 长度为 L；y1 已生成，但尚未作为输入写入 KV。主指标的名称为“预填充阶段延迟（含首 token 选择）”，避免将其误称为纯 GEMM 时间。

### 6.3 解码
紧接本请求的预填充结果，不用虚构零缓存或从另一精度组复制缓存。启动独立解码计时，然后执行 **D = G − 1 = 127 次** 自回归 forward：第 1 次输入 y1、写入其 KV 并产生 y2；最后一次输入 y127、产生 y128。

每步包含 KV 读取与追加、旋转、量化/反量化、模型 forward 和 GPU 贪心选择。第 k 次解码前有效缓存长度为 L+k−1，结束后为 L+k。最终缓存长度 L+127，而不是 L+128：最后生成的 y128 不再送入模型。

计时在完成 y128 并同步 GPU 后结束。每次重复都从自己的预填充重建缓存，不连续延长上一重复的缓存。FP16 与 QuaRot 各自使用本方案的真实缓存路径。

### 6.4 计时实现与公式
主计时采用高分辨率主机时钟，配合阶段边界的 GPU 同步，包含主机发射和阶段结束等待。解码循环内部不逐 token 强制同步。预填充/解码边界同步是隔离阶段的测量定义，两方案一致；因此该总和不是在线服务端到端延迟。可用少量 CUDA events 作非侵入交叉检查，不能用纯 GPU 时间替换主机侧时间而不注明。

设某请求预填充耗时 TP、解码耗时 TD（单位秒）：

| 指标 | 公式 | 解释 |
|---|---|---|
| 预填充阶段延迟 | TP | 整批完成提示和首输出的时间 |
| 预填充吞吐 | B×L / TP | 输入 token/s，包含上述阶段边界内开销 |
| 平均解码步延迟 | TD / 127 | 整批一次自回归迭代的平均时间 |
| 每序列平均逐输出 token 延迟 | TD / 127 | 等长同步批中每条序列的平均 token 间隔 |
| 全批解码吞吐 | B×127 / TD | 只计解码阶段产生的输出 token |
| 模型端首 token 延迟 | TP | 输入已在 GPU；不含排队、分词或传输 |
| 模型端请求阶段总时间 | TP + TD | 含人为阶段边界，不能直接当服务延迟 |
| 请求总输出吞吐 | B×128 / (TP+TD) | 含预填充，明确区别于纯解码吞吐 |

**全批吞吐的倒数 TD/(B×127) 不是单序列逐 token 延迟**；B>1 时尤其不能混用。TP 已包含第一个输出，故不能在 TD 的吞吐分子中再次计入 y1。

主测量报告请求级分布及聚合解码延迟，不声称获得每一步的 p95。逐步延迟随缓存增长、kernel 时间和带宽等只在另行诊断运行中采集，以避免 profiler 或每步同步污染主计时。

## 7. 正式测量协议与统计规则
1. 完成准入和质量评估，冻结所有配置。每个模型只常驻一个方案，避免同时驻留另一模型占用显存。
2. 每个形状与方案正式计时前预热 5 个完整请求，覆盖预填充及全部 127 个解码步，触发编译和内存池初始化。若第 5 次之后仍有首次编译或初始化，标记预热未完成，在预实验阶段制定更长的统一规则并重新开始，不能混入正式样本。
3. 对每个模型进行 30 轮配对测量。每轮双方各测 9 个负载条件，使用同一轮的输入清单。方案顺序 15 轮 FP16→QuaRot、15 轮 QuaRot→FP16，以固定种子随机排列；条件顺序也预先随机化，配对双方采用同一条件顺序。
4. 每轮方案加载后重新按上述规则预热。模型切换、加载、校准和预热都不计入请求耗时。每个正式请求重建自己的逻辑缓存；30 个配对重复不是同一次请求里的 127 个 token。
5. 记录全部原始时间、顺序、内存及系统异常。硬件错误、其他进程干扰等按预先定义的原因标记，保留原记录，必要时补测整个配对；不凭离群值本身删数据。
6. 对每单元分别报告 TP、TD/127、吞吐的中位数、四分位距和请求级 p95；30 次重复下 p95 只作描述性指标，不宣传精确尾延迟保证。
7. 主要配对效应取每轮 log(TFP16/TQuaRot)，求均值后指数化，得到几何平均延迟加速比 S。对 30 个完整配对轮次进行 10000 次有放回 bootstrap，报告 S 的 95% 百分位置信区间，固定 bootstrap 种子。吞吐比较也按相同输入工作量配对，不能将平均吞吐之比与配对延迟比混为同一估计量。
8. 配对轮次是统计重采样单位，而非 batch 内序列或解码 token。重复请求的缓存和输入是独立初始化的，但共享硬件可能存在时间相关性；检查运行顺序图，必要时另作按相邻轮次分块的敏感性分析。单机器置信区间不代表跨硬件部署的泛化误差。

## 8. 显存、OOM 与容量优势
显存使用单独的测量 pass，避免峰值计数和诊断工具干扰主延迟。报告加载后占用、请求峰值、分配/保留显存、KV 有效载荷及其元数据，注明框架计数与设备级计数差别。

- 主矩阵中仅对双方均成功的条件计算加速比。
- OOM 记为 OOM，保留失败阶段、负载及内存信息；在干净进程中复核一次以排除遗留状态。不缩小该单元的批量、换卡或使用 offload 来给某一组补出速度。
- 一方 OOM、另一方成功时，只说明在该配置下的可运行性优势；不报告“无限加速”，也不将缺失条件默默删掉。
- 可选容量扫描在相同硬件上分别寻找给定 L、G 下的最大可运行 B，采用预先规定的批量递增和边界验证。容量条件的吞吐与固定 B 的速度放在不同表中，不混合归因。
- 70B 若需要多卡，为双方采用相同卡数、并行策略及互联，并另成扩展表。若只有 QuaRot 能单卡运行，单卡事实属于容量结果，不与多卡 FP16 形成主加速比。

## 9. 分析与判断规则
按模型规模、B、L 分面展示预填充及解码延迟加速比和置信区间，并联看吞吐、显存和质量变化。优先解释负载交互，而非把所有条件压成一个“QuaRot 加速倍数”。如需整体摘要，预先采用各主单元等权几何平均，并明确哪些条件因 OOM 未纳入；不得用选择成功子集的摘要掩盖失败。

预填充可能更受矩阵计算和内核效率影响；解码可能更受权重/KV 访存影响。这只是诊断假设。另行剖析代表性小/大批条件，检查转换、旋转、内核发射、attention 与访存开销，不能单凭阶段名称判定瓶颈。

每单元、每阶段以 S 的 95% 区间分类：
- 下界 > 1：有证据支持加速；
- 上界 < 1：有证据支持减速；
- 区间包含 1：方向差异不确定，不等于已证明等效。

另以预先声明的 3% 为实用意义阈值：下界 > 1.03 才称“超过阈值的加速”，上界 < 1/1.03 才称“超过阈值的减速”。接近 1 的显著变化须标注实用影响较小。各单元区间是点态区间，不自动支持“所有负载均加速”的全局声明。性能判断与质量护栏分别报告，二者同时满足才描述为质量约束下的部署优势。
